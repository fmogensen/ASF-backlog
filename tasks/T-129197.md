The spec's design §6, §5's registration triple, §1 and §2's install rewrite — in that order inside
the Task, because each is green alone and the next one needs it (**PD1**, **PD4**, **PD5**). This is
the card's cause: `bootout` returns when launchd has *signalled* the job, the `bootstrap` on the
next line is refused while the service is still in the domain, and the clock the command was run to
install is gone (`asf/scheduler.py:926-927`). The condition the bootstrap was missing is one the
product's own `status` reader already answers.

The retry is **not** here. Task 1 leaves `_launchd_install`'s bootstrap block exactly as it is
today — `rc == 0` → `bootstrapped <label>`, else `bootstrap <label> failed (<why>)` — and Task 2
extracts it into `_bootstrap_with_one_retry`. §2's sketch shows the finished shape; the coder
should write the wait around today's bootstrap and let Task 2 replace the last two lines.
