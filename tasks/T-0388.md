## Description
stories: S-33057
writes: asf/tick/step_daily.py, tests/test_tick_steps.py, tests/test_product_loop.py
after: Task 4

§2.7's step, and D12: a product measurement is a daily reading by nature, because a verdict needs
`min_readings` on each side of a landing and a weekly cadence would put the first verdict a month
out. `run_part` already turns a part's exception into rc 1 and one line without stopping the others
(`asf/tick/step_daily.py:40-50`), which matters more here than anywhere else in that list: this part
shells out to a command the operator wrote.

**Files**

- `asf/tick/step_daily.py` — the fourth entry in `parts()`, and the module docstring naming it
- `tests/test_tick_steps.py` — the part is listed and an exception in it is isolated
- `tests/test_product_loop.py` — `DailyTests`

**Steps**

1. `asf/tick/step_daily.py`: `from asf.product_loop.loop import daily as product_daily` beside the
   `scorecard_daily` import at `:30`, and §2.7's fourth entry appended to `parts()` after
   `scorecard`, with its two-line comment copied as it stands — *the product loop: measure the
   product itself, propose a card per breached guardrail, revert a change the measurement got worse
   after (F-0050)*.
2. The module docstring's first paragraph gains the fourth part in the same voice as the three
   already named, so the step's own documentation lists what it runs.
3. Nothing else in the module changes: `run_part` (`:40`) and `run` (`:52`) are generic over
   `parts()`, the stamp logic is the tick's, and a part returning 0 with one line is all a new part
   has to be.
4. `tests/test_tick_steps.py`: `parts()` for a product lists `product-loop` fourth, by name and by
   position; a `product_daily` patched to raise yields rc 1 with one line from `run_part` and the
   other three parts still run and are still reported. Use the existing `StepsTestCase` fixtures
   (`:38`) rather than a new harness.
5. `DailyTests`, T8's first half: a product with no `improve.product` prints
   `product-loop: not configured` and returns 0, so the daily step's rc is unchanged (D13); a
   product with measurements and a refusal prints each refusal prefixed `NEEDS OPERATOR: ` and
   returns 0; a configured product with a `run=` double takes its readings, appends one line to the
   readings file and prints the summary line in §2.4 step 7's shape. T8's second half —
   `docs/products.example.yaml` still loads as a product and its `improve.product` parses into the
   `Settings` T1 asserts — is one test here too, reading that file the way `tests/test_env.py:18`
   does; it is the assertion that couples Task 1's example block to this Feature's own parser rather
   than to `validate_product_text` alone.
