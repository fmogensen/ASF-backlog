after: Task 5

The spec's §`asf/doctor.py` and its Documentation bullet. `UPGRADE AVAILABLE` is once per tag by
design, so the standing statement has to live somewhere that is never once-only: `asf status`'s
Version row already does half of it (P6, and Task 2 routed it through the same cache), and this row
is the other half. It waits on Task 5 for the `rolled-back` state its second RED case reads.

**Files**

- `asf/doctor.py` — the `upgrade` row, beside the `drift` row (`:848-849`)
- `docs/guide/upgrading.md` — a `## The release channel` section
- `tests/test_doctor.py` — `UpgradeRowTests`

**Steps**

1. One `rows.append(('upgrade', True, ok, detail))` after the `drift` row. There is no `ROWS` table
   to register it in — F-0108's Task 2 has not landed and `run` has 44 `append` sites today (PD11)
   — and no `###` section is required of it, because F-0108's check 3 does not exist either.
2. The green detail is the spec's: the policy, the installed release, the newest known release and
   the age of the cache entry — `auto · running v0.1.62 · newest release v0.1.63 available (read
   12m ago)`; `auto · running v0.1.62 · current` when there is nothing newer.
3. RED, case one (D2): `upgrade: "atuo" is not auto|notify|off — reading it as notify`, read off
   `Product.upgrade_declared` so the row quotes the word the operator actually wrote (PD13). A typo
   must never be the reason a factory installs unattended, and it must never be silent either.
4. RED, case two: `v0.1.63 was rolled back after a RED doctor; held at v0.1.62 (see B-xxxx)` — the
   channel state's `last.result == 'rolled-back'` **and** `last.to` still the newest known release.
   The product is stuck on a release it cannot take, and once a newer tag is cut the row goes green
   again by itself, because the channel will try that one.
5. A product whose repo is the factory's own source gets `trunk channel (this repo is the factory's
   own source) — approvals.upgrade: <word>` and is never RED for an `upgrade:` key it does not
   read. The row asks `drift.is_factory_source` — the same structural question the tick's fork asks
   (D3), so the two can never disagree.
6. **The row is read-only and costs no network.** It calls `latest_release` in a form that takes the
   cache as it stands and never triggers an `ls-remote` of its own: `asf doctor` is run by hand, by
   CI and by the tick's health step, and a row that shelled out to a remote would put three
   `ls-remote` an hour per product on top of the one the hour is meant to cap (D4). The step's
   implementation is a direct read of `releases_path()`, not `latest_release(url)`, and the comment
   says why.
7. `docs/guide/upgrading.md` gains `## The release channel` after `## Upgrading`: the three
   policies and the default; the hour and the one shared cache; what `auto` does in order (install
   at the tag, re-render the clocks, run the doctor through the new install) and that it ends the
   tick; what a rollback writes — the `rollback:` line, the restored tag, the one S1 Bug per
   release; the two log lines and the digest row; and the sentence the spec asks for, that a
   product whose repo is ASF's own source is on the trunk channel instead, under
   `approvals.upgrade`, and takes trunk heads rather than tags. It names no product and no operator
   — `tools/check_generic.sh` runs before the commit, not after.
8. `UpgradeRowTests`: the green row names the policy, the installed release and the cache age; a
   typo is RED and quotes the word; a `rolled-back` state at the newest tag is RED and names both
   releases; the same state with a newer tag since cut is not RED; a factory-source product gets
   the trunk-channel detail and is never RED for `upgrade:`; the row runs `git ls-remote` **zero**
   times.
