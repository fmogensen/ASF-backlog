§2.4, §2.5 and §2.6 — the thing the card asked for. Every *work* row of an item whose budget is
spent becomes one non-launching `OVER BUDGET` row, inside `candidates()` so that `asf next`, the
status cell, `briefs.build` and the groom's policy pass all see what the tick sees; the wave
prints that row's action verbatim; and I14 is what makes "no row is launched for an item whose
budget is spent" a checked property of the plan rather than of one function.

**Files**

- `asf/feeder/rows.py` — `OVER_BUDGET`, `BUDGET`, `FINISHING_KINDS`, `over_budget(rows, items,
  product)` (§2.4), and its call in `candidates()` after `hold_classes` (`:968`).
- `asf/invariants.py` — `FeederContext.items` (`:363-368`), `feeder_context` passing it (`:718`),
  `check_i14`, and the `Invariant('I14', 'feeder', _feeder_only(check_i14))` registration
  (`:609-611`); the module docstring's `feeder` list becomes `(I4, I5, I7, I14)`.
- `asf/tick/step_wave.py` — the non-launching branch of `launch()` (`:666-668`).
- `tests/test_feeder.py` — `NoWorkRowLaunchesForASpentBudget` (T4).
- `tests/test_invariants.py` — `I14Tests` (T5, second half).
- `tests/test_tick_steps.py` — `OverBudgetWaveTests` (T5, first half).

**Steps**

1. `FINISHING_KINDS = (PUSHED_REVIEW, CONFLICT, STALE)` with §2.4's comment: each ends the
   spending on work already done. A review of a branch already pushed is the last step before it
   lands; a rebase and a close are housekeeping on a branch that exists.
2. `over_budget(rows, items, product)` as §2.4 fences it, with one addition the fence omits and its
   own paragraph requires: `GROOM_ADJUDICATE` is exempt beside `FINISHING_KINDS`, the same
   exception `hold_unlanded` makes at `asf/feeder/rows.py:887` (P12). A non-launching row is
   passed through untouched — `PUSHED → LAND`, `ON TRUNK`, `APPROVED → LAND`, `WAITS ON …` say
   what the lane is doing and must not be overwritten by this one.
3. One line per item, not per row: the first launching row in emit order becomes the
   `OVER BUDGET` row (`waits_on='budget'`, the reason naming the three answers), every later
   launching row of that item is dropped.
4. The verdicts are memoised per item id inside the call: `budget.spent` is pure over the item's
   `cost:` block, and an item with a correction row, a PLAN → CODE row and a bug row is judged
   once.
5. `candidates()` gains `rows = over_budget(rows, items, product)` as the last hold, after
   `hold_classes` (`:968`) — anywhere later and the four callers that use `candidates()` directly
   would each show a row the tick would not launch (§1.4).
6. `step_wave.launch()`: the `if not row.launches` branch prints `row.action` whole when
   `row.waits_on == feeder_rows.BUDGET`, and the `waits …` line otherwise (§2.5). No tick-line
   key, no event — the line is in the tick log, the verdict is on the card, the question is in the
   groom file.
7. `FeederContext.items: dict = field(default_factory=dict)`, documented in the class docstring
   beside `rows`; `feeder_context` passes the `items` it already takes (P15).
8. `check_i14(ctx)` — for each launching row whose kind is neither a `FINISHING_KINDS` one nor
   `GROOM_ADJUDICATE`, `budget.spent(conv, ctx.items.get(row.item_id) or {})`; over → one
   `Finding('I14', 'feeder', row_key(row), f'budget spent: …')` whose message is the verdict's two
   measures. An item with no `cost:` block has spent nothing. The conventions come off
   `ctx.product`, through the same `_conventions` the rows use.
9. Registered as `Invariant('I14', 'feeder', _feeder_only(check_i14))`; the docstring's `feeder`
   list updated. Both `feeder_waits` and `feeder_gate` then run it, which is right (P11).
10. `tests/test_feeder.NoWorkRowLaunchesForASpentBudget`: T4's matrix — nine row kinds × two
    over-measures, no launch and exactly on
