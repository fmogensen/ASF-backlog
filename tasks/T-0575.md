The spec's §3 and §4. After this Task a refusal is acted on rather than ignored, which is what makes
Task 4's assertion — two waves, four launches, never six — true.

**Read PD4 before touching the take site**: `cloud_tries` is spent inside `decide()` at
`asf/workers/wave.py:244`, before the take, so "spends no cloud try" needs an explicit rollback and
the retry must not spend a second one. **PD5** is why the degraded line is wired to `from_config`'s
`seats_degraded`, and **PD6** is the `already running` case to assert rather than fix.

**What changes for an operator when this lands.** Two new lines, and one fewer overcommit. A row
whose seat was claimed under it is decided again, silently, up to twice; if it then finds nothing it
waits with `seat claimed elsewhere — <acct> <load>/<cap>` instead of launching onto a full account.
A host that cannot use the ledger at all says so once, before the first row, and launches anyway.

**Files**

- `asf/workers/wave.py` — the take site at `:301` becomes the refusal branch; `running`, `branches`,
  `local_taken` and the `entry[1] = None` move below the successful take; `cloud_tries` is rolled
  back on a refusal (PD4); `settle`'s `untake` + `take` swap at `:255-256` becomes one `pool.retake`
  (C8); the degraded line joins `pool: sessions unreadable` at `:167-168`; `SEAT_RETRIES = 2` joins
  `REFRESH_S` and `DEFAULT_LAUNCH_CONCURRENCY` at the foot of the module (`:355-358`).
- `asf/workers/__init__.py` — `cmd_spawn` keeps the pool it built, takes its seat before
  `spawn.spawn(...)`, prints the refusal and returns 1, and `untake`s when the spawn raises.
- `tests/test_seat_claims.py` — `WaveRefusedSeat(Home)` added.

**Steps**

1. The take site, at `asf/workers/wave.py:301` (**not** `:296-306` — PD13 drift 1). The seat dict is
   built as it is today, then:

   ```python
   if not pool.take(acct, **seat):           # another product claimed it between the pick and now
       if lane == 'cloud':
           cloud_tries -= 1                  # decide() spent it before the take (PD4)
       refused[row.job] = refused.get(row.job, 0) + 1
       if refused[row.job] <= SEAT_RETRIES:
           said.remove(entry)                # decided again, as a freed seat re-decides today (P10)
           pending.insert(0, row)
           continue
       entry[1] = (f'seat claimed elsewhere — {acct.name} '
                   f'{pool.load(acct)}/{acct.cap:g}')
       continue
   ```

   `refused` is a dict initialised beside `branches`; `cloud_tries` is already `nonlocal` in `decide`
   and is a plain local of `wave`, so the decrement needs no new declaration at this scope. Only
   after the take returns `True` do `local_taken += 1`, `running.add(...)`,
   `branches[_branch(product, row)] = row.job`, `entry[1] = None` and the `ex.submit` run — a refused
   row has launched nothing and must hold no branch. The retry is bounded and terminating: the
   refusing read is now in `self.live`, so the next `decide` either finds another account or produces
   the true reason (`pool full — accounts at cap: …`); `SEAT_RETRIES` is a fence against a flapping
   ledger, not the mechanism (C7).
2. `said.remove(entry)` then `pending.insert(0, row)` is the `tentative` path's own shape
   (`asf/workers/wave.py:323-328`) applied to one entry instead of a list — the row goes back to the
   **head** of `pending` so it is decided before rows behind it, which is what a serial wave would
   have done.
3. `settle`'s model swap (`:255-256`) becomes `seat = pool.retake(acct, seat, rec.get('model'))`, and
   the swapped seat is what the rest of `settle` and any later `untake` use. This is the only reason
   `retake` exists: a refusal after a successful launch would free a seat for a running session (C8,
   PD9).
