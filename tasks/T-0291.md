§2.3's third adapter and §2.4's discovery. The one adapter that touches a filesystem, and the
fixture product's first rule card — which does not exist today (PD9) and without which §3.4 has
nothing to point at.

**Files**

- `sample/backlog/rules/R-0001.md` — the fixture product's first rule card: `enforced: true` and
  `check: rules/r-0001-id-matches-file.sh`.
- `sample/backlog/rules/r-0001-id-matches-file.sh` — the check script, mode `0o755`, record-scoped:
  it reads only under `$BACKLOG_ROOT`, exits 0 when every card's `id:` equals its file's stem, and
  exits 1 printing one `R-0001 <what> <where>` line per card that disagrees. Green on the sample's
  record as it stands (PD9).
- `sample/backlog/index.json` — regenerated so it carries `R-0001` with its `check:` and
  `enforced:` (`rules.load_rules` reads the index, never the card, `asf/rules/rules.py:76`).
- `asf/evals/adapters.py` — `rule_check_fires`, in `ADAPTERS`.
- `asf/evals/run.py` — the discovered half of the roster.
- `evals/manifest.json` — the `rules` family entry of §2.1, byte for byte.
- `evals/rules/R-0001/001-violates.json`, `002-clean.json` — the pair.
- `tests/test_evals.py` — `RuleLeverTests`.
- `tests/test_sample_product.py` — `SampleEvalsTest`, and the docstring's card count.

**Steps**

1. The card and its script, and `asf index` over the fixture record so `sample/backlog/index.json`
   carries `R-0001` — by the command, never by hand, and the diff is only that card's entry plus
   `generated`. Run `python3 -m asf.cli rules check --product sample` (or `rules.run_all` over the
   fixture root) and see zero violations before going further: a rule that is red in the fixture
   would make the sample's own tick file a Bug in a fixture (PD9).
2. `rule_check_fires(given, want)`, §2.3's four steps in order, and no fifth:
   a temp directory becomes the record root; `given.files` is `{relpath: contents}` written
   verbatim, `given.index` is written as `index.json`, `given.scripts` is `{relpath: contents}`
   written mode `0o755`; `rules.run_check(root, rule)` is called with `rules.TIMEOUT` set to
   `given.timeout_s` (default 10) and restored in a `finally`, and with `hermetic.GIT_HOOK`'s names
   removed from `os.environ` for the duration — `run_check` builds the child's environment from
   `os.environ` and already sets `BACKLOG_ROOT` and `cwd` itself, so the adapter sets neither
   (PD8); `broken` non-empty raises `Broken(broken[0]['line'])`; else `fired = bool(violations)`
   and every string in `want.lines_contain` must appear in some violation line; the temp tree is
   removed in a `finally`, answered or not.
3. A real product's rule lever names no script of its own: `given.files` is the fixture the check
   is pointed at, and the script comes from the product's record through `resolve_script`
   (`asf/rules/rules.py:63`). The fixture product's tasks ship both, which is what makes the
   adapter provable in this repo (§2.3's last paragraph).
4. `asf/evals/run.py`: the discovered roster. With a `record_root`, `rules.load_rules(root)` →
   `rules.partition` → the enforced list (P2), one `rule:<id>` lever per entry, its tasks looked
   for in the core set's `rules/<id>/` first and then in `<record root>/<conv.evals_dir>/rules/<id>/`
   (PD10), inheriting the `rules` family's `adapter` and `implements`. A discovered lever with no
   pair goes through §2.4's same three-row table — exempt with an entry, unrecorded without one —
   so a product that adds an enforced rule is never blocked, and never silent (§1.4).
5. `evals/manifest.json`: §2.1's `rules` entry, `"family": true`, `"tasks": "rules/{rule}"`,
   `implements` the three globs
