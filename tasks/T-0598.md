## Description
stories: S-37004
writes: asf/doctor.py, asf/views/status.py, tests/test_doctor.py, tests/test_views.py
after: Task 1

The spec's §6. The incident was read out of a log by hand: for twenty minutes the doctor's
`SCHEDULER` section and the status `Cron` row both read `ok`, because both call `held()`, which
returns `None` for the marker's owner and for any marker past its TTL (P11). The two places that
already answer "is this factory ticking" must also answer "and does it owe an install".

This Task needs `read_due()` and `due_label()` and nothing else this card adds, so it runs beside
Task 2. Its four files intersect no other Task's `writes:`.

**What changes for the machine when this lands.** `asf doctor`'s scheduler section gains a yellow
`upgrade  upgrade to 5cab3a2 due since 06:25 — pass 4 (owner asf)` row, and the status table's
`Cron` cell carries the same words as its prefix, for exactly the twenty minutes that read `ok` in
the incident. A park still wins where there is one — every existing row is unchanged — and neither
view resolves a sha against git.

**Files**

- `asf/doctor.py` — `scheduler_rows` (`:705-715`): the `marker`/`else` pair. Nothing else in the
  function, and no other section.
- `asf/views/status.py` — `cron_cell` (`:388-394`): the same pair, building `prefix`. The module
  docstring's `Cron` bullet (`:33-34`) gains the debt's half-sentence.
- `tests/test_doctor.py` — two tests added to `TestSchedulerSection`.
- `tests/test_views.py` — two tests added to `StatusViewTests`, beside
  `test_cron_names_the_upgrade_a_pending_marker_waits_on` (`:234-247`), which is not touched.

**Steps**

1. `doctor.scheduler_rows`:
   ```python
    marker = upgrade.held(product.name)
    if marker is not None:
        rows.append((YELLOW, 'upgrade', upgrade.held_label(marker)))
    else:
        owed = upgrade.read_due()          # read_due, not due: no git in a view (P11)
        if owed is not None:
            rows.append((YELLOW, 'upgrade', upgrade.due_label(owed)))
   ```
   inserted where the single `marker` block is now, above the `scheduler.interval_s` row, so the
   wait stays the section's first line and the jobs' `ok` is never read as a ticking factory. The
   existing comment gains one sentence: the owner reads no *marker* here, and past the grace it is
   the debt that says why it is not ticking either.
2. `views.status.cron_cell`: the same shape, producing `prefix`:
   ```python
    marker = upgrade.held(product.name)
    owed = upgrade.read_due() if marker is None else None
    label = upgrade.held_label(marker) if marker is not None else (
        upgrade.due_label(owed) if owed is not None else None)
    prefix = f'{label}; ' if label else ''
   ```
   Every path below `prefix` is untouched — the `not_configured` return, the `no job loaded` return
   and the clock rows all still carry it.
3. `status.py`'s module docstring bullet: after the `held` sentence, "and
   ``upgrade to <sha> due since <time> — pass N (owner <product>)`` when no marker is showing and
   the factory still owes an install (:func:`asf.upgrade.read_due`)".
4. `TestSchedulerSection` gains: a debt with **no** marker gives one `YELLOW` `upgrade` row whose
   detail is `upgrade to 5cab3a2 due since HH:MM — pass 4 (owner sample)`, and the loaded job's own
   row is still there and still `OK`; and a fresh marker **plus** a debt gives the marker's row and
   not the debt's (the park still wins). Both use the class's existing temp `env.ASF_HOME`
   (`tests/test_doctor.py:731-741`), so the operator's home is never read.
5. `StatusViewTests` gains the two matching cases against `status.cron_cell`, and one that pins
   C10's rule: with `asf.drift.factory_root` patched to raise, both views still render — neither
   resolves a sha against git, which is why they read `read_due()` and not `due()`. The existing
   `test_cron_names_the_upgrade_a_pending_marker_waits_on` stays green unchanged.
