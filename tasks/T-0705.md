The spec's `## The design` §4 in full: `enduser.covered(product, repo, deployed, candidate)`, the
walk lifted so both callers share it, and `deploy.enduser_refusal(product, f, env)` at exactly the
two sites `marker_refusal` occupies.

Both sites, or the gate is a lie. `marker_refusal` is called at `asf/harvest/deploy.py:888` (in
`view_line`) and `:955` (in `tick`), and the docstring at `:882-885` says why: *"a view promised a
deploy for an hour that the tick kept refusing."* `enduser_refusal` goes immediately after each,
so the marker gate keeps first claim (`## Out`: the cheap check runs first, and no enduser session
is spent on a page with a placeholder still in it).

Read **PD14**: an absent ledger and an unreadable one are not the same, and collapsing them either
freezes a product's first deploy or opens the gate on an I/O error.

**Files**

- `asf/views/prod.py` — `_landings` (`:120-135`) and `_changed` (`:138`) get a module-level entry
  point the deploy pass can call; the view's own callers are unchanged. Nothing else moves here —
  the State cell is Task 6's.
- `asf/enduser.py` — `covered(product, repo, deployed, candidate)`, returning the **uncovered**
  landings newest first (the name is the spec's; the return is the gap, as §4's step 5 says).
- `asf/harvest/deploy.py` — `enduser_refusal(product, f, env)`, and its two call sites.
- `tests/test_enduser.py` — `class DeployGate`.

**Steps**

1. Lift the walk. `prod._landings` already returns `[(sha, parents, subject, pr)]` for the trunk's
   own first-parent commits that land a PR, and `prod._changed` gives a landing's files against its
   first parent. Expose them (a public name in `prod.py`, or a small module both import) and have
   `enduser.covered` call the same code — §4 is explicit that two walks that can disagree about what
   a landing is are the failure to avoid.
2. `covered` is §4's five steps in order: walk `deployed..candidate`; keep the landings whose
   changed files match `enduser.paths(conv)`; drop every landing older than the floor; a landing is
   covered when a ledger row approves it **by trunk sha or by PR number**; return the uncovered ones
   newest first.
3. The floor (D7) is the earliest ledger row's own landing, or `customer_content.enduser_from` when
   the operator set one. With no ledger rows there is no floor and therefore nothing above it:
   `covered` returns `[]`, and a product turning the gate on does not have its deploy frozen by
   history. That is D7's whole argument and it is the first thing `DeployGate` asserts.
4. PD14: `enduser.rows` distinguishes absent from unreadable. `covered` returns `[]` for absent and
   raises for unreadable; `enduser_refusal` catches the raise and returns the *unchecked* refusal —
   the same shape `marker_refusal` gives for a tree it could not read (`:928-930`), *not deployed to
   `<env>` unchecked*. An unreadable walk (the `git log` returning nothing usable) refuses the same
   way. The gate never opens on an error.
5. `enduser_refusal(product, f, env)` returns one line or None, in `marker_refusal`'s voice, naming
   the count and the PR numbers with their titles, and ending *nothing deploys to `<env>` until each
   is reviewed (asf prod names them)* — §4's text. It returns None at once when
   `not enduser.enabled(product)`, so a product with the gate off pays one attribute read and
   `asf prod`/`asf status` are byte-identical for it.
6. The two call sites, each immediately after the `marker_refusal` block: in `tick` (`:955-958`)
   print the line and `continue`, no dispatch; in `view_line` (`:886-891`) return the line in place
   of the read-only text. The gate applies to **every** environment and named target — prod, dev and
   each target — because the incident was a site target, not the app (§4).
