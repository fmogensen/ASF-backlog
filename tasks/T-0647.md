## Description
stories: S-36453

after: Task 2

The spec's `## The design` §5, and nothing else. This is the one reader that *acts* — it raises the
cause a card is filed from — so without it the classification is a number in a table. After this
lands, the card's own five six-hour runs raise `ci-job:tests (3.12)` at 5.0 red runs a week against
a 3.0 threshold, where today they score a clean sheet.

Read **PD6 before editing `rank`**: that function has **two** `setdefault` literals and the spec's
diff shows one, while its acceptance tests the other. Read **PD7 before editing `causes`**: the
detail string is a positional argument followed by `scheme=`, not the end of a statement. The cause
**key is not renamed** — `ci-job:<name>` stays exactly what `metric` and `verify` read today, which
is the whole of C11: a card already filed against it is verified by the same reading, and the count
can only go up.

**Files**

- `asf/scorecard/diagnose.py` — `from asf import ci_jobs` beside the module's two imports (`:20-21`);
  both `setdefault` literals in `rank` (`:211-212` and `:220`); the `red` predicate and the two
  counters (`:213-215`); the `ci-job:` cause's detail line (`:311-315`).
- `tests/test_scorecard.py` — new tests in `DiagnoseTests` (`:318`).

**Steps**

1. `from asf import ci_jobs` at module level. `asf.ci_jobs` imports `asf.ci_pool`, which imports
   `asf.env` and stdlib only, and `asf.scorecard.diagnose` imports `asf.scorecard.score` and
   `asf.scorecard.facts` — no cycle.
2. Both `setdefault` literals gain `'timeouts': 0, 'runner_losses': 0` (PD6). The gate loop's body is
   otherwise untouched: a gate is not a job, has no `cause`, and neither counter is ever incremented
   there — which is exactly what keeps `by_ci_job`'s rows one shape.
3. The job counter's body gains `cause = j.get('cause')`, `c['timeouts'] += 1 if cause ==
   ci_jobs.TIMEOUT else 0`, `c['runner_losses'] += 1 if cause == ci_jobs.RUNNER_LOSS else 0`, and the
   `red` predicate becomes `j.get('conclusion') not in ('success', 'skipped', 'neutral', 'cancelled')
   or cause in (ci_jobs.TIMEOUT, ci_jobs.RUNNER_LOSS)`, with the spec's three-line comment above it.
   A `failure`-class cancel and an unclassified one stay not-red, as today — measured: the
   `facts_fixture`'s ci row (`tests/test_scorecard.py:92-93`) carries job dicts with no `cause` key
   at all, so `j.get('cause')` is `None` and every existing `DiagnoseTests` assertion holds
   unchanged.
4. The `ci-job:` cause's detail gains `+ (f" {c['timeouts']} ran to their limit." if c['timeouts']
   else '')` and `+ (f" {c['runner_losses']} lost their runner." if c['runner_losses'] else '')`
   **inside** the positional argument, before the `,` and the `scheme=` keyword that follow it
   (PD7). No key, scope, threshold or unit changes.
5. The new `DiagnoseTests` cases are the Acceptance below. `metric(facts, 'ci-job:<name>', …)` needs
   no change at all: it reads `c['red']` off `rank`'s `by_ci_job` under the same key it reads now
   (`:262-266`), and the test asserts that rather than a new call.

`cause: 'timeout'` counts **red** under the unchanged key `ci-job:<name>`, with `timeouts: 1`;
`runner-loss` likewise, with `runner_losses: 1`; a `failure`-class cancel and a cancel with no
`cause` count as a run and **not** red, as today; `metric(facts, 'ci-job:<name>', …)` reads the new
count off the same key it reads now; five timed-out runs in the window raise a `PRODUCT` cause over
the default 3.0/w
