## Description

after: Task 1, Task 2

The spec's last two **In** bullets, `## The design` §`asf/scorecard/facts.py`, the `lead_days` half of
§`asf/scorecard/score.py`, and D10's change to the lead-time cause's gate. A migrated card's lead time
stops being a number that is always too small and always in the same direction. It waits on Tasks 1
and 2 because it writes `asf/scorecard/diagnose.py` and `tests/test_scorecard.py` too, and on Task 1
for `asf/scorecard/score.py`.

**Files**

- `asf/scorecard/facts.py` — `MIGRATED_RE`; `timeline`'s `created_migrated` (`:107-161`)
- `asf/scorecard/score.py` — `lead_days(item, to)` beside `days_between` (`:82-86`), and its three
  call sites (`:188`, `:189`, `:229`)
- `asf/scorecard/diagnose.py` — the lead-time cause's gate and detail (`:205-212`)
- `tests/test_scorecard.py` — `MigratedLeadTimeTests`

**Steps**

1. `asf/scorecard/facts.py`: `MIGRATED_RE = re.compile(r'\bcreated \(migrate\)')` with the spec's
   `#:` comment byte for byte, beside the other module regexes at `:28-31`. `re` is already imported.
2. `timeline` (`:107`): `migrated = bool(lines and MIGRATED_RE.search(lines[0][1]))` computed from
   the line it already has in hand, and `'created_migrated': migrated` added to the returned dict.
   **The first line only** (D12): `history()` returns the whole stripped line as the tuple's second
   element (`:92`, re-read), so `lines[0][1]` is the text the marker sits in, and scanning the whole
   History would condemn a card that merely mentions a migration later. `created` itself is
   **unchanged** — the date is still read, it is only never measured from.
3. Nothing else in `facts.py` moves: `card` spreads the timeline dict (`:201-204`), so
   `created_migrated` reaches every `Facts` item with no second edit (P17). `TimelineTests` asserts
   key by key, never the whole dict, so the new key breaks nothing there.
4. `asf/scorecard/score.py`: `lead_days(item, to)` directly after `days_between` (`:86`), with the
   spec's docstring and one-line body byte for byte. It is a named helper and not three inlined
   conditionals because the reason a lead time is missing is a **rule** (D11), and the docstring is
   where the next reader looks when a `—` shows up in the Lead column.
5. Its three call sites, and only those three — measured: `grep -n days_between asf/` gives the
   definition at `:82` and calls at `:188`, `:189`, `:229` (PD13). `:188-189` become
   `lead_days(f, f.get('landed'))` and `lead_days(f, f.get('prod'))`; `:229` becomes
   `median([lead_days(t, t.get('landed')) for t in tasks])`. `days_between` itself stays, unchanged
   and still exported — `lead_days` wraps it.
6. `window_row`'s keys do **not** change (P21): `median_lead_days`, `median_prod_days` and
   `median_task_days` keep their names and their places, and the stored
   `state/<product>/scorecard.jsonl` row keeps its schema. Only the values move. Every median and
   mean over them already drops `None` (P18, `:77-79`), so `by_unit`, `by_lane` and the pair table
   need no edit at all.
7. `asf/scorecard/diagnose.py` (`:205-212`), D10: `landed` stays the whole window's landings, and a
   second list holds the rows whose `lead_days` is not `None`. The gate counts **that** list
   (`>= 3`), the median is taken over it, and the detail says *"median over the N of M Features
   landed in D days"*. Without this, a window of three landings that are all migrated passes a gate
   that says "needs 3 landings", takes a median of nothing, and is saved only by the `lead is not
   None` two lines down — a guard propping up a rule that no longer states what it means.
8. **PD4 — read it before touching `metric`.** `metric`'s `lead-time` branch (`:162-163`) is
   **unchanged**. It answers *what does this number read over this window* for a cause already filed,
