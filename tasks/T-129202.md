The spec's design §4, and the half of S-99856 that is registration rather than reading. Two names
enter the registry, the planned-flag fixture and the example product file, and **nothing reads them
yet** — that is the point of landing them first. `tests/test_conventions_flags.py` fails on a flag
read in `asf/` that the registry lacks, never on a registry name nothing reads (its one assertion is
`{n: f for n, f in flags_read().items() if n not in conventions.KNOWN_FLAGS} == {}`, `:50-52`), so
this Task is green alone, and Task 2's `settings` finds both names already registered (**PD1**).

**Files**

- `asf/conventions.py` — `'relaunch_total_cap'` and `'relaunch_total_kinds'` added to
  `KNOWN_FLAGS` beside `'relaunch_same_report'` and `'relaunch_daily_cap'` (`:409`, not the `:403`
  the spec cites — **PD4**).
- `tests/test_env.py` — `'relaunch_total_cap': '6'` and `'relaunch_total_kinds': '[correct]'` added
  to `_PLANNED_FLAG_VALUES` (`:761`), beside the two relaunch entries at `:770`. This file is not
  optional and not separable: `PinnedReader` (`:833`) asserts
  `set(_PLANNED_FLAG_VALUES) == set(KNOWN_FLAGS)` at `:838` — a set equality in both directions — so
  the registry edit above goes red without it (`:838`, not the `:837` the spec cites — **PD4**).
- `docs/products.example.yaml` — two commented lines after the `relaunch_daily_cap` block, which
  ends at `:374` (the two existing relaunch lines are `:367-374`, not the `:366-373` the spec cites
  — **PD4**), in the voice of the two above them: each naming its constant, its default and what
  `off` does.

**Steps**

1. Add both names to `KNOWN_FLAGS` on the `'relaunch_same_report', 'relaunch_daily_cap',` line's
   group, keeping that group's order and its line width.
2. Add both entries to `_PLANNED_FLAG_VALUES` as strings, on the line that already carries
   `'relaunch_same_report': '2', 'relaunch_daily_cap': '6',` (`:770`) or a line beside it. The
   values are the defaults the spec states: `'6'` and `'[correct]'`. `PLANNED_PRODUCT` is generated
   from this dict (`:776-784`, the comprehension at `:784`), so both become real
   `conventions.flags` entries in the product file the fixture builds and must parse and read back
   clean — which is what `ProductFlags` (`:714`) and `PinnedReader` (`:833`) check.
3. Add the two yaml lines, e.g.

   ```yaml
   #   relaunch_total_cap: 6    # asf.workers.loops.TOTAL_CAP (default 6): launches of one job
   #                            # since the item's latest unpark before the loop guard parks it,
   #                            # whatever changed between them and however long it took — the
   #                            # ceiling no moved head, new cause, new finding or new day resets.
   #                            # off: rule disabled
   #   relaunch_total_kinds: [correct]  # asf.workers.loops.TOTAL_KINDS (default [correct]): the
   #                            # job kinds relaunch_total_cap applies to. A kind outside it is
   #                            # judged by the same-report and daily rules alone. off: no kind
   ```

4. Run the Gate. `PinnedReader` runs the fixture's product file through older pinned ASF shas in
   their own processes; new flag names are safe there by construction — `flags` is not in
   `PINNED_VALIDATED_CONVENTIONS` (the frozenset at `:815-818`, asserted at `:849`) — and this Task
   is where that is confirmed rather than assumed.
