The spec's `## The design` §3's `judge`, §3.1 and §3.2 — the ladder, the red path's one job log, the
split, the trunk-alone read, and the land. After this lands, a product on `gate_where: ci` has a
working landing gate: the trunk is fast-forwarded to the **exact sha** CI was green on, a red gate
hands its session the same failing line and the same files the local gate gives it today, and a run
that never concluded is unknown rather than red.

Three things are load-bearing. **The gated sha is the landed sha** (D3) — git itself refuses
anything else, and `lane.is_ancestor(trunk_sha, sha)` is re-read immediately before the push, in
`merge_queue.land`'s shape (`:454-459`); the trunk moving under the push is not an error, the next
pass reads the gate as `stale` and cuts it again. **The correction must not degrade**: D7's whole
argument is that `H.first_failing_line`, `H.gate_files` and `H.red_modules` are pure over text
(P17) and the CI log contains `tools/run_tests.py`'s output verbatim, so the session gets what it
gets today — including the footprint widening that rides on `gate_files`. And a **pending or
cancelled** run is dropped and cut again, never red, never a correction (D6): `gate_timeout_s`
bounds a process and there is no process here.

Read **PD8 before writing `land`** — the green path reads a job log too, and §3.2 does not say so.
**PD10 before the trunk push** — it asks the CI start queue, as the path it replaces does.
**PD15** for the run this factory did not cancel but something else might.
