## Description
stories: S-37755
writes: asf/views/prod.py, tests/test_enduser.py
after: Task 5

The spec's `## The design` §6, the `asf prod` half: each NOT LIVE and ON PROD row whose landing
touches `enduser.paths(conv)` gains its enduser state as a clause on the existing State cell. **The
column count does not change** — `| Target | What | State | PR |` is what it is.

Read **PD6**: `_customer_rows` throws away the sha and the changed files the clause needs, and the
clause is driven by a different glob list from the one the row filter uses (D10), so it cannot be
derived from what the row carries today.

**Files**

- `asf/views/prod.py` — `_customer_rows` (`:160-168`) returns `(what, n, sha, files)`; `_check_rows`
  (`:175-194`) appends the clause. `_is_customer`, `_landings`, `_changed`, `PR_SUBJECTS`,
  `NOT_LIVE_ROWS` and the row filter are unchanged.
- `tests/test_enduser.py` — `class ProdView`.

**Steps**

1. `_customer_rows` returns the sha and the changed files it already computed for `_is_customer`.
   No second walk, no second `_changed` (PD6).
2. `_check_rows` builds the clause per row: `· enduser ✓ r<n>` for a landing a ledger row approves,
   `· enduser ✗` for a customer-content landing with none, `· legal: signed` / `· legal: waits`
   where a legal path is in it, and **no clause at all** for a row whose landing does not match
   `enduser.paths(conv)` — the customer-*visible* but not customer-*content* row of §6's table, an
   API change the view already shows and cannot be asked this question about (D10).
3. A product with the gate off gets no clause anywhere, so `asf prod`'s output is byte-identical for
   it. This is not an optimisation; it is the same regression floor every other Task carries, and
   `ProdView` asserts it by comparing whole rendered rows.
4. The ledger lookup is by trunk sha **or** PR number, the same rule `covered` uses (Task 4, §4 step
   4) — the view and the gate answer the same question the same way, or a row says `✓` for a landing
   the deploy pass refuses.
5. `ProdView` — a NOT LIVE row and an ON PROD row each carry `enduser ✓ r<n>` for an approved
   landing and `enduser ✗` for an unapproved one; a legal landing carries `legal: signed` or
   `legal: waits`; a customer-visible-but-not-customer-content row carries no clause; the gate off
   gives byte-identical rows; the State cell is still one cell and the table still has four columns.
