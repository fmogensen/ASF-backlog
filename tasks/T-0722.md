## Description
stories: S-38353

after: Task 3

The spec's §2's second half and §3. After this Task the card's own defect is closed: a worker
session launched by `spawn` carries a rule for `bash tools/check_conventions.sh`, and a pool with
no `settings_file` configured — the case the card's evidence is from — gets a composed file where
it used to get `--settings` not at all.

The operator's file is read, never written. No rule of theirs, allow or deny, is removed; no key of
theirs is touched; and a configured path that is not on disk still refuses the launch.

Read **PD7** before writing `settings` — `console_perms.merge`, the function whose discipline the
spec says to copy exactly, is the one function here whose body must *not* be copied. Read **PD6**
for which exception still escapes and why, and **PD3** before running the Acceptance fence
verbatim: the class it names does not exist, and the tests belong in `TestRuntime`.

**Files**

- `asf/workers/worker_perms.py` — `settings(product, operator=None)` and `path(product, wp)`, the
  spec's §2 docstrings byte for byte. `json`, `os` and `asf.env` join the module imports; still no
  module-level `harvest` (PD5).
- `asf/workers/spawn.py` — **one line**, `:933`: `settings_file=settings_file(wp)` becomes
  `settings_file=worker_perms.path(product, wp)`, with `from asf.workers import worker_perms` at
  the module's import block (`:40-45`) — `worker_perms` has no module-level `harvest` import, so
  this costs nothing (PD5). `settings_file(wp)` (`:749-757`) keeps its signature, its
  `FileNotFoundError`, its docstring and its two tests: it becomes `path`'s reader of the
  operator's half rather than `spawn`'s only answer.
- `tests/test_worker_perms.py` — `class Compose`.
- `tests/test_workers.py` — the new cases in `class TestRuntime` (PD3), beside
  `test_command_line_carries_the_settings_file` (`:128`) and `test_settings_file_must_exist`
  (`:133`).

**Steps**

1. `settings(product, operator=None)` — `operator or {}` copied shallowly, its `permissions` block
   copied, its `allow` list copied, every rule of `allow_rules(product)` not already in it
   appended in order. **`permissions.deny` is neither read into nor written out** (PD7): a block
   with no `deny` key comes back with no `deny` key. Every unrelated top-level key and every
   unrelated key inside `permissions` is carried through untouched. Never reorder or deduplicate
   what the operator wrote — only append what is absent, after everything already there.
2. `path(product, wp)` — `spawn.settings_file(wp)` for the operator's path (imported inside the
   function; `spawn` imports `worker_perms` at module scope, so the other direction must be
   lazy), `_read`-shaped tolerance for a file that is there but unparseable, then
   `settings(product, operator)`, then `<env.state_dir(product)>/worker-settings.json`. **Written
   only when it differs from what is there** — read the existing file, compare the parsed objects,
   and return the path unwritten when they match, so the file's mtime is the record of when the
   rule set last changed. Write atomically (`<file>.<pid>` then `os.replace`), which is what keeps
   a half-written settings file from reaching a session that is starting concurrently. A
   configured-but-missing `settings_file` raises `FileNotFoundError` out of here, unchanged — P5's
   guarantee, and PD6's one deliberate exception to *"never raises"*.
3. `spawn`'s one line. Nothing else in `spawn` moves — not `settings_file`, not its callers, not
   the `Job` signature.
4. `Compose`'s five cases, the spec's list by name. `test_the_operators_rules_and_order_are_kept`
   is the load-bearing one and should be written first: an operator object with its own allow
   entries, a deny list and two unrelated top-level keys comes back with every one of them intact,
   its allow order preserved, the derived rules appended after. Add PD
