The spec's `## The design` §1 in full, and nothing else. After this lands, a product that configured
`ci.workflow` the documented way — a file name, as `docs/products.example.yaml:214-216` shows — stops
paging a week of every workflow's runs to discard all of them, and starts filing the flaky Bugs it
has never filed. The pass makes two requests plus one per unread run.

This Task is the one item in the card that is not a performance change. P1 and P2 together say the
pass lists 26–31 s of runs and then filters them with `r.get('name') == workflow`, comparing a run's
**display name** to a configured **file name** — so for the documented form it files nothing. Read
that before reading the design: the 25 s is the symptom, and the zero is the defect.

**Read PD7 before writing `collect`'s window.** `FakeRuns` rows carry no `created`, and a
`r['created']` in `collect` turns `PassTests` red with a `KeyError` against §3.1's own requirement
that it stay green unchanged. **Read PD8 before renaming a variable in `collect`** — today's `runs`
is already the sliced batch, and the output line counts it.

Three things are load-bearing. **The window may only move over runs that were actually read**
(D4): `MAX_RUNS_PER_PASS` and a failed `jobs()` listing both leave runs unread, and today's fixed
7-day window is the only thing that brings them back. A window narrowed to the last pass — which is
what the card's own first sentence suggests — would step over them and **lose flakes**. That is a
correctness regression in the name of speed, and D4 exists to refuse it. **The window is computed
from `created_at`, never from `ts`** (D5): `ts` is `updated_at or created_at`, the API filters on
`created`, and a run created at 10:00 and completed at 10:30 is excluded by a window of
`created >= 10:29:59`. Mixing the two clocks loses exactly the runs the overlap exists to catch.
And **the workflow id is never persisted** (D3): a renamed workflow file would make a stale id a
silent zero again, which is the defect being fixed.
