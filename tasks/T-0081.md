## Description
stories: S-15606, S-15602
writes: asf/tick/step_wave.py, asf/workers/pool.py, asf/workers/spawn.py, tests/test_tick_steps.py, tests/test_workers.py

§2.3's tick half and §2.5. Triage is pure because this Task does the reading, and the card's third
acceptance line — "the tick prints why an adjudicate row was raised, naming the two rounds" — is
one `out()` call here.

**Files**

- `asf/tick/step_wave.py` — `stale_briefs(product, root, index)`; `plan_inputs` gains
  `stale_briefs` and `rounds`; `worker_row` copies `brief.card_digest` onto `pool.Row`; `run`
  prints the adjudicate line and the triage line and appends the `triage` event.
- `asf/workers/pool.py` — `SESSION_FIELDS` gains `card_digest`; `Row` takes and keeps it.
- `asf/workers/spawn.py` — the launch record gains `card_digest`.
- `tests/test_tick_steps.py` — `AdjudicateLineTests`.
- `tests/test_workers.py` — expected untouched; in the footprint only so the one assertion that
  could move with a new ledger field is fixable inside this Task's diff.

**Steps**

1. `stale_briefs(product, root, index)` → `{item: the brief kind to re-run}`: the latest **ended**
   run of each item whose recorded `card_digest` differs from `briefs.card_digest` computed now.
   A run with no `card_digest` — every run launched before this change — claims nothing and is
   never stale (D4's migration answer). The kind is that run's own kind (D5).
2. `plan_inputs` returns `stale_briefs(...)` and `lifecycle.round_log(pool_mod.sessions_path(
   product))` beside what it returns today — one place, so the tick, `asf next` and the status cell
   plan the same rows (D3).
3. `worker_row` copies `brief.card_digest` onto the `pool.Row`; `spawn` writes it into the ledger
   record; `SESSION_FIELDS` gains the name (P10). A re-run after a stale brief therefore writes
   today's digest at launch, which is what makes D6's "one rebuild per change" hold with no
   counter.
4. In `run`, before the brief is built, §2.5's two blocks verbatim: the `adjudicate <job> <item> —
   <la>: <ta[:60]> ↔ <lb>: <tb[:60]> · both touch <path>` line when `row.brief_kind ==
   'adjudicate' and row.between` (`· no file in common` when it has none, on one line); and, when
   `row.cause`, `ctx.event('triage', item=…, cause=…, row=row.kind, action=row.action)` followed by
   the `triage   <item> — <cause>: <reason>` line. A held cause then falls through to the existing
   `waits` branch and launches nothing; a `rerun` cause launches its kind with a brief built from
   today's index.
5. Tests: `AdjudicateLineTests` — a plan holding one adjudicate row prints exactly one line
   starting `adjudicate `, on one line, naming both round labels and the common file; a plan
   holding a triaged row prints the `triage ` line, appends one `triage` event carrying `cause` and
   `action`, and launches nothing. The existing tick-step assertions stay green: no step is added
   and no step order moves.
