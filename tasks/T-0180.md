stories: S-18050, S-18051, S-18052, S-18053, S-18058

after: none

The spec's §2.2, §2.3 and §2.6. One new scenario class that drives `sample/` from its first tick
to a landed Task, playing each session's writes between ticks, and one fix to the shared fixture's
environment without which no scenario in the module runs outside CI.

**Files**

- `tests/test_sample_product.py` — three changes, all additive except the third:
  - `WholeLoopFromCardToRelease(FailurePathsBase)`, a new class after
    `FinishedWithoutPushIsCorrected` (`:467`), with the nine-tick `setUpClass` of §2.2.
  - `EXPECTED_LADDER`, a module-level list beside `RED_TEST` / `GREEN_COUNT` (`:278-281`).
  - `FailurePathsBase.setUpClass` (`:290`): the inherited `GIT_CONFIG_*` dropped from the base
    environment before `hermetic.build` is called (`:305`).

**Steps**

1. **The environment fix first** (§2.6, S-18058), because nothing else in this Task is runnable
   on an operator's machine without it. In `FailurePathsBase.setUpClass`, build the base mapping
   that is handed to `hermetic.build` as a named local, then delete `GIT_CONFIG_COUNT` and every
   key matching `GIT_CONFIG_KEY_*` / `GIT_CONFIG_VALUE_*` from it before the call. `hermetic.py`'s
   `_git_config` *appends* to whatever count it finds (`asf/hermetic.py:38-49`); dropping the
   inherited pairs is what stops an operator's `core.hooksPath` reaching the child `git` and
   making the wave's hook preflight refuse to launch. Do not touch `asf/hermetic.py`.
2. `EXPECTED_LADDER`, copied from the spec's §2.3 exactly:
   `['card', 'card', 'card', 'spec-draft', 'spec-approved', 'spec-approved', 'plan-approved',
   'building 0/1', 'landed']`. PD5 confirms `landed`, not `on-prod`, is the last entry for a
   product with no `deploy_workflow`.
3. A `stage()` classmethod: read `<cls.backlog>/index.json`, return the `stage` of `F-0001`.
   Call it after every `cls.tick()` and append to `cls.ladder`.
4. `setUpClass` walks §2.2's nine ticks. Each is `cls.script(...)` then `cls.tick()` — the base
   class's `tick()` already waits on the background harvest — and between them the test plays the
   session's writes with `cls.session_commits` / `cls.session_pushes` against
   `cls.sessions()[<job>]['worktree']`:
   - ticks 1–2: `fix-bug-b-0001` on `bugfix/B-0001`; the test commits `GREEN_COUNT` to
     `src/count.py` and a passing `tests/test_empty.py`, and pushes. Reuse `GREEN_COUNT`; the test
     it pairs with must be **green**, unlike `HeldThenCorrectedThenLanded`'s `RED_TEST` — this
     scenario is the success path and a held branch here is a failure, not a stage.
   - tick 3: `spec-f-0001` launches once the S1 lane clears; the test writes `specs/f-0001.md` —
     `sample/`'s own `specs_dir`, not `docs/specs` — commits and pushes.
   - tick 5: `plan-f-0001`; the test writes `plans/f-0001.md` carrying **one `### Task 1:` heading
     with a `writes:` line under it** (PD8). Without that line `writes_lines` returns None and the
     minted card has no footprint; without the heading `mint_plan_tasks` prints
     `has no ### Task N: heading — nothing to mint` and the ladder stalls at `plan-approved`.
   - tick 7: the coder. Read the minted Task id out of `index.json` (`type: task`,
     `parent: F-0001`) and build the job key as `f'coder-{tid}'.lower()` (PD6) — never a literal
     id, never a literal job name.
   - tick 9: no session; the tables are read.
5. `test_the_stage_ladder`: `assertEqual(self.ladder, EXPECTED_LADDER)` as a whole list, so a
   stage that repeats or never appears names its own hinge (S-18053).
