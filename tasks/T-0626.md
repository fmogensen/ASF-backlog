The spec's §5 and §7. When this lands there is, for the first time, a way for a person to write the
file the gate reads — and the two documents that describe the deploy modes say the tick exists. This
Task is last because its waiting table is `awaiting_tick`'s answer (Task 2) and its footer command
is the one the card line already prints (Task 3): a command that shipped before either would have
nothing to show and would teach an operator a string that did not yet appear anywhere else.

Read **PD11** (the `Deployed` column is dropped, and why), **PD14** (the command lives in
`asf/evidence/checked.py`), **PD2** (the command derives fresh where the tick reads the record) and
**PD12** (`add`'s triples) before starting. **D2 binds this Task hardest of the five**: `asf checked`
is the *only* caller of `checked.add` this Feature ships, and it is reached only from a person's
argv.

**Files**

- `asf/evidence/checked.py` — `waiting_rows(root, product)`, `render(root, product)`,
  `resolve_token(product, arg)`, `cmd_checked(args, root)`.
- `asf/cli.py` — the `checked` parser beside `p_prod` (`:310-311`), and its dispatch.
- `tests/test_checked.py` — **new class** `TheCommand`.
- `docs/products.example.yaml` — one clause on `manual` (`:265-272`).
- `docs/guide/operating.md` — `asf checked` beside `asf prod`.

**Steps**

1. `asf/evidence/checked.py`: `waiting_rows(root, product)` → `[(iid, pr, sha, what)]`, every held
   item's awaiting landings, newest item first. It loads the record and derives fresh (PD2):
   `core.load_items(root)` → `core.canonicalize` → `evidence.load(product=product)` →
   `ingest.derive(canonical, ev, product)`, then reads `derived[iid].awaiting` for every Story and
   Feature. `what` is the landing's subject from `ev['merged']`/the id evidence where one is known,
   else `''`. Both imports are **local to the function** — `asf.record.ingest` imports
   `asf.evidence.checked`, so a module-level import either way is a cycle.
2. `resolve_token(product, arg)` → the token to write, or None. All-digits, with or without a
   leading `#`, is a PR: the digits. Otherwise `git rev-parse <arg>^{commit}` in the product repo
   and, on success, the **full** lowercase sha (D7) — the writer always produces full shas, so
   matching is exact in practice and the prefix rule in `matches` exists only for a hand-written
   file. Fewer than 7 characters of hex, or a `rev-parse` that fails, is None.
3. `render(root, product)` → the read-only table. Header `CHECKED — landings on prod waiting on your
   check`, blank line, then `| Item | Landing | What |` and its rule row, one row per waiting
   landing, landing rendered `#<pr>` or `<sha[:9]>` (PD11 — **no `Deployed` column**). With nothing
   waiting, `CHECKED — nothing is waiting on your check` and no table. Then the footer:
   `<n> waiting · <m> ticked · <path(product)>`, where `m` is `len(read(product))`; then, when
   `LEGACY_PATH` exists, one further line naming it and saying it is read, never written (D3); then,
   when something is waiting, `Tick them with: asf checked --item <the first waiting item>`.
4. `cmd_checked(args, root)`: with no positional argument and no `--item` and no `--undo`, print
   `render` and return 0. With `--undo TOKEN`, `resolve_token` it and `remove`; print one line per
   token dropped and one naming any that was not in the product's file — including the case where it

   every landing that item is waiting on and nothing else, each as a `(token, iid, what)` triple.
