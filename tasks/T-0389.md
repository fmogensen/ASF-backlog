§2.7's command and its doctor row. The one rule both obey: **the doctor row never runs a probe.**
`asf doctor` is a read of the configuration, and taking a measurement is the daily step's job — so
the row reads `settings()` and `refusals()`, which Task 1 and Task 2 made pure and total for exactly
this caller.

**Files**

- `asf/product_loop/cli.py` — `register`, `cmd_product_loop`
- `asf/cli.py` — two lines in the registration block
- `asf/doctor.py` — `check_product_loop`, and one `rows.append(...)`
- `tests/test_doctor.py` — the row's four states
- `tests/test_product_loop.py` — `CommandTests`

**Steps**

1. `asf/product_loop/cli.py`, in `plugin_build.register`'s shape (`asf/plugin_build.py:187-192`):
   `register(sub)` adds `product-loop` with `--product`, `--dry-run` and `--json`, and
   `set_defaults(run=lambda args: cmd_product_loop(args))`. PD16 is why the parser lives here rather
   than being hand-built at `asf/cli.py:320`: `scorecard` is one of `plugin_build.VIEWS`
   (`asf/plugin_build.py:34`) and is dispatched from the views tuple at `asf/cli.py:531`, and
   `product-loop` must not join `VIEWS` — `asf plugin build` would generate an operator skill for a
   command that files cards.
2. `cmd_product_loop(args, out=print)`: resolve the product as the neighbours do
   (`args.product` else `env.default_product_name()`), then `measures.settings`. Print one line per
   reading with its guardrail and a breach marker, one block per proposal, and the summary line.
   `--dry-run` takes the readings and prints everything it *would* file, writing neither the
   readings line, the state file nor the queue — one `dry_run` flag threaded into `daily`, not a
   second code path, so what it prints is what the tick would do. `--json` prints the run's readings
   and proposals as JSON, carrying every reading **including the broken ones**, and goes to stdout
   with any announcement on stderr the way a `--json` view already does (`asf/cli.py:531`).
3. `asf/cli.py`: `from asf.product_loop import cli as product_loop_cli` and
   `product_loop_cli.register(sub)` in the registration block at `:345-352` (`plugin_build.register(sub)` is `:346`), beside
   `plugin_build.register(sub)`. Nothing else changes: `args.run` at `:571` is already the dispatch,
   and `VIEWS` is untouched so `asf plugin check` stays green.
4. `asf/doctor.py`: `check_product_loop(cfg, product)` returning `(required, ok, detail)` (PD14).
   Skip — `(False, None, 'no improve.product')` — when the product declares none; **red** —
   `(True, False, <first refusal line>)` — when `refusals(...)` is non-empty, so a probe aimed at
   the live host is the loudest thing on the page; advice — `(False, False, <problems, joined>)` —
   when `settings().problems` is non-empty; green — `(True, True, '<n> measurement(s), probe <account> → <host>')`
   otherwise. `<account>` reads `default` when none is named, and `<host>` is `base_url`'s host, not
   the whole URL. The function opens no subprocess, and `CommandTests` asserts that by patching
   `probe.take` to raise.
5. One `rows.append(('product-loop', *check_product_loop(cfg, product)))` in `run()`, appended after
   the `rule-checks` row (`asf/doctor.py:851`) so it sits with the other per-product checks.
   `format_table` (`:1055`) and `is_red` (`:1069`) need no change — that is what PD14's three-value
   return buys.
6. `tests/test_doctor.py`: the row's four states, each read off `doctor.run(...)`'s rows the way
   `test_doctor_is_red_when_the_approvals_hook_is_missing` (`:344`) reads its own — skip for an
   unconfigured product and `is_red` false; red for a `base_url` whose host is `app_host`'s, with the
   live-host line as the detail and `is_red` true; advice for a dropped measurement, not red; green
   naming the count and the host. And in all four, no probe ran.
