## Description
stories: S-36053
writes: asf/env.py, docs/products.example.yaml, tests/test_deploy.py
after: Task 3

The spec's §3 and the `docs/products.example.yaml` half of §4. A silently-ignored `exclude:` under
prod is this card's own defect wearing a different hat — the operator believes commits are excluded
and they are not — so the three glob keys are shape-checked wherever an environment block lives,
through one shared helper (C9).

**What changes for an operator when this lands.** A product file with `exclude: x` or
`exclude_defaults: maybe` refuses to load, naming the dotted key. A product file with `paths:` under
`deploy_sha.prod` that is not a list now refuses too — that typo was silent before (P8). And the
example config documents the two new keys where an operator looks for them.

**Files**

- `asf/env.py` — `_relevance_problems(k, block)`, new; `_target_problems` delegates its `paths`
  check to it and gains `exclude` / `exclude_defaults` with it; `_deploy_problems` calls it for the
  `deploy_sha.dev` and `deploy_sha.prod` blocks. No other validator moves.
- `docs/products.example.yaml` — the commented keys under `targets.site`, and a line under `prod:`
  saying the filter keys read there too.
- `tests/test_deploy.py` — the existing `Validation` class gains cases. No other class is touched.

**Steps**

1. `_relevance_problems(k, block)` exactly as the spec's §3 snippet has it: for each of `paths` and
   `exclude`, a non-`None` value that is not a list of non-empty strings yields
   `(f'{k}.{key}', f'must be {_LIST} of path globs, not {v!r}')` — the existing message verbatim,
   so `deploy_sha.targets.site.paths` refuses with the same words it refuses with today; and a
   non-`None`, non-`bool` `exclude_defaults` yields
   `(f'{k}.exclude_defaults', f'must be true or false, not {d!r}')`, the wording
   `deploy_sha.auto` already uses (`asf/env.py:583-585`). The helper takes the dotted prefix so one
   function serves three shapes of key.
2. `_target_problems` (`:606-633`): delete the inline `paths` block at `:629-632` and
   `out += _relevance_problems(k, block)` in its place, after the `mode` and `from` checks. The
   message and the key are unchanged, so `test_named_targets_load_and_a_bad_one_refuses`
   (`tests/test_deploy.py:582-590`) keeps passing untouched — check that first, it is the cheapest
   proof the refactor is faithful.
3. `_deploy_problems` (`:577-604`): inside the existing `for env, modes in DEFAULT_MODES.items()`
   loop, after the `mode` check and inside the `isinstance(block, dict)` branch,
   `out += _relevance_problems(f'deploy_sha.{env}', block)`. Nothing else about dev and prod
   validation changes — `from`, `provider` and `auto` keep their own checks.
4. The leniency gap stays, deliberately and documented (C9): `paths()` and `excludes()` coerce a
   bare string, the validator refuses one. That is today's behaviour for `paths` (`paths: x` is
   refused while `paths()` would have coerced it), it is what
   `test_named_targets_load_and_a_bad_one_refuses` already pins, and making the two agree is a
   different card. Say so in `_relevance_problems`' docstring so the next reader does not "fix" it.
5. `docs/products.example.yaml`, under `targets.site` beside the existing
   `paths: [apps/site/**]` line (`:295`), as comments in that block's style:
   ```yaml
   #     # exclude: [apps/site/fixtures/**]   # added to the defaults below, not instead of them
   #     # exclude_defaults: false            # drop the defaults; `exclude:` alone then decides
   ```
   plus a short comment above them naming the seven defaults and the one rule that matters — a
   trunk commit touching only excluded paths is not a relevant commit, and an environment naming
   neither `paths:` nor `exclude:` has no filter at all. Under `prod:` (`:276-281`), one commented
   line saying `paths:` / `exclude:` / `exclude_defaults:` are read for dev and prod too, and that
   with none of them prod counts every trunk commit exactly as it does no
