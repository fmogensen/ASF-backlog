The spec's §4 (C1). After this Task a vm product's lane decides red and green from ASF's own
store: `GitHubHost.checks` is the one override point the three `pr_checks` call sites go through,
`required_checks` skips the code host's branch protection, `trunk_red` keeps its first-parent walk
and reads the store per sha, `red_evidence` yields a tail it already holds, and `ci_green_runs`
finds a vm product's prod-deploy candidates. Not one rule downstream of the triple changes, and
`path_filtered` is never entered.

**Read PD1, PD2 and PD3 before writing a line.** They are the three places the spec's own §4
snippets do not do what §4's prose says: `trunk_red`'s replacement marks green trunk checks red
and raises on a bool, `red_evidence`'s clause leaks every check's log into a correction and is
dead code where the spec puts it, and `ci_green_runs`' clause calls a function that does not
exist. Read **PD9** (the seventh key, `host`) and **PD13** (`head` can be None, and that is
`pending`) too.

**Steps**

1. `checks_at(product, sha, required=())` first — everything else in this Task is judged through
   it. One check dict per row with PD9's seven keys; **plus one `pending` dict per required name
   with no row at the sha at all** (C4), whose detail says so, and whose detail says *"names no
   `ci.jobs` job"* when that is the reason. Then red (`BUCKETS[state] in RED_BUCKETS`), then
   pending, then green — mirroring `pr_checks`' own detail strings exactly:
   `', '.join(red)`, `', '.join(pending)`, `f'{len(checks)} check(s)'`. **Never `unknown`**: a
   falsy sha, an unreadable store, a missing sha entry and a missing required name are four
   spellings of `pending` (PD13). C4 is the single most load-bearing line in this Task — P7 says
   an empty judged list reads **green**, so a store that has not dispatched anything yet would
   merge an ungated branch.

   `concluded` is `{n for n in names if row(n) and row(n)['state'] != RUNNING}`. Nothing else.
