## Description
stories: S-37350, S-37354, S-37361

The spec's §2.2 *"Two doctor rows, both advisory, through a new `check_ci_measure` in
`asf/doctor.py`"*, §2.5's third row, and §Records' `ci census` rows. Nothing else. After this lands,
*"a slow or flaky box surfaces by itself"* is literally true: `asf doctor` names the box, the job
kind, the seconds, the ratio and the reading count, and it does it from two local files with no CI
host call at all.

**Read PD3 before deciding where the census row goes.** `ci_pool.doctor_rows` returns `[]` at
`:885-886` *before* it reads the host when the pool is empty, so the `ci census` row cannot live
there without breaking §3.1's own requirement that a discovered product with no census return exactly
what a no-pool product returns. Task 3 provides `ci_census.census_rows(product)`; this Task wires it
as its own row group beside `check_ci_pool`, the way `check_ci_runners` and `check_cloud` already sit
there (`doctor.py:959-963`). **Read PD8 before reading the stream** — `shadow.record_dir(product)`,
never `ctx.record_root()`, or `asf doctor` grows a `git fetch`.

Two things are load-bearing. **Every row this Task adds except the census one is advisory** (D19,
§3.5): a required row would turn one slow-but-green job into a doctor red the operator cannot act on
faster than the demotion already will, and *the demotion is the action*. **Nothing here raises.** A
missing census, a truncated `ci-baselines.json`, a record root that does not exist, a stream with no
`seconds` — every one of them yields no row, because a diagnostic command that dies on a state file
is worse than one that says nothing.

**Files**

- `asf/doctor.py` — two edits. `check_ci_measure(product, now=None, root=None)`: `root` defaults to
  `shadow.record_dir(product.name)` (PD8), reads
  `read_stream(root, 'ci', days_back(today(), ci_measure.WINDOW_DAYS))`, and returns
  `[(required, ok, detail)]` — all advisory — in three groups. The slow row, one per runner whose
  `Score.ratio` is at or above `DEMOTE_AT`: `ci measure: ci-3 runs gate at 384s, 2.1× the fleet best
  (11 green readings, 14 d) — asf-bulk`, naming the kind that carries the runner's worst ratio. The
  flaky row, one per `Score.flaky` runner: `ci measure: ci-6 green 0.72 over 18 readings — flaky,
  never asf-fast`. The baseline row, one per `ci_measure.regressions` hit against
  `ci_measure.read_baselines(product)`: `ci baseline: gate on ci-4 last ran 512s against its 318s
  baseline (1.6×) — 8 green readings`. `[]` when the stream is empty, when there is no census (the
  tiers a baseline falls back on come from it), or on any exception reading either file. Then the
  wiring in `rows`' body beside `check_ci_pool` (`:959-960`): one loop over
  `ci_census.census_rows(product)` labelled `ci census`, one over `check_ci_measure(product)`
  labelled `ci measure` and `ci baseline` — the row group names §Records' table gives them.
- `tests/test_doctor.py` — one new class, `CiMeasureRows`, over a temporary state dir and a
  temporary record root the test writes itself. A hand-written `ci` stream plus a census gives the
  slow row for the box at 2.1× and none for the box at 1.0×; the flaky row for the box at 0.72 over
  18 readings and none for the box at 0.72 over 4 (`n < MIN_READINGS`, D15); the baseline row for a
  latest green reading at 1.6× its baseline and none at 1.4× (D19). `doctor_rows`' own contract:
  the `ci census` row is **required** and all three measure rows are **advisory** (§3.5's last
  sentence). No census, no `ci-baselines.json`, no record root and a truncated census each give no
  row and raise nothing. Assert that the whole class runs with no network: the `FakeBackend` is never
  constructed and `ci_pool.backend_for` is never called.
