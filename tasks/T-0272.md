## Description
stories: S-29403
writes: asf/harvest/lane.py, asf/workers/lifecycle.py, tests/test_lane.py
after: Task 2

§2.3's `Tq'` and the correction it writes: the one transition that makes the cheap pass worth
paying for. A `fail` row at `high` confidence is a correction of kind `precheck`, its finding the
`file:line` paths of those rows — and no `REVIEW` state is entered, no review round is asked for,
and no expensive session is launched. `precheck` is an ordinary correction kind (D7), so the third
repeat of one finding reaches adjudicate.

**Files**

- `asf/harvest/lane.py` — `Tq'` in `next_state`; the `precheck` branch of `enter_back`
- `asf/workers/lifecycle.py` — the module docstring naming `precheck` as a correction kind that is
  **not** in `MECHANICAL`
- `tests/test_lane.py` — `PrecheckBounceTests`

**Steps**

1. `next_state`: between Task 2's faults check and its fall-through,
   ```python
   if precheck_mod.blocking(pc.get('rows') or ()):
       return BACK, f'kind={precheck_mod.KIND}'
   ```
   — the whole of `Tq'`. Nothing above it moves: the review is still not consulted, so a branch
   bounced here has been read by no expensive session.
2. `enter_back` gains the branch §2.3 gives, beside the `review` one (`:2130`):
   ```python
   elif kind == precheck_mod.KIND:
       pc = f.get('precheck') or {}
       rows = pc.get('rows') or ()
       n = len(precheck_mod.blocking(rows))
       text = (f"{pc.get('path')} holds {n} high-confidence finding(s) at level "
               f"{f.get('level')}: answer each one on {b}, then push")
       finding = precheck_mod.keys(rows)
   ```
   and the `finding` line below (`:2145`) becomes `finding = review_mod.c_items(...) if kind ==
   'review' else finding if kind == precheck_mod.KIND else None`, so `hold_with_correction(…,
   kind='precheck', text, finding=finding)` is reached unchanged.
3. `lifecycle.MECHANICAL` is **not** touched (D7) — `precheck` stays an ordinary kind, so
   `same_finding` counts the repeats and the cap turns the correction into an adjudicate row. The
   module docstring's note on `MECHANICAL` gains one sentence saying why `precheck` is deliberately
   absent: a cheap model's judgement needs the escape a lane-repaired defect does not.
4. `PrecheckBounceTests` per §3.4, on Task 2's fixture. A branch whose precheck at the head holds
   one `fail` row at `high`:
   - `next_state` is `(BACK, 'kind=precheck')`;
   - `enter_back` writes a correction whose `kind` is `precheck` and whose `finding` is that row's
     `file:line` paths;
   - the lane line names the file and the count;
   - the lane record's review `round` is **unchanged**, no `REVIEW` record was ever written, and
     `feeder.rows` raises no `PUSHED → REVIEW` row for the item.
5. The rest of §3.4, each its own assertion: `fail` rows at `medium` and `low` only → `REVIEW`,
   and the rows still in the file afterwards; every row `pass` → `REVIEW`, or `GATE` for a branch
   whose review is waived; a precheck of an older head (its `head:` names a commit whose code
   differs) → treated as absent, `PRECHECK` again; a precheck with a fault in its own table →
   `PRECHECK` with the fault in the reason, never `REVIEW`.
6. The escape: the same `precheck` finding on three successive heads reaches the adjudicate hold;
   `self.assertNotIn(precheck_mod.KIND, lifecycle.MECHANICAL)`; and a `precheck` correction never
   increments a review round — asserted on the record before and after, and by there being no new
   file in the reviews directory of the review pattern's shape.
