The spec's `asf/cli.py` design block and its `resolve_record` table: one formatter, printed by
`resolve_record` through the `announce` seam it already has, so every record command and the nine
views of P4 open on a line that names the record, the product and the input that chose it. Three of
the four convention call sites (PD6, PD7) become `env.resolve_product(args.product)` in the same
diff, and the module docstring stops describing the three-step order (PD8).

**Files**

- `asf/cli.py` — `product_line`, `resolve_record`'s announce, the module docstring's four steps
- `asf/approvals.py` — `cmd_approvals` resolves through `env.resolve_product(args.product)`
- `asf/scheduler.py` — the same at `:805`
- `asf/schema.py` — the same at `:233`
- `tests/test_cli.py` — `RecordCommandUsesTheProductRecordTests` extended
- `tests/test_path_resolution.py` — the `kind` column becomes the expected shape; `tokens`,
  `scorecard` and `release-readiness` gain rows

**Steps**

1. `product_line(product, source, record=None)`: with a record, `record: <path> · product <p>
   (<source>)`; without one, `product <p> (<source>)`; with `product` `None`,
   `record: <path> · product (none) (cwd is a record)`. The card's `record: <path> · product <p>`
   is the literal head of the line (D3), so a `startswith` on the card's string still holds.
2. `resolve_record` keeps every branch and every return value it has. Only what it announces
   changes, and it keeps the `announce` parameter: stdout for a table, `_announce_stderr` for the
   commands whose stdout is a value — `new`, `inbox`, `set`, `reopen`, `stale`
   (`asf/cli.py:465-497`) and any of the nine views under `--json` (`asf/cli.py:541`). No call site's
   `announce=` argument changes.
3. The `--product` branch and the fall-through branch resolve through
   `env.resolve_product(getattr(args, 'product', None))` and announce
   `product_line(res.name, res.source, record)`.
4. The cwd-is-a-record branch announces the product that claims *that record* —
   `env.product_of_dir(cwd)`, source `cwd` — and `product (none) (cwd is a record)` when none claims
   it (PD5). It still returns the cwd, still resolves no product file, and still cannot raise
   `ConfigError`.
5. `cmd_approvals`, `asf/scheduler.py:805` and `asf/schema.py:233` replace
   `args.product or env.default_product_name()` with `env.resolve_product(args.product).name` — the
   order walked in one place instead of by argument position. None of the three prints a header:
   `approvals` and `scheduler` are repo commands (the spec's **Out**) and `schema-migrate` reports
   per product already. `asf/doctor.py:1075` is Task 3's (PD7).
6. `asf/cli.py`'s module docstring (`:3-6`) states the four steps — `--product`, else
   `$ASF_PRODUCT`, else the product whose repo or record holds the working directory, else
   `default_product` in `~/.ASF/config.yaml` — and names the new first line.
7. `tests/test_path_resolution.py`: the `kind` column becomes the expected first-line shape (PD9).
   Every row that is `record` today stays `record` and its assertion becomes the full line for
   `--product sample`: `record: {self.record} · product sample (--product)`. `tokens`, `scorecard`
   and `release-readiness` are added as `record` rows — they dispatch through `resolve_record`
   (`asf/cli.py:539-540`) and were the three views the matrix never covered. `next`, `brief` and
   `doctor` keep their exemption until Task 3 makes them true, and `capacity` is Task 3's row (PD4).
   The `repo` rows are unchanged and assert no first line.
8. `tests/test_path_resolution.py:151`'s equality — the record command run from a product repo cwd —
