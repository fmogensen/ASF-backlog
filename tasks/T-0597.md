## Description

The card's own test, and the one that would have caught it: `StarvedUpgradeTest` drives
`tick.cmd_tick` for the owner over N clock passes against a scripted `SequencedRun` and a fake
clock, with `drift.check` reporting `5cab3a2`-shaped drift. On the code as it stands on the trunk
today this script installs **nothing at all, at any N** — that is the defect this class pins, and
it is the reason the class is a Task of its own rather than a paragraph inside Task 3.

**Read PD6 before writing a line of it**: `run=subprocess.run` is a default argument and cannot be
patched. `cmd_tick`'s `finally` calls `upgrade.install_due(product.name)` and `_run_steps`'s
`run_upgrade` closure calls `upgrade.cmd_upgrade(_ns(...))`, neither passing a `run` — so both
module attributes are wrapped with delegating lambdas that inject the scripted `run`, an `out` sink
and a no-op `sleep`. Everything inside `install_due`, `install` and `_install` then runs for real
against the fake; only the argument binding is stubbed, and that binding is `ExitInstallTest`'s
assertion.

**What changes for the machine when this lands.** Nothing — it is a test. What changes is that the
card's sentence ("overlapping owner ticks → the pending upgrade installs within N passes; it must
never be 'deferred' forever") has a number and a name in the suite instead of a log an operator read
by hand at 06:41.

**Files**

- `tests/test_install.py` — `StarvedUpgradeTest(HomeCase)` added after `DrainWindowTest`. No
  existing class is touched, and no product module is written by this Task at all.

**Steps**

1. The harness, once, as the class's own helper: a `SequencedRun` whose `pgrep` answers come from a
   script (one per call, the last repeating) and whose `ps` answers the one
   `-m asf.tick.step_harvest --product asf` line; a fake clock (a list-backed `now()` the test
   advances by a clock interval per pass); a product whose `repo_dir` is the factory's source and
   whose `approvals.upgrade` is `auto`, built as `PendingUpgradeTest` builds its `other`
   (`tests/test_install.py:826-834` — `env.Product(...)` with `asf.env.load_product` patched); and
   a `passes(n)` driver that calls `tick.cmd_tick` `n` times with `asf.tick.steps.resolve`,
   `check_owned` and `_run_locked` patched, `drift.check` returning the scripted `Drift`, and
   `upgrade.cmd_upgrade`/`upgrade.install_due` wrapped per PD6.
2. *The incident.* Every tick **start** sees another asf pid, for every pass — the floor is never
   empty on the aligned minute, which is what a cron scheduler guarantees (P3). Asserted: the
   install runs, by pass 3 at the latest; it runs from an **exit** and not from a start (the pipx
   call in `run.calls` is preceded by `the floor is empty at this exit`, or for the passes before it
   by the draining line); `upgrade-due.json` and `upgrade-pending.json` are both gone afterwards;
   and no line after the install says `deferred`.
3. *The floor that will not empty by itself.* Every start and every exit sees another pid until the
   park engages, after which the script empties — the parked ticks spawn nothing and the running one
   ends. Asserted: from `DUE_GRACE_S` on, every tick prints the draining line and runs no step
   (`_run_locked` not called); the install happens within `DUE_PARK_MAX_S` of the grace; and the
   record's `passes` at the moment of the install is `<=` the bound the class states as a named
   constant, so the number the card asks for is written down rather than reconstructed.
4. *The cool-down hole.* With `upgrade-expired.json` freshly written so `write_pending` is refused
   (`cooling()` holds), the debt is still recorded, still drains and still installs — the sequence
   that let the incident restart from a worse position, because in that window nothing was parked
   and `step_harvest.run` spawned gates again (P7).
