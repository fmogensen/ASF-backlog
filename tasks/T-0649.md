## Description
stories: S-37951

after: none

The spec's `## The design` §2.2 in full, and nothing else. After this lands, a product that infers
`pull-request` from a `steps.batch` command and has never declared `conventions.landing` gets one
RED doctor row naming both keys and saying what deleting the line would do — so the ambiguity
Task 1 opens is visible *before* an operator acts on it, not after the lane has pushed a gated head
straight onto the trunk.

This Task is a `no`-returning guard with one message, and everything about it is in the guard.
**The finding fires on exactly one pair** (D5): `conventions.landing` unset **and** `steps.batch`
resolving to owner `command`. A product with `landing` declared either way, or with `batch` off or
absent, draws nothing — an ordinary fast-forward product is correctly configured and is never
warned about. **The row is `required=True`** (P9), because the failure it guards is *"the lane
pushed to the trunk instead of opening a PR"*; a `NEEDS OPERATOR` line or a runtime refusal in the
lane were both considered and rejected in D4, and a second source of truth for landing is exactly
what must not appear. And **`lane.landing()` is not in this Task's `writes:`** — the row *reports*
the inference, it does not change it (D3).

Read **PD6 before writing the fifth test** — §3.3 cannot reach the `products/<p>.yaml:<line>`
prefix, and the same decision forbids writing any absolute path into a file this Task touches.
**PD7** for the three product reads and the measured green baseline. **PD9** for why this Task has
no `after:` on Task 1 even though D4 exists because of D1.
