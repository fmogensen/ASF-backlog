## Description
stories: S-37703
writes: asf/ci_pool.py, asf/scheduler.py, asf/harvest/lane.py, tests/test_ci_vm.py
after: Task 2

The spec's §5 *"Its three entry points"* (C13/P11). After this Task a vm product's slots do not
sit idle for the seven-to-twenty-four minutes between ticks: the `ci-vm` clock runs the pass every
minute, the lane's own call does it once more at the end of a lane pass and steps aside when the
clock's pass holds the lock, and an operator has `asf ci vm` to look and `asf ci vm --apply` to
run one by hand.

Read **PD8** before touching `asf/scheduler.py` — the clock is four edit points there, not one,
and the fenced *"retires it when the provider changes"* fails without the fourth.

**Files**

- `asf/ci_pool.py` — `register` (`:1317-1334`): `ci_vm.register(sub)` after
  `ci_queue.register(sub)` (`:1332`), giving `asf ci vm [--apply] [--dry-run]` under the existing
  `ci` group (P17). The parser itself (`register(sub)`) is written in `ci_vm`, which Task 2 owns
  and this Task extends — the `ci_pool` diff is the two lines.
- `asf/scheduler.py` — four points, PD8:
  - `CI_VM_CLOCK = 'ci-vm'`, `CI_VM_COMMAND = 'ci-vm'`, `CI_VM_EVERY_S = 60` beside
    `QUEUE_CLOCK`/`QUEUE_COMMAND`/`QUEUE_EVERY_S` (`:70-72`), with their `#:` lines
  - `tick_argv` (`:201-213`) — one branch beside the queue's, rendering
    `asf ci vm --apply --product <name>`
  - `clocks()` (`:311-314`) — one block beside the queue's, appending the Clock when
    `CI_VM_CLOCK not in declared and hasattr(product, '_get')` and `ci_vm.enabled(product)`
  - `clock_of_plist` (`:809-818`) — one branch beside the queue's, so `install` reads its own
    job back and can retire it
  - the module docstring (`:36-40`) — the sibling paragraph
- `asf/harvest/lane.py` — `lane_pass`'s tail only (`:2286-2290`): the spec's §5 snippet after the
  queue's own call, byte for byte, with the same comment shape. **No other line of this file.**
- `asf/ci_vm.py` is *not* in this Task's footprint: `register(sub)` is added by Task 2 as part of
  the module's own surface, so this Task's diff is the four files above. (If it is not there when
  this Task starts, add it here and say so in the report's `needs writes:`.)
- `tests/test_ci_vm.py` — `class Wiring`, the clock and CLI half: the scheduler cases and the
  registration case. The `post_status` case in the same class is Task 6's.

**Steps**

1. The three constants and the docstring paragraph, mirroring the queue's wording exactly — the
   reason is the same reason and stating a different one would invite a reader to look for a
   difference.
2. `tick_argv`'s branch, then `clock_of_plist`'s. Write them as a pair and test them as a pair:
   `clock_of_plist(render(tick_argv(...)))` round-tripping to the same `Clock` is what makes
   `install` idempotent, and is the assertion that catches a mismatched argv slice.
3. `clocks()`'s block. `ci_vm.enabled(product)` is the whole predicate — not "has `ci.hosts`",
   because a product may declare hosts under another provider and must get no clock; and not
   "the queue is off", which is the queue's predicate and is true for products that want nothing
   to do with this (C13's own rejection of reusing `QUEUE_CLOCK`).
4. `ci_pool.register`'s two lines.
5. `lane_pass`'s tail. It goes **after** the queue's call, so a product that somehow has both
   still runs the queue's pass first, and its `is None` branch prints the one line the spec
   gives: `ci vm: its own pass is running — the lane leaves the CI pass to it`. `dry_run` is
   threaded from `lane.dry_run` — and is a backstop, not the guard: C17's point is that the
   guard is asked inside `run_ssh`, because a threaded flag is what failed open in the incident
   P14 describes.
6. `Wiring`'s scheduler and CLI cases: `asf.<p>.ci-vm` installed every 60s for a vm product,
   retired when the provider changes, nothing installed for a non-vm product, and `asf ci vm` /
   `asf ci vm --apply` registered under the `ci` group beside `queue`.
