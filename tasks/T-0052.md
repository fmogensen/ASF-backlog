**Steps**

1. `shape.area_of(glob, depth)` per the spec's D5: the glob's `footprint._literal_head`, minus its
   last path component unless the glob ends in `/`, cut to the first `depth` segments; a root file
   is `.`. `areas(writes, depth)` returns `{area: [globs]}` in first-seen order.
2. `shape.ready_tasks(canonical, derived)`: `type: task`, `is_open`, machine `state: New`, not
   `blocked`; its Feature (parent chain or `feature:`, as `feeder.rows._task_feature` resolves it)
   decided, open, at `plan-approved` or `building …`; no `reshape:`; and, when it has a
   `split_from:`, also `decided: true`. Sorted by (Feature rank, Task rank, id).
3. `merge_proposals` (D2): the overlap graph over one Feature's ready Tasks, using
   `asf.feeder.footprint.overlaps` — never a second overlap test. One `Proposal` per connected
   component of size ≥ 2; `ids` ordered by `(rank, id)`, so `ids[0]` is the survivor (D7). The `why`
   names the first overlapping pair.
4. `batch_proposals` (D3): per Feature, `units` = ready Tasks with each pending merge counted as one.
   When `units > capacity` and at least two Tasks have `len(writes) <= batch_max_globs`, batch the
   `max(2, units - capacity + 1)` smallest, ordered `(len(writes), rank, id)`.
5. `split_proposals` (D4): a ready Task whose globs fall in two or more areas, where at least one
   area overlaps a holder (an `Active` Task, or a ready Task of *another* Feature — splits compare
   across Features) and at least one overlaps none. The `why` names each held area with its holder,
   then the free areas.
6. `proposal_key(verb, ids, areas=())` → `<verb> <sorted ids>`, or `split <id> <areas>`. Every
   proposal builder drops a proposal whose key is already in any named Task's `reshape_declined`
   (D11).
7. `groom.GROOM_SECTIONS` gains, after `Stories without Tasks after plan-approved`:
   `('Merges proposed', 'merge')`, `('Batches proposed', 'batch')`, `('Splits proposed', 'split')`,
   `('Split parts to confirm', 'split_parts')`. `build_groom_sections` computes all four and takes
   the three new keyword arguments of P5; `cmd_groom` fills them. Render each line as
   `- [ ] <id> <verb> <ids> — <why> → answer: ____`, matching the spec's four worked examples
   byte for byte in shape; `(none)` when empty, like every other section.
8. `PROPOSAL_RE = ^- \[[ xX]\]\s+(?P<id>[A-Z]-\d{4})\s+(?P<verb>merge|batch|split)\s+(?P<rest>.*?)\s+—`.
   `apply_groom_answers` tries it before `ANSWER_LINE_RE`; a match goes to `apply_proposal` and never
