## Description

The spec's §2 and the card's first acceptance clause: a tick that finds the record or the config
below the package's numbers migrates them itself, drained to a bound, and goes on with its steps.
The card's fear — an upgrade that halts every factory until a human runs `schema-migrate` — becomes
true only for a migration the tick cannot run, and even then it is one line, not silence.

**Files**

- `asf/tick/tick.py` — the migration block in `_run_steps`, between the upgrade block
  (`asf/tick/tick.py:394-412`) and the daily catch-up, and the tick's own `schema.require` call
- `tests/test_schema_version.py` — `TheTickMigratesItselfTests`, `AnAdditiveGapNeverRefusesTests`
  appended; Task 1's classes untouched
- `tests/test_tick_steps.py` — the step order is unchanged when nothing is pending

**Steps**

1. In `_run_steps`, immediately after the upgrade block and before the daily catch-up: nothing runs
   when `schema.pending(product)` is empty in both halves, so a tick on a matching install costs one
   read of `index.json` and one of `config.yaml` and prints nothing new — which is every tick today.
2. The block runs under `locks.record('schema migrate')`, the lock the version check already takes,
   and skips (leaving the gap for the next tick) when the lock is not free — a migration is never
   worth blocking a tick's start for.
3. Before applying: one line naming what it found —
   `tick: schema 1 → 2 pending (additive) — migrating`. Then
   `schema.auto_migrate(product, drain_s=schema.tick_drain_s())`, whose returned lines go to the tick
   log as they are: `migrate: schema 1 → 2` per record step (also the record clone's own commit
   subject) and `tick: config schema 1 → 2 — renamed feeder.capacity → capacity.per_product.sessions
   (backup: …)` per config step.
4. Still in flight past the bound (D4, 120 s by default, `upgrade.migrate_drain_s` to override):
   `tick: schema 1 → 2 still pending — 2 session(s) in flight; the next tick retries`, and then the
   steps run — because the gap is additive and this package reads the record fine. A tick that
   blocked for `DRAIN_TIMEOUT_S`'s hour (P9) would be a dead factory by every liveness rule the
   product has.
5. A **non-additive** gap, whether or not the drain succeeded: the operator line —
   `NEEDS OPERATOR: run asf schema-migrate --drain — <detail>` — and the tick returns 3 without
   running a step. This is the only case in which a pending migration stops anything.
6. A refused push leaves the migration commit local, exactly as `migrate_product` does today (P9),
   and the next tick pushes it; the tick says so on the same line rather than treating it as a
   failure.
7. Immediately after the block, `schema.require(product)` — the tick's own call (PD6, and the spec's
   §1 last paragraph). The only mismatch that can reach it is one step 5 already reported, so in
   practice it is the assertion that step 5 did its job; it is written as a call and not as an assert
   so the tick refuses identically to every other `RECORD` writer.
8. `TheTickMigratesItselfTests`: on the tick's own fixture with a record stamped one below the
   package's `SCHEMA_VERSION`, one tick migrates it, the record clone carries the
   `migrate: schema a → b` commit, the tick's output carries that line, the tick exits 0 **and its
   steps ran** — asserted against the step rows, not just the exit code, because "the tick never
   stops on a migration it can run itself" is a claim about the steps. A second tick migrates
   nothing and says nothing.
9. `AnAdditiveGapNeverRefusesTests`: with a session in flight and a drain bound of 0, the tick logs
   the still-pending line and runs its steps anyway, exit 0; with a fabricated non-additive entry the
   same tick prints the `NEEDS OPERATOR` line, runs no step and exits 3; a pending config step is
   migrated and stamped by the tick with no operator ac
