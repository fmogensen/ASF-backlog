The spec's §1 whole: `CONFIG_VERSION` beside `SCHEMA_VERSION`, a `Migration` record carrying
`additive`, `pending`/`blocking`/`auto_migrate`, the `_set_config_version` that can insert, the
snapshot and its restore, `changelog_notes` — and the one guard at `asf/cli.py`'s dispatch that turns
`require` from a function with no caller (P1) into the refusal the guide has been promising. Nothing
in this Task changes what any command *prints* on a matching install: every version in the field is
`1`/absent, so `pending` is the config stamp alone and every step of it is additive.

**Files**

- `asf/schema.py` — `CONFIG_VERSION`, `TICK_DRAIN_S`, `tick_drain_s`, `Migration`, `MIGRATIONS`,
  `CONFIG_MIGRATIONS`, `product_version`, `config_files`, `pending`, `blocking`, `require`,
  `auto_migrate`, `migrate_config`, `_set_config_version` (insert), `snapshot`, `restore`,
  `snapshots`, `changelog_notes`; `check`, `migrate_dir` and `migrate_product` keep their signatures
- `asf/cli.py` — one guard in `_main` after `parse_args` (PD5, PD6)
- `tests/test_schema_version.py` — `RequireRefusesOnlyANonAdditiveGapTests`, `ConfigMigrationTests`,
  `EveryMigrationIsAdditiveOrBumpsTheMinorTests`; `RecordCarriesSchemaVersionTests` and
  `IngestKeepsTheStamp` untouched
- `tests/test_surface.py` — `EveryRecordWriterChecksTheSchemaTests`; the `COMMANDS` count literal is
  **not** touched (P21: this Feature adds no command)

**Steps**

1. `CONFIG_VERSION = 1` beside `SCHEMA_VERSION = 1`, with D1's comment: one key name
   (`schema_version`), two numbers, each compared against its own file — a config-field rename must
   not cost the 500-card commit a record bump costs (P8). `TICK_DRAIN_S = 120` (D4) and
   `tick_drain_s(cfg=None)` reading `config.yaml`'s `upgrade.migrate_drain_s`, non-negative number or
   the default (PD14), the shape `upgrade._config_number` already uses.
2. `class Migration(NamedTuple)`: `apply` (the callable, as today), `additive: bool` — "a package at
   `n` still reads and writes a file at `n-1`" — `note: str` (one line, for the CHANGELOG and the
   tick log), and, for the config table, `renames: dict` and `removes: tuple`, both defaulting empty,
   from the spec's **In** bullet "a `CONFIG_MIGRATIONS` entry declares `renames` and `removes`". One
   record type, two tables.
3. `MIGRATIONS = {1: Migration(_migrate_to_1, additive=True, note='the first stamped schema')}` —
   the existing `_migrate_to_1` and its docstring unchanged — and
   `CONFIG_MIGRATIONS = {1: Migration(_config_to_1, additive=True, note='the first stamped config',
   renames={'feeder.capacity': 'capacity.per_product.sessions', 'worker_pool.reserve_for_s1':
   'capacity.reserve_for_s1'}, removes=())}`. `_config_to_1(paths)` stamps and changes nothing else
   (PD8), with a docstring saying why the renames are declared and not applied.
4. Reading the numbers. `config_version()` keeps its meaning exactly — `None` when the key is absent,
   "no opinion" (PD7) — and `product_version(name)` reads `products/<name>.yaml`'s `schema_version`
   the same way. `config_files()` → `[config_path()] + sorted(products/*.yaml)`, the set a config
   migration stamps and a snapshot copies.
5. `pending(product)` → `{'record': [(a, b, Migration)], 'config': [(a, b, Migration)]}`: the steps
   standing between each file's stamp and the package's number, the record's taken as the lowest

   `config_files()` (absent counts as 0). A stamp *greater* than the package's is never in `pending`
   — that is forward-only, and it is `migrate_dir`'s existing refusal, unchanged.
