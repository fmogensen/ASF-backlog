## Description
stories: S-32353, S-32355

after: Task 1

The spec's §4: `schema_version` becomes a known product-file key, `validate_product_text` splits into
errors and warnings behind one internal `_problems`, the one rule that moves a problem from one to
the other is "unknown key **and** the file is stamped newer than this package", and `deprecated_reads`
reads the rename table Task 1 declared. D9 is why the public 3-tuple does not move: ~30 call sites
across the suite unpack `(line, key, why)`.

**Files**

- `asf/env.py` — `PRODUCT_FIELDS` gains `'schema_version': None`; `_problems(text) -> (errors,
  warnings)`; `validate_product_text`, `product_warnings`; `load_config`'s two validated sections
  given the same treatment; `deprecated_reads`
- `docs/config.example.yaml` — the `schema_version` key and `upgrade.migrate_drain_s`, as comments
  (D12, PD14)
- `docs/products.example.yaml` — `schema_version` as a comment (D12)
- `tests/test_env.py` — `ConfigSchemaVersionTests`, `TolerantReaderTests`; every existing class
  unchanged in expectation

**Steps**

1. `PRODUCT_FIELDS` gains `'schema_version': None` (D12) — a known key with no shape constraint, so a
   stamped file loads on this release and every later one, and `tests/test_env.py`'s
   `test_the_documented_example_validates` keeps passing.
2. `_problems(text) -> (errors, warnings)` takes the whole current body of `validate_product_text`.
   It builds the same sorted list of `(line, key, why)` it builds today, then partitions it: a
   problem goes to `warnings` when, and only when, its `why` is the unknown-key wording (top level or
   a nested table) **and** the file's own `schema_version` is greater than `schema.CONFIG_VERSION`.
   Every shape problem, every enum problem and every finding from `_deploy_problems`,
   `cloud.config_problems`, `ci_pool.pool_problems`, `ci_queue.config_problems`,
   `credentials.product_problems` and `conventions.validate_mapping` stays in `errors` at any
   version, and an unknown key in a file at or below the package's version stays in `errors`: a typo
   is still a typo.
3. `validate_product_text(text)` returns `_problems(text)[0]` — the same 3-tuples in the same order
   as today (D9), so every call site listed by the spec is untouched. `product_warnings(text)`
   returns `_problems(text)[1]`. `load_product` keeps raising `ConfigError` on `errors` and ignores
   `warnings`; the doctor is where a warning is told (Task 3).
4. `load_config` gets the same treatment for the only two sections it validates (P5):
   `validate_worker_pool` and `cloud.config_problems` findings that are unknown-key findings become
   warnings when `config.yaml`'s own `schema_version` is greater than `CONFIG_VERSION`, and raise as
   today otherwise. `config_warnings()` returns them. The rest of `config.yaml` is already tolerant
   (P5) and stays so — making it strict first would be D-out's "work in a circle".
5. `deprecated_reads(data)` → `[(old, new)]` for every old name still present in `data`, read from
   `schema.CONFIG_MIGRATIONS`'s `renames` (PD8) rather than from two hand-written lines. The old name
   keeps being honoured wherever it is read today, and the new name wins when both are set — the
   behaviour `capacity.resolve` already has for these two pairs, now stated in one place.
6. `docs/config.example.yaml`: a commented `# schema_version: 1` line at the top of the file, with
   one sentence saying it is written by `asf schema-migrate` and `asf upgrade` and that absent means
   "no opinion" (D12); and `# migrate_drain_s: 120` inside the already-commented `upgrade:` block at
   `docs/config.example.yaml:181-187`, with the sentence D4 gives. Comments only: a required key
   would brick rollback to all 65 tags (D12), and neither example file gains a live key.
7. `docs/products.example.yaml`: the same commented line and the same sentence.
