## Description
stories: S-33602
writes: asf/briefs/templates/reshape.md, tests/test_briefs.py
after: Task 1

The spec's third **In** bullet (D4). The split is the wrong deliverable for a Task that is not too
wide but unreadable, so the template's binding line stops asserting a split and the deliverable
splits in two, keyed on the row's reason.

**This Task is the operator's console edit, not a coder's** (PD11): `asf/briefs/templates/reshape.md`
is in the amendable set's `role_agents` kind, so its feeder row is
`CONSOLE → AMEND  WAITS ON console: amendable asf/briefs/templates/reshape.md` and no session is
launched for it. It is a Task of its own so that nothing else is dragged to the console with it.

**Files**

- `asf/briefs/templates/reshape.md` — the binding line (`:3-4`) and the DELIVERABLE block (`:6-17`)
- `tests/test_briefs.py` — the reshape template's two modes

**Steps**

1. The binding line stops asserting a split. `Binding: the groom's approved split — {reason} —` becomes
   a line that names the reason without claiming what kind of change it asks for: the groom's
   judgement *or* the feeder's footprint gate, of this Task of `{plan_path}`, under the approved spec
   `{spec_path}`. `Add no scope. Change only how {item_id} is cut.` stays, word for word — it is true
   of both modes and is the sentence the whole template exists for.
2. The DELIVERABLE block becomes two, chosen by the reason's opening words, each stating its own key
   so a reader can tell which one is theirs without guessing:
   - **when `{reason}` begins `no writes:`** — add `stories:`, `writes:` and `after:` to `{item_id}`'s
     `### Task N:` section of `{plan_path}`, directly under the heading and before anything else, from
     what that section's own Files and Steps already say; set `{item_id}`'s card `writes:` to the same
     set; **mint no ids, split nothing, add no scope, and leave {item_id}'s own id in place**; and
     say so in the final message. A section whose Files block names nothing the Steps confirm is a
     `NEEDS OPERATOR:` line, not a guess — the spec's Out forbids inventing a footprint
     ("Widening a no-writes Task's footprint automatically").
   - **otherwise** — today's split, byte for byte: one Task per area with ids from
     `BACKLOG_ID_RANGE`, each `split_from: {item_id}` with its `writes:` and `stories:`, the plan
     section replaced by one per part, and `{item_id}` marked `removed: split into <ids>`.
3. The `footprint: needs <paths>` paragraph (`:13-15`) stays inside the split mode, where it belongs:
   it is about a `writes:` that exists and is too narrow, which is not this Task's case.
4. The `NEEDS OPERATOR: {item_id} does not split along <area>` escape (`:16-17`) stays in the split
   mode, and the second mode gets the escape named in step 2 instead. The final-message line names
   what each mode produced.
5. `{writes}` is **not** interpolated anywhere in the second mode (PD10): it renders as the literal
   `(none declared)` for every Task that mode is for. `{item_id}`, `{plan_path}`, `{spec_path}`,
   `{branch}`, `{main}` and `{reason}` are all in `briefs.build.context` and all still used, so no
   key is missing and none is newly required.
6. `tests/test_briefs.py`: a reshape brief built from a row whose reason is Task 1's `NO_WRITES_RECUT`
   renders the second mode — the three machine-line names are in it, `split_from` and
   `BACKLOG_ID_RANGE` are **not**, and `removed: split into` is not; a reshape brief built from a
   groom `reshape:` reason renders today's split — `split_from`, `BACKLOG_ID_RANGE` and
   `removed: split into` are all in it, and the second mode's sentence is not. Cases: both modes
   render with no unsubstituted `{…}` left (the whole-template format check the module already does
   for the other kinds); `(none declared)` appears nowhere in the second mode's text; and the reason
   is quoted in both, so the operator reading the brief sees which row sent it.
7. The amendable set is **not** changed: `asf/
