## Description
stories: S-31353
writes: tools/spike/f-0065/session.sh
after: Task 1, Task 2

§2.2's third file, and PD5, PD6 and PD7 — the three things the spec leaves unsaid about what a
launched session is. This is the Task that turns the instrument into a measurement: everything
before it runs on the host, everything after it runs inside a session.

**Files**

- `tools/spike/f-0065/session.sh` — **new**. `session.sh <role> <variant>` launches **one real
  session** and prints one thing on stdout: the path of its stream-json log,
  `<state>/spike/f-0065/<role>.<variant>.jsonl`. A re-run of a leg overwrites its own file and no
  other (§4).
  - **The environment is the real one** (PD5). It constructs a `runtime.Job` and calls
    `asf.workers.runtime.build_env` (`asf/workers/runtime.py:363-392`) and
    `asf.workers.runtime.build_command` (`:98-110`) — imported, never reimplemented — so the
    session gets `hermetic.build(..., mode='worker')`'s allow-list (`asf/hermetic.py:63-66`,
    `:144`), its own HOME (`session_home`, `:121`) with `<home>/.local/bin/asf` on it (`:250`),
    `ASF_HOME` pointing at the operator's `~/.ASF`, `CLAUDE_CONFIG_DIR` at the account's config
    dir, `core.hooksPath` under the state dir, and git's credential helper for the code host
    (`:344-351`). Three declared departures and no others: cwd is the fixture worktree,
    `--settings` is the rendered leg file, and the brief is the spike's.
  - **The brief** is `roles.block(roles.load(<role>), cap)` (`asf/roles/roles.py:168`, `:282`) plus
    a tail telling the session to run `probe.sh <role>` and report its output. The prober is
    rendered by hand precisely because it binds no kind (`roles.UNBOUND`,
    `asf/roles/roles.py:58-59`) and so no launch path would ever produce it (D10, P13).
  - **The settings file is rendered, not passed through** (PD4): `${REPO}`, `${STATE}`, `${HOME}`
    and `${TMPDIR}` in `settings/<role>.<variant>.json` are expanded into
    `<state>/spike/f-0065/settings/<role>.<variant>.json`, untracked, and that path is what
    `--settings` gets. `--permission-mode` and `--add-dir` come from the variant.
  - **Two refusals before any money is spent.** (a) The account's own user settings file
    (`hooks.account_settings_path`, and `asf/hooks.py:317-319` is what put the `approvals` entry
    there) is read and the leg is refused if it carries any key the surface reading calls a sandbox
    key — otherwise `off` and `bare` are not distinguishable and every pair reads green on a fence
    that was never off (PD6). (b) The rendered file is `json.load`ed and the leg is refused if any
    value still matches `${…}` or any top-level key is outside the surface's list (PD7), because
    under `-p` an invalid settings file is silently ignored and the session would report a clean
    fence it never had (P11).
  - **The credential refusal**, verbatim from §4: when none of
    `asf.workers.runtime.RUNTIME_AUTH_VARS` (`:276`) is set, it prints
    `NEEDS OPERATOR: no runtime credential in this environment — set the account's auth_env (<var>)
    and re-run: bash tools/spike/f-0065/session.sh <role> <variant>` and exits without launching —
    rather than launching an unauthenticated session and reporting its failure as a finding.

**Steps**

1. Build the `Job` and the environment through the package first, and prove it before launching
   anything: dump the environment the job would get and read it against `WORKER_ALLOW` plus the
   passthrough names. An environment with the operator's variables in it is the failure PD5 exists
   to prevent, and it is cheaper to catch here than in a table.
2. Add the renderer and the two refusals (PD6, PD7). Test both by hand with a deliberately broken
   leg file — an unrendered placeholder, an unknown key — and confirm neither reaches a launch.
3. Add the credential refusal and confirm its exact line with the variable unset.
4. Launch `prober off` — the cheapest leg there is, the fewest probes, no fence, and the one
