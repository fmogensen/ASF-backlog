§2.5 and §4. The wave asks the rule before it builds a brief; a row that can be continued is sent
its findings and is not launched; a row that cannot is briefed and launched in the **same tick**,
with one line naming why. This is the Feature: the card's first acceptance lands here, and the
fallback branch it shares with Task 5 lands here too.

**Files**

- `asf/workers/continuation.py` — `continue_run(product, row, run, session_id, round_n,
  review_path)` → the ledger record, or `None` when the runtime declined.
- `asf/tick/step_wave.py:171` — `run`'s row loop gains §2.5's block between the held check and
  `_build`, and the `cold` line after `_build`.
- `tests/test_continuation.py` — `WaveTests` (§3.4).

**Steps**

1. `continuation.continue_run` writes the message to
   `<state>/briefs/<writer job>.continue-r<n>.md` — one file per round, kept for the operator
   exactly as a brief is (§4) — through `spawn.write_brief`'s own directory
   (`spawn.briefs_dir`), so the two live side by side.
2. The worktree is `spawn.make_worktree(product, run['job'], branch)` (PD8): the writer's own,
   reused as it stands and rebased onto the fetched trunk, with `may_launch` and the push-gate
   check carried along. A `SpawnError` from it is not a crash — it is the fallback's trigger,
   returned as `None` with its text as the reason.
3. The account is the writer's, by name, off `run['account']` (PD6); the id range is the
   writer's, off `run['id_range']`, and no range is reserved or released (PD10).
4. The `Job` is built as `spawn.spawn` builds one — same `permission_mode`, `settings_file`,
   `hooks_dir`, `add_dirs` — with two differences: `resume=session_id`, and
   `env['ASF_SESSION']` is the **writer's** `session`, not a new one, because the run is that
   session continuing.
5. `runtime.continue_run(job)` is called; `None` returns `None` and the caller falls back in the
   same tick (PD9).
6. The ledger line is appended through `pool_mod.append_session` with the fields PD7 lists: a
   launch line by P2 — its own `pid`, `pgid`, `started`, `brief` — carrying the writer's
   `session`, the row's `kind`, `resumed: <runtime session id>` and `continued: 1`. That
   `session` field is the whole of acceptance #3 (P10), and the `started` on it is what answers
   the pending correction (P4).
7. `step_wave.run` per §2.5's fence: `continuation.target(product, row, ctx.record_root())`
   between the held check and `_build`; on a session id, `continue_run`, then the `continued
   <job> <item> → session <id> (round n)` line, a `ctx.event('continue', …)` and `continue` —
   the row is never appended to `worker_rows`, so `_wave` never sees it and no slot beyond its
   own is taken. A `None` from `continue_run` sets `why = 'runtime declined to continue'` and
   falls through.
8. After `_build`, a non-empty `why` prints one `cold <job> <item> — <reason>` line. The launch
   itself is the code that was already there, untouched: the row is briefed and handed to
   `_wave` exactly as today, so the operator reads the rate of fallback off the tick's own
   output rather than off a metric that arrives a day later.
9. `WaveTests` per §3.4, end to end over the git fixture and `FakeRuntime`. The doc lane: a
