**S-122758 — the action, the applier and the port.**

```bash
python3 -m unittest tests.kernel.test_main_pending.DispatchPortTests tests.kernel.test_ports
```

- [ ] the action carries the sha the kernel judged and the one line of why
- [ ] the action describes itself in one line naming the short sha and the reason
- [ ] applying the plan calls the port exactly once
- [ ] applying the plan writes nothing to the record and moves no item's state
- [ ] the apply log line carries the port's own note, naming the workflow and the trunk branch
- [ ] a port that refuses the dispatch leaves one failed entry in the result and the rest of the plan applied
- [ ] the port runs the trunk's workflow on the trunk ref through the repo slug
- [ ] the port takes the workflow from the product's trunk workflow convention
- [ ] the port refuses with a port error when the product declares no trunk workflow
- [ ] the port refuses under the dry-run mutation guard like every other kernel write
- [ ] the staleness guard never skips a dispatch, since it targets no pull request

**S-122759 — the knob, its record, its line, and the trigger the dispatch needs.**

```bash
python3 -m unittest tests.kernel.test_main_pending.KnobTests tests.test_workflow
```

- [ ] the kernel settings hold a mainline section whose max pending defaults to five
- [ ] a product file setting the knob is read back as given
- [ ] a knob of the wrong type is a named error against its dotted key and the load is refused
- [ ] the documented block in the settings module names the mainline section and its default
- [ ] the example product file documents the mainline section and its default
- [ ] the product's knob reaches the config the judge reads
- [ ] a knob of zero reaches the config as off
- [ ] the tick line for a pending trunk reads MAIN PENDING with the sha and the action
- [ ] the tick line for a red trunk still reads MAIN RED with the sha and the action
- [ ] a trunk record carrying no kind at all still prints as MAIN RED
- [ ] the trunk's workflow declares the workflow dispatch trigger
- [ ] the trunk's workflow still fires on a push to the trunk only, and on pull requests
- [ ] the trunk's workflow still groups its runs by event, so a dispatched run is its own group
