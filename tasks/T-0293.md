§2.5, §2.6 and §4: the stream, the daily part that appends it, and the `## Evals` section that
renders it. One Task, because §3.7's fence names `EvalsStreamTests`, `EvalsDailyTests` and
`DailyEvalsTests` together and the first two live in one module.

**Files**

- `asf/metrics/metrics.py` — `STREAMS` gains `'evals'` (`:41`); `SCHEMAS` gains §4's entry;
  `validate`'s dispatch and `natural_key` gain theirs (PD6, PD7); `render_daily` gains the section.
- `asf/init.py` — `STREAM_FOLDERS` gains `'metrics/evals'` (`:28`).
- `asf/tick/step_daily.py` — `parts` gains `('evals', …)` **first** (`:26`).
- `asf/evals/run.py` — `daily(product, root)`: score, append one event per lever, print the one
  line the step reports.
- `tests/test_metrics.py` — `EvalsStreamTests`, `EvalsDailyTests`.
- `tests/test_tick_steps.py` — `DailyEvalsTests`, and `DailyPartsTests`' exact list.
- `tests/test_scorecard.py` — `WiringTests`' exact list.

**Steps**

1. `SCHEMAS['evals']` exactly as §4's block writes it, fifteen keys, no key `MATCH` (§2.5).
2. `validate`: the final `else` becomes `elif stream == 'ticks':`, and an `elif stream == 'evals':`
   branch joins it (PD6) — `passed` and `total` non-negative with `passed <= total`; `lever`
   non-empty; `exempt` and `unrecorded` booleans, `unrecorded` only true when `exempt` is; every
   entry of `failures` a dict carrying `task`, `why`, `expected`, `got`; each raising `SchemaError`
   naming the key.
3. `natural_key`: `('evals')` → `(ev['ts'], ev['lever'])` (PD7). The fallthrough that returns
   `(ev['tick'],)` stops being the default and becomes the `ticks` branch.
4. `asf/init.py`: `'metrics/evals'` in `STREAM_FOLDERS` (PD12).
5. `asf/evals/run.py`: `daily(product, root)` — `score` over the core set and the product's record
   root, one `evals` event per lever appended through `metrics.append_event`, and a printed last
   line of the shape §2.6 names: `evals ok — 18/19 passed, 1 exempt`. It returns 0 unless the
   append itself failed: a *failing reading* is a number, not a broken step, and the daily step's
   `FAILED` is reserved for a part that could not run (P8). No core set on disk (PD10) prints
   `no eval set on disk` and returns 0.
6. `asf/tick/step_daily.py`: `('evals', lambda: evals_run.daily(product, root))` **first** in
   `parts`, before `stale` (§1.4: a hand-run `asf metrics rollup <today>` in the same tick then
   sees the reading), imported locally as the other three are. Update the module docstring's list.
7. `render_daily` (`:715`): a `## Evals` section after the `## Waste` table and before
   `## Cost per Feature`, rendered from `read_stream(root, 'evals', [day])` — the last event per
   lever by `ts` (PD7) — exactly §2.6's markdown: the summary line with the set hash, the passed
   total, the percentage, the exempt and unrecorded counts, then the table with `—` for an exempt
   lever's rate and its note. The three rules the renderer keeps, each its own assertion: no
   reading for the day renders the one line `no eval reading for <day>` and the section is **never**
   omitted; a rate is never printed for an exempt lever; and when the day's events carry more than
   one `set_hash`, or the previous day's differs, the first line is
   `instrument changed <a> → <b> — readings before and after are not comparable` and no rate is
   compared across it. The previous day comes from `read_stream(root, 'evals', [<day-1>])`, one
   more day than the section's own read and nothing wider.
8. `tests/test_metrics.py`: `EvalsStreamTests` — the schema of §4 validates, an unknown key and a
   missing required one raise `SchemaError`, `metrics/evals/<day>.jsonl` is appended with sorted
   keys, no `items` key is matched and no matcher is called (PD17), and one event per lever per run
   is what `append_event`
