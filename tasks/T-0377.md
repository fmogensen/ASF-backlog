**Steps**

1. `Source.live_runs(self)` beside `Source.live_jobs` (`:714`): returns None, with §2.1's docstring
   — the product's own runs not completed, `[{id, status, headBranch, headSha, createdAt,
   workflow}]`, or None when unreadable. A provider whose backend cannot list runs raises nothing
   (§1.2, D4). Extend `Source.live_jobs`' docstring with `steps` — `[{name, status, started_at,
   completed_at}]` in the provider's own order, the key left out by a provider that publishes none.
2. `GitHubSource._repo_jobs` (`:878`): the `jq` field list gains
   `steps: [.steps[]? | {name, status, started_at, completed_at}]`. The `?` is deliberate — a job
   the provider returns with no `steps` array yields no key rather than an error, which is the
   `unknown` case the judge is built for.
3. `GitHubSource._runs_by_status` (`:828`): memoise on `self._by_status`, keyed `(repo, status)`,
   initialised lazily as `getattr(self, '_by_status', {})` the way `busy_runners` already
   initialises `self._live` (`:858`). One listing per `(repo, status)` per pass; a None result is
   memoised too, so an unreadable listing is not asked twice.
4. `GitHubSource.live_runs(self)`: the product's own repo, both statuses
   (`QUEUED_STATUSES | {'in_progress'}` — spelled from the module's own constant, `:1907`), from
   the memo. None when `self.slug` is falsy or any listing is None. Each run is mapped into the
   queue's own vocabulary: `id`, `status`, `headBranch` from `head_branch`, `headSha` from
   `head_sha`, `createdAt` from `created_at`, and `workflow` from `os.path.basename(path)` (PD4).
   Dedupe by id — a run can move between the two listings under the read.
5. The module docstring gains its §2.1 sentence: the stall watch and the phantom watch ask the same
   listing question and pay for one answer.
6. `tests/test_ci_step_silence.py` (new), `SeamTests`, over `tests/test_ci_phantom.py`'s fake host
   imported rather than copied:
   - `test_live_runs_returns_the_products_non_completed_runs_in_the_queues_vocabulary` — the four
     runs of the fixture, each with `id`/`status`/`headBranch`/`headSha`/`createdAt`/`workflow`.
   - `test_live_runs_carries_the_runs_workflow_basename` (PD4).
   - `test_the_two_listings_are_made_once_per_pass_for_both_watches` — §3.5's assertion, over the
     argv log: exactly two `/actions/runs?status=` calls for the product's repo in a pass that asks
     both `busy_runners()` and `live_runs()`, in either order.
   - `test_an_unreadable_listing_makes_live_runs_none_and_is_not_asked_twice`.
   - `test_the_base_source_returns_none_for_both_readers` — `Source().live_runs()` and
     `Source().live_jobs(1)` are None, and neither raises.
   - `test_live_jobs_carries_the_steps_the_provider_published` and
     `test_a_job_with_no_steps_array_carries_no_steps_key`.
7. `tests/test_ci_phantom.py`: the `job()` helper (`:40`) takes `steps=None` and writes the key only
   when given; the fixture's four job lists gain a plausible `steps` array each (a completed step
   and a running one). No existing assertion changes — the phantom watch reads `status`,
   `runner_name` and `labels` and nothing else.
