## Description
stories: S-7904
writes: asf/feeder/rows.py, tests/test_feeder.py

Three typed fields a groom answer writes (`reshape:`, `split_from:`, `decided:`) become rows. The
feeder still writes nothing and reads nothing but the index.

**Files**

- `asf/feeder/rows.py` — `RESHAPE` constant, `task_rows` (`asf/feeder/rows.py:303-321`), `KIND_ORDER`
  and the sort key (`asf/feeder/rows.py:325,353`), the module docstring's row table
  (`asf/feeder/rows.py:9-25`).
- `tests/test_feeder.py` — new `ReshapeRowsTest`, built on the file's existing index-dict fixtures.

**Steps**

1. `RESHAPE = 'RESHAPE → PLAN'`, and one line in the docstring's row table:
   `RESHAPE → PLAN         a Task the groom's split answer marked: hold it, reshape it`.
2. In `task_rows`, for each New, not-busy, not-blocked Task, before the footprint gate:
   - `reshape:` set → a `PLAN → CODE` row with `action='WAITS ON reshape'`, `waits_on='reshape'`,
     which launches nothing and takes no slot, followed by
     `Row(tier=2, kind=RESHAPE, item_id=t['id'], feature_id=feature['id'], action=LAUNCH,
     brief_kind='reshape', branch=branch_for(product, 'plan', t['id']),
     reason='groom: split <areas>')`. The Task's writes do not join `running`: it launches no coder.
   - `split_from:` set without `decided: true` → `WAITS ON confirm`, launches nothing, and again no
     `running` entry.
   - otherwise, exactly as today.
   Both holds keep the Feature's other Tasks flowing — the hold is on the Task, never the Feature
   (D10).
3. `KIND_ORDER[RESHAPE] = 3` and the sort key's fallback `KIND_ORDER.get(r.kind, 4)`, per P7.
4. `ReshapeRowsTest`. For the capacity-1 case, read presence off `rows.candidates()` and the slot
   arithmetic off `rows.plan_rows()` (P8).
