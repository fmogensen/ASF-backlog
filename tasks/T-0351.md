**Steps**

1. `watch(product, job, every=SAMPLE_EVERY_S, alive=None, now=None, max_h=WATCH_MAX_H)` — §2.4's
   contract. Sample, then end on: a sample whose `result` is True, a pid that is gone
   (`os.kill(pid, 0)` by default, `alive` injected for the test), a registry line that is no longer
   live, or `max_h` since it started. It judges nothing and stops nothing. Every iteration is
   wrapped: an `OSError` in one sample is skipped, not fatal. Returns the number of samples taken.
   Reading the registry line is the one place the leaf needs the ledger; it reads the JSONL under
   `env.state_dir(product)` itself rather than importing `asf.workers.pool`, which the licence
   forbids — the fold it needs is "the last line for this job", not the whole `lifecycle` fold.
2. `start(product, record, cfg=None, spawn_fn=None, cloud=False)` (PD6). None, with no raise, when
   `cloud`, when `(cfg or {}).get('worker_pool', {}).get('progress_sampler')` is `False`, or when
   the spawn raised. Otherwise `(spawn_fn or detach_spawn)([sys.executable, '-m', 'asf.cli',
   'workers', 'progress', '--product', product.name, '--job', record['job'], '--watch'])` and its
   pid. `detach_spawn` is imported inside the function (`from asf.detach import spawn`) — `detach`
   is stdlib-only and importing it at module level would still read as a sibling in
   `LeafImportTests`, so the test's allow list gains `asf.detach` and the module docstring says why.
   `asf/detach.py` is the double-fork that leaves no defunct child and `[sys.executable, '-m',
   'asf.cli', …]` is the canonical way to run an asf command from python (P14,
   `asf/scheduler.py:205-208`).
3. `spawn.spawn`: after `pool_mod.append_session(product, record)` and before `return record`,
   §2.4's three lines with `cloud=cloud` added — `pid = progress.start(product, record, cfg=cfg,
   cloud=cloud)`, and `pool_mod.update_session(product, row.job, progress_pid=pid)` when it is
   truthy. `progress_pid` is a fact about the run, never judged on, and the sampler is never
   signalled by anything (D16). A launch is never refused because the sampler did not start: the
   `start` call is inside its own `try` over `OSError`.
4. `cmd_progress(args)` and the subparser: `add_product_arg`, `--job`, `--watch`, `func`. Three
   forms (§2.8): `--job J --watch` runs `progress.watch` and returns 0; `--job J` prints that job's
   newest sample and its verdict; `--product P` alone renders §2.8's table over the live runs —
   job, class, for, commit, files, the `WINDOW_MIN` classes, last call — and exits 1 when any live
   run is `stuck`, 0 otherwise, the convention `cmd_stall` already uses (`:90-93`). The `workers`
   parser's own help string gains `progress`.
5. `TestCli`: renamed to `test_register_adds_the_seven_verbs`, with `'progress --job j'` in its
   tuple (PD12). `tests/test_path_resolution.py`: one row, `(['workers', 'progress'], 'repo')`,
   beside `stall`'s (`:51`) — the verb runs against the repo, as every other `workers` verb does
   (P17).
