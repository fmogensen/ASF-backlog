## Description
stories: S-33103, S-33104
writes: asf/probe/host.py, asf/tick/step_harvest.py, tests/test_probe_run.py, tests/test_harvest.py
after: Task 4, Task 5

§2.5 and §2.7: one probe per deployed sha, through the start queue, on a light runner of the
product's own pool — dispatched by one tick and read back by a later one, never waited on. The
pass is four lines inside the harvest step that already runs the deploy pass; everything it calls
has landed.

**Files**

- `asf/probe/host.py` — `Host`, `GitHubHost`, `host_for(product)`
- `asf/tick/step_harvest.py` — `probe_pass(ctx, out)`, and one call after `deploy_pass` (l. 159)
- `tests/test_probe_run.py` — T4, and `PassTests`
- `tests/test_harvest.py` — the step's own assertions

**Steps**

1. `Host.dispatch(workflow, ref, inputs)`, `Host.runs(workflow, limit=15)`,
   `Host.artifact(run_id, name, dest)`. `GitHubHost` over `gh workflow run`, `gh api .../runs` and
   `gh run download`, argv shaped as `deploy.dispatch_argv` shapes its own
   (`asf/harvest/deploy.py:831`). Every call is bounded by a timeout and returns `None` rather
   than raising, as `ci_pool`'s backend does. No workflow or artifact name is a literal in the
   module (PD16) — all four inputs and both names come off the `Probe`.
2. `artifact` returning `None` — the run uploaded none — becomes one `unrunnable` per journey with
   the step `the run uploaded no results`, through `journey.parse_results`.
3. `probe_pass(ctx, out)`, called from `run(ctx, …)` immediately after `deploy_pass(product, out)`
   (`asf/tick/step_harvest.py:159`), before the gate lock is looked at, with the same guarantee:
   one loud line on any fault, never a failed step.
4. **Read back first.** For every `dispatched` ledger entry, ask `runs`. Still going: the waiting
   line, done. Complete: download the artifact, `parse_results`, `fence.judge`, `stream.append`
   into `ctx.record_root()`, mark the entry `read`. Older than `probe.timeout` and still not
   complete: mark `abandoned` with the reason, and never dispatch that sha again — the next
   deploy is the next probe.
5. **Dispatch second.** For each target whose deployed sha (`deploy.states(product)`) has no ledger
   entry and whose deploy run concluded successfully: refuse and print if `fence.lint` has a
   problem; refuse and print the `NEEDS OPERATOR` line of §2.11 if `fence.consents_granted` is
   false; build `scope.owed` and `journey.journeys`; ask `ci_queue.admit(product,
   f'probe:{target}', 'probe', item=…, workflow=probe.workflow, out=out)` (PD11); dispatch; write
   a `dispatched` entry. One target per tick at most, prod first.
6. **Never wait.** The pass takes no lock and holds up no gate. A product with no `probe:` block
   prints `probe: none — no ``probe:`` block in this product` and returns.
7. The six lines of §2.7 are asserted verbatim.
8. `tests/test_probe_run.py`: T4's four-tick sequence against a fake `Host` — dispatch once with
   the right argv and a `prod@<sha7>` entry; nothing while the run is going; the artifact read,
   the stream written and the entry `read`; then nothing at all. Past `timeout` and incomplete →
   `abandoned` with the reason, never re-dispatched for that sha, and the next deploy's sha is. A
   `ci_queue` that holds the start dispatches nothing and prints the queue's own line. A host
   whose every call returns `None` produces one line and exit 0. And the assertion that no literal
   workflow name appears in the module. `PassTests` holds the pass-level cases, including the two
   refusals of step 5.
