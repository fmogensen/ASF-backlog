## Description
stories: S-33656
writes: docs/guide/getting-started.md, tests/test_readme.py
after: Task 4, Task 6

The spec's eighth **In** bullet and `## The design` §7's first bullet. The guide's onboarding page
today takes an operator from the config files to the first `asf doctor` and never mentions the queue
of pull requests the product arrives with. Last in the wave, because the page describes what
`asf adopt-pr`, the `Adopted` row and the doctor row print on a terminal, and none of them exists
until Tasks 4 and 6 land. `docs/guide/product-config.md` and `docs/products.example.yaml` are Task 1's
and are not touched here.

**Files**

- `docs/guide/getting-started.md` — a new `## 4. Adopt the in-flight pull requests`; the existing
  `## 4. Add the /asf:* plugin` (`:105`) and `## 5. The first asf doctor` (`:121`) renumber to 5 and 6
- `tests/test_readme.py` — `AdoptTheInFlightQueueProseTests`

**Steps**

1. The new `## 4.` sits between `## 3. Adopt the record` (`:90`) and the plugin section (`:105`), and
   the two headings below it renumber — every in-page reference to "step 4" or "step 5" moves with
   them, and the file is grepped for both before the Task is done.
2. What the section says, in the order an operator does it. **What the queue is**: the open PRs the
   product's previous process opened, which ASF's native landing will not merge because their commits
   name no card and their review is not an ASF review file — so the old merge step has to keep running
   beside ASF until they are gone. **Look first**:
   `asf adopt-pr --all '<glob>' --dry-run --product <p>`, and what the table's five columns mean,
   including that a PR nothing attributes is refused by name with the `--item` line to run and that
   the rest are still adopted (D2). **Then adopt**: the same command without `--dry-run`, and what it
   wrote — one line in the product's session ledger per PR, nothing on the PR itself, nothing in the
   record. **The old review form**: `conventions.legacy_review` with a pointer to
   `product-config.md`'s paragraph, and the one sentence that matters — it is read for an adopted PR
   and for nothing else, so it can never approve a branch an ASF session pushed.
3. **Watch it drain**: `asf status`'s `Adopted | N open (M landed)` row, that the PRs merge through
   the ordinary tick with the product's own required checks, its approval matrix, `pr_order` and
   `branches_per_tick` — nothing special, nothing faster — and that the row disappears when the last
   one lands, which is the signal to move on.
4. **Then turn the old step off**: `asf doctor`'s `adopted` row, what its three forms say, and the
   edit the operator makes — `steps: {batch: off}` in the product yaml — with the warning stated
   plainly: turning it off **first** strands whatever is still open, because nothing else will merge
   those PRs. The factory never makes this edit itself (the Out section).
5. What the section must not claim: that `adopt-pr` merges anything, closes or comments on a PR,
   writes a card or a `links.prs`, or that an adopted PR's review can be answered by a factory
   session — it cannot, and the page says instead that the PR's own author answers on the PR, which
   is the `WAITING` line the lane prints.
6. `AdoptTheInFlightQueueProseTests` in `tests/test_readme.py`, in the shape
   `ProductResolutionProseTests` (`:399`) already uses — read back from the checkout, not asserted
   against a copy: the `## 4. Adopt the in-flight pull requests` heading exists and sits between
   `## 3. Adopt the record` and the plugin section; the numbering runs `1…6` with no gap and no
   repeat; every `asf` command line the section quotes is a real subcommand of `build_parser` with
   real flags, and `adopt-pr`'s quoted flags all parse; `legacy_review`, `branch_patterns`,
   `steps: {batch: off}`, `Adopted` and `asf doctor` are each named; and the warning sentence about
   turning the step off first is present.
7. Every command line quoted in the new section is run
