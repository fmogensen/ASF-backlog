## Description
stories: S-15510
writes: asf/doctor.py, tests/test_doctor.py

§2.9: a step that exists, is implemented and is on no clock is the exact failure this card is
about, and it is invisible today. On the operator's factory it reports one thing — `groom` — which
is why the report of this plan's sessions carries the line the operator has to act on.

**Files**

- `asf/doctor.py` — `check_clock_steps(product)` (new), run for each product beside
  `check_scheduler` (`:98`, `:171`) and listed in `cmd_doctor`'s output (`:484`).
- `tests/test_doctor.py` — §3/T11's three cases, beside `TestCheckScheduler:84`.

**Steps**

1. `check_clock_steps(product)` over `scheduler.clocks(product)` and `steps.resolve(product)`:
   every `asf`-owned step no clock names, as one `NEEDS OPERATOR` line naming the step and a clock
   to add it to. A step whose owner is `off` is deliberate and is not reported.
2. Wired in beside `check_scheduler`, per product, in `cmd_doctor`'s section order.
3. Tests per §3/T11: a product whose clocks tick every step but `groom` returns one line naming
   `groom`; one whose clocks tick them all returns none; a step declared `off` is not reported;
   `asf doctor` prints the line. `sample/product.yaml`'s dispatch clock naming `groom` is Task 1's
   edit (PD12) and is asserted here through `tests.test_sample_product`.
4. The Task's report carries `NEEDS OPERATOR: add the groom step to a clock in
   ~/.ASF/products/asf.yaml — dispatch: steps: [health, groom, wave, prs, harvest, batch]`; that
   file is not in this repository (§1.2).
