## Description

D16: three readers of one sha is the defect, and adding an interface beside them would make it four.
`asf/harvest/deploy.py` and `asf/views/prod.py` move onto `sources.deploy`; their own behaviour,
output and config keys are unchanged, and `tests/test_deploy.py`, `tests/test_prod_view.py` and
`tests/test_cloud.py` are the proof of it. Only the line that picks the deployed sha moves (PD13) —
`_vercel_deployed` stays, and `facts` keeps its own `runs` read for `running` and `failed`.

**Files**

- `asf/harvest/deploy.py` — `facts` takes `deploy=None` and reads the workflow sha through it
- `asf/views/prod.py` — `_deploy_sha`'s `github-deployments` branch reads through it; `_gh_json`'s
  run-list use for the deployed sha goes
- `tests/test_deploy.py`, `tests/test_prod_view.py`, `tests/test_cloud.py` — a `Recorded` or a
  concrete `WorkflowDeploy` with a fake `run`, where a `sh=`/`_gh_json` stub stood for the sha

**Steps**

1. `facts(product, sh=_sh, now=None, env='prod', _ci=None, deploy=None)`: `deploy` defaults to
   `sources.for_product(product).deploy`. Its non-vercel branch (`asf/harvest/deploy.py:622`) becomes
   `f['deployed'], f['at'] = deploy.deployment(env)`, and the `env == 'dev'` `mode == 'ci'` branch
   (`:602`) becomes the same call for `'dev'` — `WorkflowDeploy` already owns that rule (§3.7). The
   `runs` read stays for `live`/`failed`; `_age`, `_set_behind`, `_ahead`, `recorded_sha`, the modes,
   the holds and every printed line are untouched.
2. `_deploy_sha(product, kind)` (`asf/views/prod.py:39`): the `source == 'github-deployments'`
   branch becomes `deploy.deployment(kind)`; the `vercel` branch and the `(None, None)` default are
   unchanged (PD13). It keeps returning `(sha, iso_time)` — which is why the interface answers both
   (PD6).
3. The existing suites carry the regression: every assertion of `tests/test_deploy.py`,
   `tests/test_prod_view.py` and `tests/test_cloud.py` holds byte for byte, with the stubs that
   answered a `gh run list` for the deployed sha replaced by a provider. Nothing new is asserted
   here — §3.7's own new cases are `tests.test_evidence_sources.DeployTests`, landed by Task 1.
4. No config key changes: `deploy_sha.provider` is read for the first time, not invented (§4), and
   its validator row landed with Task 1.
