## Description
stories: S-33600, S-33601
writes: asf/feeder/rows.py, tests/test_feeder.py
after: none

The spec's first two **In** bullets and its `## The design` §1. The hotfix's waiting row is kept word
for word; what it was missing was a session that repairs the card, and the delivery path never had
the gate at all.

**Files**

- `asf/feeder/rows.py` — `NO_WRITES_RECUT` (new module constant); `task_rows`'s `recut` local and
  the second row in its no-writes branch; the `elif code_stage:` arm of `delivery_rows`
- `tests/test_feeder.py` — `ANoWritesTaskIsRecut`, `ADeliveryWithNoWritesDoesNotLaunch` (new
  classes); `ATaskWithNoWritesIsNotLaunched` and `WaveReadsTheBlockersOriginHolds` moved above the
  `__main__` guard (PD7)

**Steps**

1. `NO_WRITES_RECUT` beside the other row-reason constants, with the spec's comment and its text
   byte for byte: `'no writes: declared — this Task came from a plan section with no '`
   `'stories:/writes:/after: lines; re-cut that section so it carries them'`. It is a module
   constant and not an f-string because Task 6's template keys its second mode on the leading
   `no writes:` (P5, D4), and a reason built at the call site could drift from what the brief reads.
2. `task_rows` gains `recut = None` before its `for` loop, with the spec's comment naming D2.
3. The no-writes branch at `asf/feeder/rows.py:1137-1146` keeps every byte it has — the row's
   `action`, its `reason`, its `waits_on` and its `branch` are the hotfix's and are not touched
   (Out, D3) — and gains, before its `continue`, the launching row the spec writes: `kind=RESHAPE`,
   `action=LAUNCH`, `brief_kind='reshape'`, `branch=branch_for(product, 'plan', t['id'])`,
   `reason=NO_WRITES_RECUT`, guarded by `if recut is None:` and setting `recut = t['id']`.
4. The loop is already `sorted(tasks, key=lambda v: (ix.rank(v), v['id']))` (`:1099`), so "the first
   no-writes Task in the loop's own order" needs no new ordering — it is the first one the loop
   reaches. Nothing is sorted twice.
5. `delivery_rows`'s `elif code_stage:` branch (`:936-945`) computes `union = _delivery_union(items, lead)`
   as it does today, and before `footprint.first_conflict` refuses an empty one exactly as the spec
   writes it: a non-launching `WAITS ON writes` row with `waits_on='writes'` and the reason
   `'no writes: declared on any open member: the plan must name the files this delivery writes '`
   `'before a coder can start'`, then `continue`. The `continue` is the point (PD14): the lead never
   reaches `running.append`, so an empty footprint claims nothing against the Tasks running beside it.
   No re-cut row is added on this path — a delivery's members are Tasks, and each one that has no
   `writes:` gets its own re-cut through `task_rows`.
6. `_delivery_union` itself is not touched. The amend `elif` above (`:930-932`) already calls it and
   already returns None for an empty list (PD13), so the two calls stay as they are rather than
   being hoisted — hoisting would change which branch runs first.
7. `ANoWritesTaskIsRecut` (new class, above the guard): a Feature at `plan-approved` with three New
   Tasks — two with no `writes:`, one writing `a.py` — gives **two** `WAITS ON writes` rows, each
   with the hotfix's exact reason; **exactly one** `RESHAPE → PLAN` row, `action` launching,
   `brief_kind='reshape'`, on `plan/<the first id in (rank, id) order>`, with a reason starting
   `no writes:`; and the third Task still launches its coder. Cases: the re-cut lands on the lower
   `rank` when the ids would order the other way, and on the lower id when the ranks tie; a second
   Feature in the same index gets its **own** one re-cut (the local is per call, not per wave); a
   Feature all of whose Tasks have `writes:` gets no reshape row at all; and a Task the groom marked
   `reshape:` keeps its own `WAITS ON reshape` + `RESHAPE → PLAN` pair and does **not** consume the
   Feature's re-cut, so a Feature with one groomed and one no-writes Task has two reshape row
