## Description
stories: S-32800

after: none

The spec's §`asf/env.py`, D1 and D2. One declared product-file key, one normalising property, one
raw-word property, and the example file's documentation of it. Nothing reads the key yet — Task 3
is its first reader — so this Task lands alone and changes no behaviour.

**Files**

- `asf/env.py` — `'upgrade': _STR` in `PRODUCT_FIELDS` (`:515-523`), `UPGRADE_POLICIES`,
  `UPGRADE_DEFAULT`, `Product.upgrade`, `Product.upgrade_declared`
- `docs/products.example.yaml` — the annotated `upgrade:` row beside the `approvals:` block
- `tests/test_env.py` — `UpgradeKeyTests`
- `tests/test_release_channel.py` — new module: `ProductUpgradePolicyTests`

**Steps**

1. `asf/env.py`: `'upgrade': _STR` joins `PRODUCT_FIELDS`. It is a top-level scalar, not a member
   of `NESTED_FIELDS` and not a fourth `approvals` class (D1) — `approvals.upgrade` is a different
   key governing a different channel, and the two must be readable side by side in one product
   file without either shadowing the other.
2. `UPGRADE_POLICIES = ('auto', 'notify', 'off')` and `UPGRADE_DEFAULT = 'notify'` at module level,
   with the comment the spec gives: what `upgrade:` may say, and that anything else reads as the
   default and is a doctor RED.
3. `Product.upgrade`, beside `Product.approvals` (`:828-830`): `str(self._get('upgrade') or
   UPGRADE_DEFAULT).strip().lower()`, returned when it is in `UPGRADE_POLICIES`, else
   `UPGRADE_DEFAULT`. The docstring is the spec's, verbatim in substance: which of the two channels
   the key governs, and that a product whose repo is the factory's own source is on the other one
   under `approvals.upgrade`.
4. `Product.upgrade_declared` returns `self._get('upgrade')` raw — `None` when absent, the literal
   string when present (PD13). It exists for one caller, Task 6's doctor row, which must quote the
   typo back; normalising it here would make the row unable to say what is wrong.
5. An unrecognised word does **not** refuse the product load (D2): `_shape_ok` checks the shape and
   nothing checks the value, so a typo loads, reads as `notify`, and is caught loudly by the doctor
   rather than taking the whole product down. The property's docstring says why.
6. `docs/products.example.yaml`: one commented `upgrade:` row beside `approvals:`, saying the three
   words, the default, that an unrecognised word reads as `notify` and is a doctor RED, and the one
   line the spec asks for on which channel it governs — this key is the *release* channel; a
   product whose repo is ASF's own source is on the trunk channel under `approvals.upgrade`. The
   row is commented out, like its neighbours, so `tests/test_env.py:284`'s
   `test_the_documented_example_validates` keeps passing on an unchanged parse and the key is still
   documented.
7. `UpgradeKeyTests` in `tests/test_env.py`: `upgrade: auto` validates; a product declaring no
   `upgrade:` reads `notify`; `upgrade:` with an empty value reads `notify`; `docs/products.example.yaml`
   names the key and still validates with no problems.
8. `tests/test_release_channel.py`, new module, stdlib and the suite's own fixtures only:
   `ProductUpgradePolicyTests` — each of the three words round-trips through `Product.upgrade`;
   `AUTO`, ` auto `, `Auto` all read `auto`; `atuo` reads `notify` and `upgrade_declared` returns
   `'atuo'`; an absent key reads `notify` and `upgrade_declared` returns `None`. The module is
   picked up by `tools/run_tests.py`'s `tests/test_*.py` glob with no registration.
