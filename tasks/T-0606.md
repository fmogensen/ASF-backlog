## Description
stories: S-36551
writes: asf/workers/health.py, tests/test_health_publish_steps.py
after: Task 1

The spec's §3 (D3): the publish gate widens by the single case `reason == lifecycle.FAILED_BARE`,
and the two sibling gates that S-36551's own fence names widen by the same one (PD1). No new push
path, no new function, nothing downstream of any gate touched — the same `commit_leftovers`, the
same rebase, the same `lifecycle.publish`, the same re-judge, the same `publish_refused`.

Read **PD1** (three gates, measured) and **PD2** (`publish_refused` is written in exactly one
place, and it is behind the third gate) before starting.

**Files**

- `asf/workers/health.py` — `publish_gap`'s `result_ok` (`:396`), `push_retry`'s opening guard
  (`:557-558`), `republish_steps`' opening guard (`:521-522`).
- `tests/test_health_publish_steps.py` — the dead run's publish, its three refusal paths, and the
  case the gate must **not** take.

**Steps**

1. `publish_gap`: `result_ok = (reason == lifecycle.FINISHED or (reason or '').startswith(
   UNPUSHED_REASON_PREFIXES) or reason == lifecycle.FAILED_BARE)`, with the spec's own trailing
   comment — `# F-0223: a mid-flight death still has work`. Equality, never a prefix test: that is
   what keeps `failed: <anything>` out of the gate (P4, P6) and it is the fence's last assertion.
2. `push_retry`: the guard becomes `if not ((reason or '').startswith(UNPUSHED_REASON_PREFIXES) or
   reason == lifecycle.FAILED_BARE): return None`, with a comment naming PD1's reason — a dead
   run's publish can be refused by the repo's hook or lose the network exactly as an unpushed run's
   can, and this function is the only reader that tells those two apart. Nothing else in it moves:
   the `pushed:` line it reads, the `publish \S+ refused:` regex, the 600-character cut all stay.
3. `republish_steps`: the guard becomes `if not (reason.startswith(UNPUSHED_REASON_PREFIXES) or
   reason == lifecycle.FAILED_BARE) or run.get('harvested') or not branch: return`. This is what
   records `publish_refused` for a dead run (PD2) and what gives it F-0094's later retry once the
   refusal's cause is fixed. Its docstring gains one sentence naming the second reason class it now
   covers; the worktree-owner check, the `' refused: '` split and the "not printed again" guard are
   untouched.
4. Nothing else in the module changes in this Task. In particular the ladder (`:723-792`) gains no
   arm here — that is Task 3 — so a bare-`failed` run whose publish succeeds still reaches no arm
   when this lands, and that is the honest intermediate state: its branch is on origin, its work is
   safe, and the item is still going nowhere until Task 3.
5. `tests/test_health_publish_steps.py`, in its own idiom (`health.run_steps` driven by hand-built
   generators, `threading` for the concurrency cases): a bare-`failed` run with commits in its
   worktree is published and `publish_gap` returns a line; the same run with a reason of
   `failed: not pushed: …` behaves as today (regression, not a new case); a `failed:
   <anything>` run — `failed: token cap`, and one with a second clause — is **not** published, and
   that assertion is the proof the gate widened by exactly one case.
6. The three refusal paths, each asserted to behave as an unpushed run's does: the repo's pre-push
   hook refuses → `push_retry` classifies it, the reason becomes `failed: hook refused: …` and the
   hook-refusal hold is written; the network blips → the `retry` row is found, no round is spent
   and no `ended` is written, so the next pass publishes again; origin holds commits the head lacks
   → the stale-head line is produced. Plus `publish_refused` recorded through `republish_steps` for
   an **ended** bare-`failed` run whose publish was refused, and not written twice for the same
   line (PD2).
