## Description
stories: S-104409
writes: docs/guide/upgrading.md, docs/guide/troubleshooting.md, tests/test_readme.py
after: Task 1, Task 3

The spec's design §5's two guide edits (D-0008). The upgrading row is the sentence that licensed the
interruption, and once Tasks 1 and 3 have landed it is only half true — the install still ends the
tick, but it no longer leaves the clock behind. The troubleshooting table has a row per operator
line the installer can print, and a new line with no row is a line nobody can look up.

This is the one Task whose `writes:` intersect nothing else, so it runs alongside Task 4 (**PD8**).
Its `after:` names Tasks 1 and 3 because the sentence it writes is a claim about their landed
behaviour, not because of a file.

**Files**

- `docs/guide/upgrading.md` — the `asf scheduler install` row becomes §5's wording: the tick still
  ends, nothing is lost, *and the command waits for the old job to leave launchd, reads every clock
  back, and exits non-zero naming any it could not load. Still: install between ticks when you
  can*. **The row is at `:159`, not the `:125` the spec cites everywhere** (`ed15152ec` inserted 34
  lines above it — **PD3**); find it by its text, not its line.
- `docs/guide/troubleshooting.md` — one row in the installer table (`:30-40`) for
  `NEEDS OPERATOR: clock(s) not loaded after install: <labels>`, whose repair is the command again,
  between ticks, then `asf doctor --product <p>`. It goes beside the existing step-8 clock row at
  `:38`, which is the *installer's* line (`install: NEEDS OPERATOR: clock(s) still not loaded after
  retrying the bootstrap`) and stays exactly as it is — the two lines are different commands and
  need separate rows.
- `tests/test_readme.py` — `test_troubleshooting_names_the_installer_operator_lines` (`:473-479`)
  gains a needle for the new line, and a case for the `asf scheduler install` row in
  `docs/guide/upgrading.md`. The existing needles all keep passing: nothing here removes a line.

**Steps**

1. Rewrite the upgrading row, located by its text. Do not soften the existing warning: the row
   still says to install between ticks when you can, because the install still ends a running tick
   — refusing to install while a tick runs, or draining first, is in the spec's **Out**.
2. Add the troubleshooting row in the voice of the ten rows around it: the line, the cause, the
   repair.
3. Extend `tests/test_readme.py` to pin both, then run the Gate.

## What this plan leaves unbuilt, and why

Everything in the spec's **Out** stands untouched, and this plan adds nothing to it: refusing to
install while a tick is running or draining first (the guide licenses the interruption and nothing
is lost by it; the drain machinery that exists costs a bounded wait on the whole floor plus a pause
record per clock); a periodic out-of-band check that a product's clocks are loaded (the doctor row
already says it, and a product whose tick clock is gone cannot notice its own absence — a host-level
watcher is a Feature of its own); `asf install` step 8's own read-back and retry, which stays byte
for byte; the `--host` install's exit status, which already returns 1 on a `failed` line and
inherits the wait and the retry through `_launchd_install`; a read-back for the systemd connector or
any non-launchd kind, which needs the exit-status-3 contract rethought first; a pid in the "it was
running" line, which the product's own `print` reader does not parse; changing `bootstrap()`,
`resume()`, `pause()` or `uninstall()`; a new card, record row, metric
