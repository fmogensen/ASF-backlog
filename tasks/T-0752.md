## Description
stories: S-39252
writes: docs/guide/operating.md, tests/test_readme.py
after: Task 1

The spec's `## The design` §3 — the inbox paragraph of `docs/guide/operating.md` (`:263-269`, inside
`## The groom and the inbox` at `:255`, which runs to `:315`), and the prose class that holds it.

The paragraph says, today, *"The type is always derived from the card's shape, and a `type:` line is
not read"* — false since `9230bf932`, in the customer-facing guide, in the same section that
documents the drop-a-file path F-0134's reporter used (P7). It is the sentence the card's title is a
complaint about, printed at a customer instead of an operator.

It waits on Task 1 because the paragraph it writes describes Task 1's refusal (PD13). Landing it
first would replace one false claim about intake with another.

**Files**

- `docs/guide/operating.md` — the inbox paragraph at `:263-269`; the five shape rules in it stay
  exactly as they read. No other section moves
- `tests/test_readme.py` — `IntakeTypeLineProseTests`, shaped on `ProductResolutionProseTests`
  (`:482`), `WorktreeSetupProseTests` (`:507`) and `ModelRoutingProseTests` (`:540`) — `_read` plus
  assertions over the checkout, never a fixture (P13)

**Steps**

1. Rewrite the paragraph's two claims. The body *may* carry a `type:` line, named beside `parent:`,
   `severity:`, `signature:`, `writes:` and `stories:` — six, not five. And the sentence *"a `type:`
   line is not read"* goes; what replaces it says the line **is** read.
2. State the two outcomes, in the guide's own voice: a `type: bug` card with no `signature:` gets one
   from its title and is minted a Bug (`9230bf932`, P3); any other declared type the card is not yet
   shaped like is refused with a question in `groom/<date>.md` naming the line that would settle it,
   and is never minted as the other type.
3. State the rule Task 1 adds: every header line, `type:` included, must sit **below** a `# <title>`
   line, because a card that leads with a header has no title and is refused. This is the one
   sentence that would have saved F-0134's reporter, and PD6 measures why it only ever bites a
   hand-dropped file: `asf inbox` and the scorecard loop both write the `# <title>` line themselves.
4. Leave the five shape rules exactly as written — Bug ← `signature:`, Task ← `writes:`, Epic ← a
   Features list, Story ← a Feature `parent:`, else Feature. They are what fills whatever the `type:`
   line leaves open, and the paragraph must still name all five. Keep *"To file a Bug, give it a
   `signature:` and a `severity:`"* true: with `type: bug` the signature is now optional, and the
   sentence should say what it gets instead.
5. `IntakeTypeLineProseTests` in `tests/test_readme.py`, the spec's cases: the file does not contain
   ``a `type:` line is not read``; the inbox section names `type:` among the lines the body may
   carry; it states the `type: bug`-without-`signature:` rule; it states that a header line must come
   below the `# <title>` line; and it still names all five shape rules. Slice the section between
   `## The groom and the inbox` and the next line starting with `## ` — the two precedent classes'
   `_section` helpers cut on `###`, and this section has no `###` inside it (`:255-315`), so the
   helper needs the `## ` bound instead. Copy their `_read` verbatim and read from `REPO_ROOT`.
6. No other document changes. `README.md` carries no copy of the claim (measured: `grep -rn "is not
   read"` finds it only in `docs/guide/operating.md:266`, `docs/guide/product-config.md:33` — an
   unrelated `share` row — and `tests/test_inbox_shape.py:217`, which is Task 1's).
