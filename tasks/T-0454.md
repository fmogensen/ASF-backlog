The spec's §5 and P19: a non-required `schema` row after `config` with the four answers the spec
spells out; `check_config` loading a product whose only problems are tolerated so the other twenty
rows still render (P7, PD12); and `doctor._capacity_deprecations` deleted in favour of
`capacity.deprecations`, which now reads `CONFIG_MIGRATIONS`'s rename table — which is what the
comment at `asf/doctor.py:495-499` has been asking for since F-0079.

**Files**

- `asf/doctor.py` — `check_schema`, the `schema` row in `run`, `check_config`'s tolerated path,
  `check_capacity` delegating; `_capacity_deprecations` deleted
- `asf/capacity.py` — `deprecations(cfg)` reading `schema.CONFIG_MIGRATIONS`'s `renames` through
  `env.deprecated_reads`, its two hand-written lines gone; its wording unchanged
- `tests/test_doctor.py` — `SchemaRowTests` (new); `Capacity` keeps its cases and gains the table's
- `tests/test_schema_version.py` — `RenamedFieldsStayReadableTests` appended; every class Task 1
  wrote is untouched

**Steps**

1. `check_schema(product)` → `[(level, detail)]`, the four answers of the spec's §5, byte for byte:
   `ok` — `record 2, config 2, package 2`; one warning line per tolerated key —
   `products/sample.yaml: 'lane_timeout' is not a field of the product file — written by a newer
   asf? (file schema 3, this package 2)`; a warning — `schema 1 → 2 pending (additive) — the next
   tick migrates`; a red — `schema 1 → 2 pending (not additive) — run asf schema-migrate --drain`.
   It reads `schema.pending`, `schema.blocking` and `env.product_warnings`/`env.config_warnings`, and
   computes nothing of its own.
2. The row is appended in `doctor.run` directly after `config`, non-required, so a warning never
   makes `asf doctor` red and the pending-migration case is visible without being a failure.
3. `check_config` (PD12): it still returns a single red row when `config.yaml` itself does not load,
   or when the product file has a fatal problem — nothing after it can work without a `Product`. When
   the product file's only problems are `product_warnings`, it loads the product from that path,
   returns `ok` with its existing detail, and `run` proceeds through every other row; the keys
   themselves are named by the `schema` row, not by this one. The early `return rows` stays for the
   two fatal cases and only those.
4. `capacity.deprecations(cfg)` keeps its exact two output strings and stops hard-coding the pairs:
   it walks `env.deprecated_reads(cfg)` and renders `f'{old} is set — move it to {new}'`. With
   PD8's table the output for today's configs is byte-identical, which is what keeps
   `tests.test_doctor.Capacity` and `asf capacity` green without an edit to their expectations.
5. `doctor._capacity_deprecations` is deleted and `check_capacity` calls `capacity.deprecations(cfg)`
   (P19). The stale comment block at `asf/doctor.py:495-499` — "Once `asf.capacity` exists,
   `check_capacity` should delegate" — goes with it. `_product_declared_sessions` is left alone: it
   is the other half of that comment and `capacity:` is a declared field now, but retiring it is not
   this card's footprint and it has its own callers.
6. `SchemaRowTests`: a matching install renders the `ok` detail; an install with an unstamped config
   renders the additive-pending warning and nothing red; a fabricated non-additive gap renders the
   red with the `--drain` line; a product file stamped newer with two unknown keys renders two
   warning lines naming both keys and **the rest of the doctor table still renders** — asserted by
   row count against the same install without the keys, which is P7's defect stated as a test.
7. `Capacity` gains one case: with `feeder.capacity` set, the deprecation line is the one string it
   has always been, and it now comes from `capacity.deprecations`; patching `CONFIG_MIGRATIONS`'
