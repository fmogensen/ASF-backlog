## Description

§2.3: the one fact the wave knows and nothing else does — that it launched nothing, that New Tasks
existed anyway, and which gate held the rows it planned but did not launch. A pure function for the
answer, one key on the tick line, one key in the ticks schema. No printed line changes,
`wave: nothing to launch` included.

**Files**

- `asf/tick/step_wave.py` — `GATE_CAP`, `NO_ROW`, `wave_state`; `run` collecting the held and
  non-launching rows it already iterates and setting `ctx.wave` before each return
- `asf/tick/tick.py` — `Context.__init__` gains `self.wave = {}`; `tick_line` carries `wave=ctx.wave`
- `asf/metrics/metrics.py` — `SCHEMAS['ticks']['wave'] = (('dict',), {})`
- `tests/test_tick_steps.py` — `WaveStateTests`
- `tests/test_metrics.py` — `TickWaveSchemaTests`

**Steps**

1. `GATE_CAP = 10` and `NO_ROW = 'no row planned'` at module level in `step_wave`, with §2.3's
   doc comments.
2. `wave_state(planned, held, items, launching=0)`, pure, returning
   `{'idle': bool, 'new_tasks': int, 'new_task_ids': [...], 'gates': {gate: items}}`:
   - `idle` is `not launching`;
   - `new_tasks` / `new_task_ids` from `items` per PD13, ids sorted, capped at `GATE_CAP`, the
     count uncapped;
   - a gate per non-launching row: `held <class>` when the row's item is in `held`, else
     `row.waits_on`, else the first word of `row.action` (PD14); counted, not listed;
   - `gates = {NO_ROW: new_tasks}` when `planned` is empty and New Tasks exist; `{}` when neither.
3. `run` collects the rows it skips in the loop it already has — the `not row.launches` branch and
   the `row.item_id in held` branch — and sets `ctx.wave = wave_state(planned, held, items, launching=len(worker_rows))`
   before the `not worker_rows` return **and** before the final return (PD15). The `out()` calls,
   the `capacity` event, the `launch` events and `ctx.counts['launches']` are untouched.
4. `Context.__init__`: `self.wave = {}` beside `self.counts` (`asf/tick/tick.py:149`).
5. `tick_line`: `wave=ctx.wave` in the returned dict (`asf/tick/tick.py:415`). Nothing else on the
   line moves, and `write_tick_line` is unchanged.
6. `SCHEMAS['ticks']` gains `'wave': (('dict',), {})` and only that (PD6). No new rule in
   `validate`'s `ticks` branch: a `dict` is all the key promises.
7. `WaveStateTests` per T5: the three-row planned list (one `WAITS ON T-0044`, one `ON TRUNK`, one
   row whose item is in `held` as `('merge_pr', 'human-now')`) with `launching=0` →
   `idle: True`, the record's New Task count and ids capped at 10, and
   `gates == {'T-0044': 1, 'trunk': 1, 'held merge_pr': 1}`; the same with `launching=1` →
   `idle: False`; `planned=[]` with `n` New Tasks → `gates == {NO_ROW: n}`; a row with neither
   `waits_on` nor a launching action → the first word of its action.
8. In `WaveStepTests`: a tick over the existing fixture with `plan_rows` returning `[]` still
   prints exactly `wave: nothing to launch` and leaves `ctx.wave['idle']` true. In the tick's own
   end-to-end fixture: `asf tick --steps record,wave` writes a `metrics/ticks` line whose
   `wave.idle` is true, and `asf tick --steps record` writes one whose `wave` is `{}`.
9. `TickWaveSchemaTests` per T5: `metrics.validate('ticks', line, {})` accepts a line carrying
   `wave` and returns it unchanged; a line without `wave` comes back with `{}`; a `wave` that is
   not an object raises `SchemaError`.
