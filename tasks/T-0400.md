stories: S-33755

after: Task 1, Task 3

§2.5's first row and §2.4. D3: `import-items` pairs with the `import-sessions` already on the
surface, so the surface gains a family instead of a singleton, and the one genuinely dangerous
option — giving the name `migrate` to `schema-migrate` — is refused, because an operator with
`asf migrate` in muscle memory would then silently run a schema migration.

The guard lands here and not earlier (PD5): `surface.RENAMED` retires all three names at once, and
only now have `board` and `stories` landed, so every line it prints names a command that exists.
`after:` is both Task 1 (the module the guard imports) and Task 3 (the last rename before it).

Four prose disclaimers exist only to tell the two migrations apart. They are deleted, not reworded:
the collision is what they were for, and the collision is gone.

**Files**

- `asf/cli.py` — `sub.add_parser('import-items', …)` at `:226`, the dispatch arm at `:488-490`, and
  the `RENAMED` guard at the top of `_main`
- `asf/tick/migrate.py` — the module docstring's `(``asf migrate``)` (`:1`). The module keeps its
  name: `asf.tick.migrate` is imported by `asf/record/plan_order.py`, `asf/record/plan_tasks.py` and
  `asf/tick/file_bugs.py`, and §2.5 names the docstring only
- `asf/schema.py:2`, `asf/record/plan_tasks.py:4`, `pyproject.toml:3` — the three disclaimers whose
  whole content is "not the other migration": deleted
- `asf/views/roadmap.py:4` — not a disclaimer but a reference: `asf migrate` → `asf import-items`
- `asf/conventions.py:332-334` — three comments naming `asf migrate` as the reader of
  `design_spec_name`, `decisions_file` and `reports_dir`
- `tests/test_surface.py` — `RenameTests`
- `tests/test_path_resolution.py:35`, `tests/test_migrate.py`, `tests/test_report.py:99`,
  `tests/test_cli.py`

**Steps**

1. `asf/cli.py:226`: the parser name becomes `import-items`, the local becomes `p_import_items`, the
   flags and the `help=` string are unchanged. `:488-490`'s arm compares `args.command ==
   'import-items'` and still calls `cmd_migrate` from `asf.tick.migrate` — the command is renamed,
   the module is not.
2. The guard, at the top of `_main`, exactly as §2.4 writes it: read the first positional, and when
   it is a key of `surface.RENAMED`, print one line to stderr naming the replacement and the command
   to run, and return 2 with nothing else done. `import asf.surface` at the top of `asf/cli.py`
   beside the others — `surface` imports nothing from `asf`, so there is no cycle.
3. Exit 2 is what the CLI already returns for an operator-fixable refusal (`needs_operator_line`),
   and the guard runs **before** `build_parser()`, so argparse never gets to answer with its list of
   49 choices (D6). Note in the docstring what the guard does not catch: a retired name behind a
   global flag (`asf --product p migrate`) reaches argparse and gets `invalid choice`. That is
   §2.4's own design — the first positional is the whole check — and this plan does not widen it.
4. Delete the three disclaimers (`asf/schema.py:2`'s parenthetical down to the `asf.tick.migrate`
   pointer, `asf/record/plan_tasks.py:4`'s sentence, `pyproject.toml:3-4`'s comment) so each
   docstring says what its own module is, with no reference to a collision that no longer exists.
   `asf/views/roadmap.py:4` and `asf/conventions.py:332-334` keep their sentences with the new
   command name — they name the reader of a convention, which is still true.
5. `tests/test_surface.py`: `RenameTests`, over `asf.cli.main` in process with stdout and stderr
   captured. For each of the three retired names: rc is 2; stderr carries one line naming the old
   name and its replacement; stdout is empty; and nothing is written — ru
