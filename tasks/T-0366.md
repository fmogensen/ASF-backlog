§2.8: the three rule cards with their shims, in the layout and the reserved band F-0061 §2.1
specifies, created by whichever of the two Features lands first (P13, D8, PD12). The ids are
`R-0008`–`R-0010` and the scripts `r0008.sh`–`r0010.sh`, so neither Feature renames a file when the
other lands.

**Files**

- `rules/README.md` — created when absent, appended to when F-0061 landed it first (PD12)
- `rules/R-0008.md`, `rules/R-0009.md`, `rules/R-0010.md` — `id`, `type: rule`, `title`, `check`,
  the statement; **no `hook:`** on any of them
- `rules/r0008.sh`, `rules/r0009.sh`, `rules/r0010.sh` — the four-line shims
- `tests/test_core_rules.py` — `CardTests`, `ScriptTests`, `AdoptionTests`, `PassCheckTests`

**Steps**

1. `rules/README.md`: the core band `R-0001`–`R-0099` (F-0061 D11), the card shape (F-0061 §2.1's
   frontmatter block), the two halves — the `hook:` half binds from this directory on `asf hooks
   install`, the `check:` half only through a product's own record card of the same basename — and
   P15's consequence in one sentence: an installed `asf` packages `asf/**` only
   (`pyproject.toml:23-29`), so this directory ships with a checkout and a product's record holds
   the one-line shim. When F-0061 landed the file first, only the three rows are added and nothing
   else in it is rewritten.
2. Each card: `id`, `type: rule`, `title`, `check: tools/checks/r000N.sh`, then the statement in
   the card's own words — R-0008 the security pass ("a branch whose diff touches a configured
   sensitive class is not read by a general review alone"), R-0009 the host's alert feeds, R-0010
   exposed ports. `type: rule` and `check:` are what `rules.py`'s `partition` reads off a record
   card (`:96-110`); `hook:` is deliberately absent — a `PreToolUse` hook cannot see a branch, a
   feed or a box (§2.8).
3. Each script is F-0061 D4's shim, §2.8's four lines: the shebang, two comment lines naming the
   rule and the contract, `set -euo pipefail`, and `exec "${ASF:-asf}" security <sub> --check`.
   Executable (`chmod +x`), no path literal, no product name.
4. `resolve_script(root, 'tools/checks/r0009.sh')` finds the product's own script first and this
   directory's basename second (`asf/rules/rules.py:67-73`), which is why the card's `check:` is
   the *product's* path and the script's name is the basename.
5. `CardTests`/`ScriptTests` per §3's T8: `rules/` holds `README.md` and the three cards; every
   card's frontmatter carries `id`, `type: rule`, `title` and `check`; every `id` is inside
   `R-0001`–`R-0099` and no two collide (asserted over every card in the directory, so F-0061's
   seven are included when they are there); every `check:` basename has a script beside its card;
   every script is executable, passes `bash -n`, and its `exec` line names a subcommand **the real
   parser accepts** — asserted by building Task 8's parser and parsing the script's argument list,
   not by comparing strings.
6. `AdoptionTests` — the card's first acceptance, hermetic per PD11: with `ASF_CORE_RULES_DIR`
   pointed at `rules/`, `BACKLOG_ROOT` at a temp record holding three one-line adoption cards, a
   fake `gh` on `$PATH` and `ASF_HOME` at a tmpdir, `asf rules check` runs all three and reports
   each as a pass over a clean fixture and a violation over a planted one. The fake `gh` asserts
   that no `--jq` it is handed names the `secret` field.
7. `PassCheckTests` per §3's T9: over a lane snapshot fixture, a branch in a live state whose diff
   touches `auth` with no precheck of its head is one line carrying `sig=unread-<item>`; the same
   branch with a current, complete, clean precheck is none; one whose precheck holds a blocking row
   is one line; one whose precheck misses a class row is one line naming the dimension; a branch
