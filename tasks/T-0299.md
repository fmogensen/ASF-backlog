## Description
stories: S-30454
writes: asf/record/plan_check.py, asf/cli.py, tests/test_plan_check.py
after: Task 1

§2.5, with PD5's correction: the two findings the section names cannot be read off
`task_order`'s result, because `task_order` drops an unknown predecessor and a cycle-closing edge
before returning. The check reads what each Task section *declares* and what the parser *kept*,
and reports the difference. A path in, a table out: no record, no product, no git, which is what
makes it runnable on a draft in a worktree before anything is committed (§1.4).

**Files**

- `asf/record/plan_check.py` — new; `findings(plan_text)`, `cmd_check(args, out=print)`,
  `register(sub)`
- `asf/cli.py` — the `plan-check` registration
- `tests/test_plan_check.py` — new module; `PlanCheckTests`

**Steps**

1. `asf/record/plan_check.py`, docstring first: what the module is for — a plan is read by
   `plan_order` and `migrate` when its Tasks are minted, and this runs those same readers before
   the plan is committed, so the author sees the DAG the factory will build and not the one they
   meant. It names no document directory in a string literal (PD14): the path is `argv`'s.
2. Read the plan once: `records = migrate.plan_task_records(text)`, `order = plan_order.task_order(text)`,
   and per record the declared edges `plan_order._explicit(body)` and `plan_order._card_ids(body)`.
   The private helpers are this module's package neighbours and are called, not copied: a second
   `after:` parser is the defect this Story closes.
3. Finding 1 — **an `after:` target that is not a Task of the plan**: a number in `_explicit`'s
   list that is not a key of `order`. Print it as `! T<n> after: <m> — no such task`. This is the
   finding §2.5 sourced from "keys vs. values", where it is not visible (PD5).
4. Finding 2 — **a cycle**: a number in `_explicit`'s list that *is* a key of `order` and is not
   in `order[n]`. `task_order` dropped exactly one class of edge for that reason, and
   `plan_order._reaches(order, m, n)` says which way round it was. Print
   `! T<n> after: <m> — would close a cycle; the minter drops this edge`. A self-reference
   (`after: Task <n>` in Task `n`) is the same finding with the same line.
5. Finding 3 — **two Tasks with no ordering between them whose `writes:` overlap**: for each pair
   `(a, b)` where neither reaches the other in `order` (`plan_order._reaches`, the transitive
   closure — Task 3 after Task 1 may overlap Task 1 and may not overlap Task 2), report the first
   pair of globs for which `footprint.globs_overlap` is true, in either direction. Print
   `! T<a> and T<b> run together and both write <glob>`.
6. Finding 4 — **a Task section with no `Files:`/`Writes:` line**: `migrate.writes_lines(body)`
   returns `None`. Print `! T<n> — no Files:/Writes: line`. A Task with no footprint is a row the
   feeder refuses (`asf/feeder/rows.py`'s `WAITS ON writes`), so it is a finding here.
7. The header and the per-Task footprint lines of §2.5's block: `plan-check <path> — <n> tasks`,
   then one indented `T<n>  <glob>, <glob>` line carrying **what `writes_lines` parsed**, not what
   the line said. That is the whole reason the footprint is printed: `writes_lines` splits on
   commas (`asf/tick/migrate.py:216`), so a space-separated line reads back as one glob, and the
   author sees it instead of being told about it. The comma split is not changed here (§1.3).
8. `== <n> findings` as the last line; `cmd_check` returns 1 on any finding, 0 on none.
   `--json` prints the findings as a list of typed dicts for a session that wants to act on them.
9. `register(sub)`: `asf plan-check <plan> [--json]`, `set_defaults(run=...)`, the same shape as
   Task 1's; `asf/cli.py` gains `from asf.record import plan_check` / `plan_check.register(sub)`
   in the block at `:345-352`. `plan-check` is not in `plugin_build.VIEWS`, so the plugin tree is
   unchanged (§1.1).
