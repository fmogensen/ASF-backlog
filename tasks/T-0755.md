stories: S-39352

after: Task 2

The spec's `I4`, `I5` and `## The design` §3 — `scheduler.launcher_stale(product_name)`, two new
keys on `clock_code`, and one suffix plus one clause on the `clock code` row. Neither of the two
failures this card is about is visible in the row today: a clock running a stale launcher and a code
dir holding 140 worktrees both read as a healthy green row.

The row is worth building even though Task 1 self-heals the drift, and C5 is why: the case where the
drift matters most is the case where the self-heal never fires — a clock that is not ticking. It is
also the only place the pool's size is ever stated to a human.

It waits on Task 2 because the count it prints is the number Task 2 bounds — a row that reports 140
before the bound lands is a true number and a misleading one — and because both Tasks write
`tests/test_snapshot.py`.

Read **PD2** (the row must name `asf scheduler install --product <p>`; `asf clock install` is not a
command), **PD3** (there is no YELLOW for a product row — `ok` stays `True` and the words go in the
detail), **PD11** (`launcher_stale` is carried as the whole pair) and **PD18**
(`tests.test_doctor.ClockCodeRowTests` is a class this Task creates) before starting.

**Files**

- `asf/scheduler.py` — `launcher_stale(product_name)` below `write_launcher` (`:167-184`) and above
  `clock_code` (`:187`); `clock_code`'s snapshot branch and docstring (`:187-198`)
- `asf/doctor.py` — `check_clock_code` (`:353-365`); the module docstring's `clock code` sentence
  (`:34-36`)
- `tests/test_snapshot.py` — `DoctorShowsTheClocksSha` (`:155-168`) extended: `launcher_stale`'s
  three cases over the real fixture code dir, and `clock_code`'s two new keys
- `tests/test_doctor.py` — `ClockCodeRowTests`, a new class (PD18)

**Steps**

1. `launcher_stale(product_name)` in `asf/scheduler.py`, with the spec's docstring byte for byte
   (§3): `(stale, reason)` from the installed `launcher_path(product_name)` read against
   `snapshot.__file__`'s bytes, and `(False, '')` when there is no launcher — the clock is not a
   snapshot clock and there is nothing to be stale. Every `OSError` on either read returns
   `(False, '')`: a doctor row never raises out of a missing file. The reason, when it is stale, is
   `"the installed launch.py differs from this package's asf/snapshot.py"` — the words the spec's §3
   row prints, so the row is a `.format` of the reason and not a second copy of it.
2. `launcher_stale` does its **own** read rather than being factored out of `write_launcher`
   (`:170-179`), which does the same compare. O1 keeps `write_launcher` unchanged, and the two
   functions want different things from a failure: the writer falls through to writing, the reader
   answers `(False, '')`. Note the shared contract in the docstring instead.
3. Note in the docstring what `snapshot.__file__` means when the running package *is* a snapshot: the
   comparison is then against the sha the tick is running, which is the right answer — the question
   the row asks is whether the launcher matches the code that is running, not the checkout's HEAD,
   which the row already reports separately (P8).
4. `clock_code`'s snapshot branch (`:193-198`) gains exactly two keys (PD11): `launcher_stale`, the
   whole pair from step 1, and `snapshots`, `len(snapshot.snapshots(code))` where `code` is the
   `code_dir(product_name)` the branch already computes at `:193` — bind it to a local rather than
   calling it a third time. The early `not snapshot` return (`:191-192`) is unchanged: a product
   whose clock runs an installed package has no launcher and no pool, and the row's non-snapshot
   detail (`asf/doctor.py:358`) stays exactly as it reads. `clock_code`'s docstring gains both keys.
5. No byte size in the row (O2): `snapshot.snapshots` is one `os.listdir` plus one `isfile` a sha
   (`asf/snapshot.py:93-98`), where a size would be a f
