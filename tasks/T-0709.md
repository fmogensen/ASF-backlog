The spec's §2, §3 and §5's `vm_pass` — the heart of the card. After this Task `ci_vm.vm_pass`
pushes a sha to a machine, runs a command in a disposable worktree, collects the exit code and
forty lines, moves the artifacts, removes the directory, cancels what a newer push superseded,
fails what ran past its timeout and prunes what is older than the retention — all of it under one
lock, all of it behind the dry-run guard, and none of it wired to anything yet.

The transport and the pass land together because they must: the spec's `OneRun` fixture — this
Task's own acceptance, byte for byte — drives every one of them through `ci_vm.vm_pass`, so a
Task that stopped at `push_sha` would have no way to run its own fences.

Read **PD4** (the `ever_red` key and why the pass never re-dispatches over a concluded row),
**PD10** (`vm_pass` has no `Lane`), **PD11** (the lazy `lane` import for `red_log_lines`) and
**PD12** (no `/tmp`, no `mktemp`) before starting.

**Files**

- `asf/ci_vm.py`
  - §2 — `ssh_argv`, `run_ssh`, `push_sha`, and the three script constants `REMOTE_START`,
    `REMOTE_POLL`, `REMOTE_CANCEL` plus the inlined cleanup and prune scripts, each a `sh`
    program with `{}` slots filled by `shlex.quote`
  - §3 — `STORE_FILE`, `RUNNING`/`PASSED`/`FAILED`/`TIMEOUT`/`CANCELLED`, `RED_STATES`,
    `BUCKETS`, `load`, `save`, `rows_at`, `in_flight`
  - PD10 — `heads`, `dispatch_targets`, and `GREEN_TRUNK_LIMIT`/`trunk_shas` (PD3: the reader
    lands here with its siblings; its only caller arrives in Task 4)
  - §5 — `_MUTATING`, `vm_pass` and the five step functions it calls in order (`collect`,
    `supersede`, `time_out`, `dispatch`, `prune`)
- `tests/test_ci_vm.py` — `class FakeSsh` (the fixture) and `class OneRun(FakeSsh)`, the spec's
  §*One run, end to end, on a fake host* in full

**Steps**

1. The fixture first, because every assertion in this Task is about what a real `sh` actually
   did: a temp directory as the "machine", a `sh` script put on `PATH` as `ssh` that strips the
   flags and the target off its own argv and runs the remaining stdin script against that
   directory, a real git repo with one commit, and a real bare repo reached over `file://`. No
   network, no real ssh, no mock of the scripts — `REMOTE_START`, `REMOTE_POLL` and
   `REMOTE_CANCEL` are executed.
2. `ssh_argv(host, timeout_s)` — the exact five options and no more (C3): `BatchMode=yes`,
   `StrictHostKeyChecking=accept-new`, `ConnectTimeout=<n>`, the target, `sh -s`. No `-i`, no
   `-p`, no user, no `ProxyJump`: that is the operator's `~/.ssh/config` and re-expressing a
   subset of it here is the second configuration language C3 refuses.
3. `run_ssh(host, script, kind='read', timeout_s=None, run=subprocess.run)` — the script on
   **stdin**, never argv. `kind` other than `'read'` is a write: `if kind in _MUTATING and
   mutation_guard.is_active()` prints `would_line('ssh', …)` and returns `(1, '', line)` **before
   any process starts** (C17). Never raises: `OSError` and `TimeoutExpired` are
   `(124, '', <why>)`. `_MUTATING = ('start', 'cancel', 'cleanup', 'prune')` lives here, not in
   `mutation_guard` (C17's own argument: there is no ssh argv to inspect).
4. `push_sha` — `git push --force <ssh://…/repo.git> <sha>:refs/asf/<run_id>` from
   `product.repo_dir` (C5). A write: refused under a dry run, through the same guard, with the
   same line shape. `(True, '')` / `(False, why)`.
