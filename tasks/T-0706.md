## Description
stories: S-37754
writes: asf/approvals.py, asf/harvest/deploy.py, tests/test_enduser.py
after: Task 4

The spec's `## The design` §5: two new `ActionClass` entries, one arm in `merge_class`, and the
deploy pass asking the second one.

`precheck` needs **no edit**. Everything it does with an approvals class is already written
(`asf/harvest/lane.py:2485-2506`, P12, re-read at this branch point): the class lookup, the level
lookup, the `is_granted` check, the `dropped` path, the `ask`, the `wait(..., 'held')` line and the
release under `merge: auto`. One new arm in `merge_class` is the whole landing half. That is why
`asf/harvest/lane.py` is not in this Task's `writes:`.

**Files**

- `asf/approvals.py` — the two `ActionClass` entries in `CLASSES` (beside `merge_amendable_set` at
  `:108-113`); `merge_class`'s new arm (`:555-567`); the two recogniser lines in the printed matrix
  (`:1296-1303`).
- `asf/harvest/deploy.py` — the `deploy_legal_content` ask in the deploy pass, after
  `enduser_refusal` and before dispatch.
- `tests/test_enduser.py` — `class LegalApproval`.

**Steps**

1. Both classes: `default='human-now'`, `read_by=('harvest',)`, `operator=True`, `grantable=True`,
   `parks=True` — the table in §5, and `parks=True` for the reason the comment at `:47-51` gives: a
   branch held on a merge class waits to land either way, and relaunching its session buys the same
   refusal and spends a slot. `covers` is one line each, as §5 writes it.
2. `merge_class` gains its arm **before** the amendable-set loop (D9): when `enduser.legal(product,
   files)` is non-empty, return `('merge_legal_content', <the first matched file>)`. The existing
   `amendable.excluded` skip and the amendable loop are unchanged below it. `merge_class` returns the
   first match, so the order *is* the decision — `LegalApproval` asserts it with a file in both sets.
3. The deploy side asks from the deploy pass, after the uncovered-landing check passes and before
   dispatch: when the `deployed..candidate` window carries a legal-path landing, ask
   `deploy_legal_content` for that **sha** and print one held line instead of dispatching. The hold
   key is `<sha>/deploy_legal_content`, not the item — a signature on legal text is about the text,
   and the thing being shipped is a sha (§5, `## Records`). The window is the walk Task 4 lifted;
   this Task adds no third walk.
4. Both classes appear in `asf approvals`' printed matrix with their recognisers, as
   `merge_amendable_set` and `merge_routine_pr` do (`:1302-1303`).
5. `LegalApproval` — `merge_class` returns `merge_legal_content` for a legal-path branch, and
   returns it **before** `merge_amendable_set` for a branch whose files reach both (D9); `precheck`
   holds such a branch with the `held <branch>: merge_legal_content (human-now) — <file>` line and
   `asf approvals resolve <item>/merge_legal_content granted` releases it; `deploy_legal_content`
   holds the dispatch, is keyed by sha, and is released separately from the merge class (D8 — grant
   one, assert the other still holds); with both classes mapped to `auto`, nothing is held at either
   place; a branch with legal paths and the enduser gate **off** still takes the merge signature,
   because `legal_paths` is a convention and the signature is not the gate.
