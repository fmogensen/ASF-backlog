**Steps**

1. `host.install` keeps every refusal it has — the scheduler's launchd refusal at `:367-370`, the
   shadow preflight at `:383-384`, the tick lock at `:389-393` — each still leaving both plists
   and both loaded jobs exactly as they were, and returning 1.
2. Inside the `tick_lock` block it already holds, before overwriting anything: keep each pending
   job's plist as it is on disk now, in memory.
3. After the boot-in, verify over **both** labels from `jobs(product, cfg, python)`, not only the
   pending ones — the 2026-10-10 incident was both jobs down at once. Any label not loaded makes
   `install` print the labels and roll back: restore every kept plist and bootstrap it again,
   through `asf.scheduler`'s own `bootstrap`, never a new raw `launchctl` argv (`K11`).
4. `install` returns non-zero when it rolled back, and its last line names the labels that were
   not loaded. A rollback that itself fails prints the exact `launchctl bootstrap` command for
   each label still down, the way a `NEEDS OPERATOR` line would.
5. `prune_venvs` moves behind the success condition: it still runs after an install where both
   labels are loaded, and never after a rollback (`K15`).
6. A dry run writes nothing, boots nothing and checks nothing; an install with nothing pending
   takes no lock and verifies nothing, because the skip at `:378-381` has already read both
   labels loaded.
7. Create `tests/kernel/test_install_rollback.py` with one case per acceptance line, with
   `scheduler._launchd_status`, `scheduler.install` and `scheduler.bootstrap` patched and the
   plists in a temporary LaunchAgents directory — the files and the bootstrap calls both asserted
   for each refusal path.
