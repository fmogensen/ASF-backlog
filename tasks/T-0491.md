## Description
stories: S-34251, S-34252
writes: asf/product_config.py, tests/test_product_config.py, tests/test_install.py
after: Task 2

The spec's `## The design` §The rewriter, its §`asf config migrate`, its parked-block example and its
§Registration's `migrate` half. This is the only Task in the card that writes an operator's file, and
every one of its three refusals leaves that file exactly as it was.

**Files**

- `asf/product_config.py` — `blocks`, `rewrite`, `effect`, `cmd_config_migrate`, and the `migrate`
  subparser inside the existing `register`
- `tests/test_product_config.py` — `CheckNamesEveryKeyAndItsHome` extended where migration is
  visible, and `MigrateRewritesTheRenames`, `MigrateParksWhatHasNoHome`, `MigrateIsIdempotent`,
  `MigrateNeverDropsAKeyAndNeverChangesAValueAlreadyRead`, `MigrateLeavesAHandDecisionAlone`
- `tests/test_install.py` — one `argv → handler` row for `config migrate`

**Steps**

1. `blocks(text)` → `[(dotted key, first line, last line, indent)]` for every key line, with the
   comment lines directly above a key counted as part of its block: a comment is the operator's note
   on the key it sits over, and a move that left it behind would strand it (D3).
2. `rewrite(text, now=None)` → `(new_text, [(Finding, what was done)])`. A line-based splice: every
   byte it does not move is unchanged (D3, P11 — there is no dumper in the tree and a round trip
   would drop every comment). A rename whose target sits in another section moves the block there,
   re-indented, creating the section when absent; `conventions.harvest_gate` →
   `conventions.harvest.gate` therefore creates a two-level block.
3. Parking: an unknown key's block moves under `x-unmapped:` — appended when absent, with the spec's
   two header comment lines — behind one comment line naming the key and why it is there. The
   appended block is byte for byte the spec's example.
4. `effect(data)` — every `env.Product` property (18 today) plus the fields of the `Conventions` it
   builds, derived from `Product`'s own properties so a new one is covered with no edit here.
   `Product` never validates (P19), so this is computable for the file before the migration as well
   as after.
5. The three refusals, each raising `env.ConfigError` and leaving the caller with the original text
   (D11): the new text does not `env.validate_product_text` clean; a leaf value of the old text is
   not in the new one under its old dotted key or its new; `effect(old)` is not a subset of
   `effect(new)`. The subset direction is the point — a migration may make an ignored key start being
   read, never change a value already read.
6. Skipped, never guessed, with the rest of the file still migrated (D7): a rename whose target is
   already set, a duplicate key, a wrong shape.
7. `cmd_config_migrate` — the spec's table and its closing line. The backup is
   `<file>.bak.<UTC stamp>`, written **only** when something changed (D12), never overwritten. A
   second run writes no file and no backup and prints one line, no table. Exit 1 while a hand edit is
   owed, 0 once the file loads.
8. `register`: the `migrate` parser with `env.add_product_arg` and `set_defaults(run=cmd_config_migrate)`.
   No `--apply` and no `--all` (the spec's Out).
9. `MigrateRewritesTheRenames`: the rename lands in its section, the section is created when absent,
   and the value is read back through `Product` afterwards.
10. `MigrateParksWhatHasNoHome`: a homeless scalar, a homeless block list and a homeless nested map;
    the file then loads through `env.load_product`; every parked value is still in it, with the
    comments that sat above each key, behind the comment naming why.
11. `MigrateIsIdempotent`: two runs; the first writes a backup and changes the file, the second
    writes neither — asserted on the filesystem (mtime, and no second `.bak.*`), not on the output
    (D12).
12. `MigrateNeverDropsAKeyAndNeverChangesAValueAlreadyRead`: each of the three refusals leaves the
    file and its back
