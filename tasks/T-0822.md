The spec's §5's second half, and the whole point of the card: the precedent a session cited becomes
precedent itself. `HISTORY_RULING_RE`'s text group is open-ended (P12, re-measured), so a clause
appended to the ruling's own line is still parsed, still reaches `rulings.standing`, and from there
reaches every later review, correct, fixer and adjudicate brief through `rulings.brief_section` —
which is the asymmetry this spec exists to close. The adjudicator was the one role that wrote
precedent and read none.

Read **PD6** (the `result` local the spec's snippet names and `file_rulings` does not have) before
starting.

One write, the one `file_rulings` already makes: no second History line, no new card field, no new
record writer, no new event, no new metric (C13, C15). A run with a precedent claim and **no
ruling** writes nothing at all (C14) — it is already marked `adjudicated: none` and named once, and
a History line saying only "it looked at D-0002" records a search, not a decision, which
`rulings.standing` would hand to the next reviewer as binding.

**Files**

- `asf/tick/step_health.py` — `result` bound in `file_rulings` (`:122-160`, PD6), the clause
  appended to the `## History` line it already writes, and the `else` branch's `why` naming a
  missing precedent when the run declared a question
- `tests/test_tick_steps.py` — the spec's two `f0262` cases

**Steps**

1. PD6's split: `result = rec.get('result') if isinstance(rec, dict) else ''` then
   `text = report_mod.ruling(result)`. One line becomes two, no behaviour change.
2. The line `file_rulings` already writes gains one term:
   `line = f'- {stamp} adjudicate ({job}): {" ".join(text.split())}{precedent.history_note(result)}'`,
   inside the same single read-modify-write of the same file. Import `precedent` function-locally
   beside that function's existing function-local imports (`from asf.record.core import TYPES`,
   `from asf.record import frontmatter`, …) — this module imports its readers where it uses them.
3. The `else` branch's `why`, for the one case the spec names: when there is no ruling **and** the
   run declared a question (`report_mod.needs_input(result)`) **and** `precedent.claim(result)` is
   empty, it reads `no ruling in its report (and no precedent line)` — so the tick's existing
   `ruling <job>: <why> — marked, not filed` line names the gap once. Every other `why` is
   unchanged: a run with no ruling that asked nothing still reads `no ruling in its report`, and a
   run with a ruling and no card still reads `no card for <item> in the record`.
4. The spec's two cases, both extensions of the landed `test_b0064_an_adjudicate_runs_ruling_is_filed_on_the_card_by_the_factory`
   fixture (`tests/test_tick_steps.py:254`) — the same session, the same log, the same card, with
   one more REPORT line. The first asserts the `[precedent: …]` clause is on the card **and** that
   `rulings.parse(body)[-1]['text']` still carries it, which is P12's fence and the reason the
   clause goes on this line rather than a new one. The second is C14: a report with
   `precedent: D-0004` and no `ruling:` leaves `'precedent'` out of the card entirely and marks the
   run `adjudicated: none`.
5. Nothing else in `step_health.py` moves. `file_rulings`' guard (`kind == 'adjudicate'`, `ended`,
   not already `adjudicated`), its `ctx.event('ruling', …)`, its `adjudicated=stamp` update and its
   return value are what they are today, and the "filed once" assertion of the landed case must
   stay green: a second pass finds nothing and the card gains no second line.
