## Description
stories: S-36854
writes: asf/views/prod.py, tests/test_prod_view.py
after: Task 1

The spec's §6. When this lands, the table that has been headed **ON PROD — check these** since it
was written finally says which of those rows has been checked — and its empty case,
`(no unticked customer-visible change on prod)`, becomes a true statement for the first time
(PD10). It needs `checked.read` and `checked.matches` and nothing else of this Feature's, so it runs
in wave 2 beside Task 2 with disjoint `writes:`.

Read **PD8** (`_customer_rows` has to return the landing sha, and why the `✓` cannot be computed
without it), **PD9** (the cell is prod-only) and **PD10** (what the placeholder's condition becomes,
and that the rows still render under it) before starting.

**Files**

- `asf/views/prod.py` — `_customer_rows`' and `_check_rows`' return shapes; `render`'s header,
  placeholder and row loop.
- `tests/test_prod_view.py` — **new class** `TheTickColumn`.

**Steps**

1. `asf/views/prod.py`: `from asf.evidence import checked` — a local import inside `_check_rows`, as
   `render` already imports `asf.harvest.deploy` locally (`:220`), so the view module gains no
   import-time dependency on the evidence package.
2. `_customer_rows` returns `(what, n, sha)` per row — the `sha` `_landings` already yielded and the
   function already has in hand (PD8). Both callers are inside `_check_rows` (`:184`, `:191`).
3. `_check_rows` reads `ticked = checked.read(product)` once, before the target loop, and returns
   `(name, what, state, n, tick)` where `tick` is:
   - `''` for a `NOT LIVE` row and for the `… and N more` row — there is nothing on prod to check
     yet, and the spec says the cell is blank;
   - `''` for any row whose `name` is not `'prod'` (PD9);
   - `'✓'` when `checked.matches(ticked, n, sha)`;
   - `'needs your ✓'` otherwise.
   Extend the docstring by one clause naming the fifth field.
4. `render`: the header becomes `| Target | What | State | PR | ✓ |` and its rule row `|---|---|---|---|---|`
   (`:236-237`). The placeholder becomes a five-cell row and its condition becomes
   `if not any(tick == NEEDS for …rows)` rather than `if not rows` (PD10) — the rows still render
   below it. The row loop appends the fifth cell. Name `'needs your ✓'` as a module constant beside
   `NOT_LIVE_ROWS` so the writer and the test read the same string.
5. Nothing else in `asf/views/prod.py` changes: `_landings`, `_title`, `_strip_prefix`,
   `_is_customer`, `_changed`, `_legacy_kinds`, `_deploy_sha`, the head line, the per-environment
   `view_line` block and `cmd_prod` are all untouched. The `deploy_sha: none` early return (`:210`)
   is untouched, so a product that configures no deploy renders exactly as it does today.
6. `tests/test_prod_view.py` `TheTickColumn`: a live row whose PR is in the list renders `✓`; one
   that is not renders `needs your ✓`; a live row whose PR number is None but whose landing sha is
   ticked renders `✓` (D4, the case PD8 exists for); a `NOT LIVE` row's cell is blank even when its
   PR is ticked; a named target's live row's cell is blank even when its PR is ticked (PD9); with
   every live customer-visible landing ticked the table renders
   `(no unticked customer-visible change on prod)` **and still lists the ticked rows** (PD10); with
   one unticked it does not render the placeholder; and a product with `deploy_sha: none` renders
   byte-for-byte what it does today. `GithubDeploymentsProvider`, `ProdCustomerPathsList` and
   `PerTargetGap` (`:45`, `:62`, `:78`) must stay green untouched — they assert on the table's rows,
   and a fifth cell that broke them means step 4 changed a row it should not have.
