## Description
stories: S-73206
writes: asf/reviews.py, asf/briefs/build.py, asf/briefs/templates/review.md, tests/test_doc_lane_review.py
after: Task 2

The spec's §4. The template's hardcoded six-row table becomes one `{checklist}` placeholder and
its reading order one `{review_reads}` line; the builder fills both from the row. The evidence
hints move out of the template and into `asf.reviews.EVIDENCE`, because the template can no longer
hold them once the table is chosen per branch (C12), and because `asf.reviews` is already the only
module that knows what a checklist is.

**Files**

- `asf/reviews.py` — `EVIDENCE`; `render_table(rows, evidence=None)`.
- `asf/briefs/templates/review.md` — the table replaced by `{checklist}`, the reading order's tail
  replaced by `{review_reads}`.
- `asf/briefs/build.py` — the two new context keys.
- `tests/test_doc_lane_review.py` — `TheReviewBriefOfADocumentBranch`, beside Tasks 1 and 2's.

**Steps**

1. `EVIDENCE` in `asf/reviews.py`, with the spec's §2 comment: what the evidence cell of each
   check asks for, keyed by normalized check name. The six code hints are copied from the live
   `asf/briefs/templates/review.md` table — `the file, or the one outside it`,
   `the step → the code`, `file:line`, `the run's last line`, `each command's last line`,
   `what you looked at` — so a Task's brief renders byte-identically to today's. Entries for every
   name in `CHECKLIST`: all three kinds, both tuples, twenty-one names (**PD9**). A name with no
   entry renders an empty cell.
2. `render_table(rows, evidence=None)` puts `(evidence or {}).get(normalize(name), '')` in the
   third cell. Called with no `evidence` it renders exactly what it renders today — the empty
   third cell — which is S-73206's fourth acceptance line and keeps `tests/test_reviews.py:137`
   green unchanged. The escaped `<pass\|fail>` cell is untouched.
3. `asf/briefs/templates/review.md`: the six table rows and the header above them become
   `{checklist}{delivery_checks}`, with the spec's §4 wording for the paragraph above it kept word
   for word; `then the plan `{plan_path}` for the Task it claims to deliver.` becomes
   `then {review_reads}.`. Nothing else in the template moves — not the verdict block, not the
   round, not `{review_path}`, not the never-touch-the-branch rule.
4. `asf/briefs/build.py` adds two keys to the one flat context dict:
   - `checklist` — `reviews.render_table(reviews.required(*kinds), reviews.EVIDENCE)`, where
     `kinds` is `getattr(row, 'review_kinds', ()) or ('code',)`. The `or ('code',)` covers every
     row kind that is not a `PUSHED → REVIEW` and every ledger line written before Task 2.
   - `review_reads` — ``the plan `{plan_path}` for the Task it claims to deliver`` for a Task or a
     Bug; for a Feature, the document its branch carries, read from
     `preamble_mod.conventions(product).branch_kind(row.branch)` (**PD11**): the spec on a `spec`
     branch, the plan on a `plan` branch, both on a `direct` branch, and the Task wording for
     anything else, including a branch under no known prefix.
5. `delivery_checks` is not touched: it still renders right after the table's last row and carries
   its own leading blank line, which is S-73206's sixth acceptance line. Its own prose says "the
   six checks above"; a delivery branch delivers two or more items and is always a code branch
   (the spec's `## Out`), so that sentence stays true and is left alone.
6. Write `TheReviewBriefOfADocumentBranch` to the six acceptance lines of S-73206, one case each:
   a Task's `PUSHED → REVIEW` brief rendering the same six rows with the same hints as today; a
   Feature's `spec/F-0280` row of class `code` rendering eleven rows — the five spec checks then
   the six code checks — each with its hint and the escaped `<pass\|fail>` cell; the reading order
   naming `docs/specs/f-0280.md` rather than the Task's plan, with the `plan/` and direct variants;
   `render_table` with no `evidence`; `EVIDENCE` covering ever
