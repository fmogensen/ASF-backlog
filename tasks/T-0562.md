set, from the product the groom step already holds (P10, D6). Footprint-disjoint from Task 2 on
purpose (PD1), so it runs beside it.

**Files**

- `asf/groom/shape.py` — `merge_proposals(ready, declined=None, shared=())`: the component walk's
  `footprint.overlaps(cur.writes, other.writes, shared)` (`:248`) and the `hit` that writes the
  reason (`:260`). `split_proposals(ready, active, depth, declined=None, shared=())`: the holder
  test (`:306`). `shared` is the **last** parameter of each, after `declined`, because both are
  called positionally up to `declined` from `groom.py:869-871`. `batch_proposals` is untouched: it
  reads `len(writes)`, never an overlap.
- `asf/groom/groom.py` — `groom_shape_sections(..., shared=())` and
  `build_groom_sections(..., shared=())`, passed to the two proposal calls; the one caller with a
  product (`:1202`) passes `footprint.shared_globs(product)`. The other three callers are tests and
  keep the default, which is today's behaviour.
- `tests/test_groom_shape.py` — `class SharedPathProposalTests(ShapeRepo)` beside
  `MergeProposalTest` and `SplitProposalTest`.

**Steps**

1. The three calls and the two signatures. Nothing else in `shape.py` moves — in particular
   `areas`, `ready_tasks` and `active_tasks` are untouched, and `asf/record/check.py`'s import of
   this module (it reads `shape` for the record's own checks, never the proposals) is unaffected.
2. `SharedPathProposalTests`, the Story's fence exactly:
   - two ready Tasks of one Feature writing `[src/a.py, uv.lock]` and `[src/b.py, uv.lock]` with
     `shared=['uv.lock']` → `merge_proposals` returns `[]`; with no set it returns the proposal it
     returns today, and its `why` carries `uv.lock ↔ uv.lock` — so the test shows what stopped;
   - the same two Tasks both writing `src/a.py` → the merge proposal is still made with the set
     declared: only the shared glob is exempt;
   - `split_proposals`: an area whose only overlap with a holder is the lockfile counts as free, so
     no split is proposed for it — and an area that genuinely overlaps a holder still is;
   - one row through `build_groom_sections(..., shared=['uv.lock'])` so the threading is proved, not
     only the pure function.
