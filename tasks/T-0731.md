The spec's §4 and §5. After this Task the operator asks one product's orchestrator a question and
reads its answer back: `asf center ask <product> "<question>"` appends `asked` to that product's
mailbox, runs that product's own `center.deliver` template and records `delivered` or
`undeliverable` with the failure's first line, `--wait` prints the reply when it lands and exits 1
with the id, the age and the orchestrator's last-seen when it does not; `asf mail` lists a
product's unanswered questions oldest first and stamps `center/orchestrator.json` as it reads, so
the heartbeat is the act of looking; and `center.inbound` decides what a product does with a
question, with `off` refused at the *asking* end, naming the key.

Nothing here is ever dropped. C11 is the spec's own list of the five ways it could be, and each is
refused by name: a timeout exits 1 and never 0, a failed `deliver` leaves the thread `open`, no
question expires, and only `asf mail reply` or an explicit `asf center thread --drop <id>` closes
one.

Read **PD8** (the question file is a fourth path under `center/`, and the product Task 6's fenced
set is measured against must name no `deliver`), **PD9** (which function reports an unknown key
under `center:`), **PD11** (the id is re-minted while it collides) and **PD12** (no `.claude/`
anywhere in the example or a docstring).
