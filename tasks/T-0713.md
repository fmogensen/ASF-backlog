The spec's §8 and §9 (C16). After this Task a product may set `ci.post_status` and a PR page shows
the verdict ASF decided — written once per conclusion, never read back by anything — and an
operator switching a product to `vm` has a page that tells them what a machine needs, what one run
does on it, and the three lines of yaml that make the switch.

It lands last because the guide describes everything the five Tasks before it built, and a guide
written against code that has not landed is a guide that will be wrong in exactly the places
nobody checks.

**Files**

- `asf/ci_vm.py` — `post_status(product, sha, job, state, run=None)` (§8) and its one call in the
  pass's **collect** step, guarded by `ci.post_status`
- `docs/products.example.yaml` — the `ci.provider: vm` block of the spec's §1, **commented**,
  beside the existing `pool:` (`:225-235`); the `provider:` comment line (`:211`) grows `| vm`;
  `capacity.ci`'s comment (`:239-241`) notes that `ci.hosts` slots are the other slot sum it
  overrides
- `docs/guide/ci-vm.md` — new
- `docs/guide/ci-runner-pool.md` — one sentence at the top saying it is the `github-actions`
  provider's page, pointing at the new one

**Steps**

1. `post_status` — one `gh api -X POST repos/<slug>/statuses/<sha>` with `state`
   (`success`/`failure`/`pending`), `context: asf/<job>` and a one-line description, **through
   `asf.harvest.harvest._gh`** so the dry-run backstop refuses it with no new predicate (P14 —
   `is_mutating_gh` already covers `api -X POST`). Lazy import, PD11. `False` on any failure and
   never raises: *"a PR badge that did not post is never a reason to hold a branch"*.
2. Its one call site: the pass's collect step, per conclusion, only when `ci.post_status` is
   truthy. Off by default (C16). Nothing anywhere reads a status back — the `Wiring` case asserts
   that by `grep` over `asf/` for `statuses/` finding only the writer, so do not add a reader,
   not even a doctor row.
3. The example block, commented. Commented is not decoration: an uncommented vm block in a file
   whose `provider:` is `gh-actions` would be validated by the delegation Task 1 added, and
   `tests/test_env.py:283-285` asserts the example produces no problems.
4. `docs/guide/ci-vm.md` — the spec's §9 list, in its order: what a host needs (`sh`, `git`, ssh
   access) and **what it does not** (a code-host credential — C5's whole argument, and the one
   sentence an operator most needs to read before opening a firewall); the two config blocks; what
   one run does on the machine and where it leaves things (`repo.git`, `runs/<run_id>/`,
   `artifacts/<sha12>/<job>/`, and that nothing is written outside `<root>`); how a result becomes
   a check (the store is the judge, and a required job with no row is `pending`, never green);
   the `ci-vm` clock; the doctor rows; and the switch from `github-actions` in three lines of
   yaml. Two sentences this plan adds to that list because nothing else carries them:
   **`deploy_sha.prod.required_jobs` on a vm product must name `ci.jobs` names**, or the gate waits
   forever on a name no job answers (PD7 — the doctor says so for the static half and cannot for
   the dynamic half); and **what the Capacity row counts under `vm`** is dispatched-not-concluded
   jobs, not workflow runs (PD6 — `views/status.py`'s own docstring still says the gh-actions
   sentence and is out of this card's footprint).
5. The one sentence on `docs/guide/ci-runner-pool.md`.
6. `Wiring`'s `post_status` cases.
