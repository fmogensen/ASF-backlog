after: Task 3

§2.4 and §2.5. Both are registered in `asf/cli.py`, which is why they are one Task and why they
wait on Task 3 rather than on Task 2. Neither has a `--fix` (D6) and neither writes anything
(§4).

**Files**

- `asf/views/health.py` — new: `render(root, product)`, `cmd_health`
- `asf/views/performance.py` — new: `render(product, days)`, `as_json(product, days)`, `cmd_performance`
- `asf/cli.py` — `health` into the `resolve_record` group (`:533`), `performance` beside
  `capacity` (PD12); two `sub.add_parser` calls with their `help=` strings (which become the two
  skills' descriptions in Task 7)
- `tests/test_views_health.py`, `tests/test_views_performance.py` — new

**Steps**

1. `asf/views/health.py` `render(root, product)`: one `| What | State | Detail |` table under
   `header.head('health', product.name, <clause>)`, seven rows in §2.4's order — sessions,
   stalls, worktrees, retention, invariants, drift, roles.
2. Each reader is called at `fix=False` and with the accessor it actually has (PD11):
   `health.health(product, fix=False, out=collect)`, `stall.stall(product, out=collect)`,
   `retention.sweep(product, fix=False, out=collect)` and
   `check.invariant_findings(root, product, deep=False, out=collect)` take `out=<a list's
   append>`; `worktrees.dry_run(product)`, `drift.check(product)` (formatted by `drift.line`) and
   `roles.load_all()` + `roles.validate` are read by return value.
3. What makes each row not-green is §2.4's table, copied: any `ended`/`re-judged` transition this
   call would record and any `failed: not pushed`; one line per `STALL` or `DEAD`; orphans and
   what the reaper would remove; what retention would sweep; one line per violation as
   `I<n>: <subject>`; the installed commit behind the trunk; and for roles,
   `12 valid, 16 kinds bound` green, one line per problem otherwise (the counts read from
   `roles.load_all()` and `roles.BINDINGS`, not retyped).
4. A raising reader leaves the table: its row reads `? (ValueError: boom)` and every other row is
   still drawn — the shape `tests/test_views.py` already holds `status` to. The exception is
   caught per row, not per table.
5. `cmd_health` returns 1 when any row is not green and 0 otherwise — the shape `doctor` and
   `rules check` use, so a clock can call it. The stamp still prints on the 1 (PD14). There is no
   `--fix` argument, so `asf health --fix` is an argparse error (D6).
6. `asf/views/performance.py` `render(product, days)`:
   `runs = measure.ended_runs(product, since=<days ago, ISO>, as_of=<now, ISO>)` then
   `t = measure.table(runs)`, and three tables under
   `header.head('performance', product.name, f'last {days} d')` — the scalars (`sessions`,
   `hours`, `usd`, `landed_sessions`, `landed_items`, `non_landing_share` rendered as a
   percentage, `minutes_per_landed_item`, `usd_per_landed_item`), `by_kind` and `by_model` as
   `| kind | sessions | hours | usd |`, and the `repeat_items` block — its count, its items, and
   its `usd_share` and `hours_share`.
7. `--days` defaults to `product.improve.get('window_days')` (`asf/env.py:761`) and then to 7.
   `--json` prints `measure.table(runs)`'s dict as it stands (D7); `record_usd` is not passed, so
   the key is `None` (§1.3). A product with no session ledger — `pool.sessions_path(product)`
   absent, the guard `asf/metrics/metrics.py:722` already makes — prints one line naming the path
   and exits 0.
8. `tests/test_views_health.py`, §3.4: over a ledger with one live session whose pid is dead, one
   finished session whose branch is not pushed, one orphan worktree, one invariant violation and
   a role file over `MAX_LINES`, all seven rows are not-green, each names its finding, and the
   command exits 1. The proof that it wrote nothing: a recursive hash of `sessions.jsonl`, the
   state dir and the record is identical befor
