§2.7, and nothing else. This Task knows nothing about credentials: it adds one typed field to a
rule card and teaches the Bug filer that a violation can be somebody else's problem. Every test
below uses a fixture rule card whose check script the test writes, and it is the generic change
D7 argues for — the next rule of this class needs no code at all.

**Files**

- `asf/record/new.py` — `SETTABLE['rule'] |= {'owner'}` at `:20`, so `asf new rule` and
  `asf set R-nnnn owner=operator` both write the field through the parser.
- `asf/rules/rules.py`:
  - `OWNERS = ('factory', 'operator')` and `DEFAULT_OWNER = 'factory'` beside `TIMEOUT`.
  - `owner_of(rule)` → the card's `owner`, lower-cased and stripped, when it is in `OWNERS`, else
    `DEFAULT_OWNER`. `load_rules` carries the raw field through from the index as it carries every
    other key (it already does `dict(entry)` at `:97`), so nothing changes there; `owner_of` is
    the one reader, and an unrecognised value is read as `factory` — a typo makes the rule
    factory-owned and its violation files a Bug exactly as today, so nothing is silenced (PD11).
  - `unknown_owners(rules)` → `[(rule id, the raw value)]` for every card whose `owner:` is set
    and not in `OWNERS`.
  - `cmd_check`: build `owners = {r['id']: owner_of(r) for r in rules}` once, then
    - `--json` violations gain `"owner": owners.get(rule_of(l), DEFAULT_OWNER)` (PD5), and the
      payload gains `"owner_unknown": [{"rule", "value"}]` from `unknown_owners`;
    - the `== RULES` summary gains `, <k> operator` when any violated rule is operator-owned,
      appended after the existing `, <n> unenforced` and before `broken_part`;
    - a violation line whose rule is operator-owned prints with a `NEEDS OPERATOR: ` prefix — at
      print time only, never in the `line` field (PD6);
    - each `unknown_owners` entry prints
      `<rule> owner: <value!r> is not one of ('factory', 'operator') — read as factory` after the
      violations. Exit code unchanged by any of this.
- `asf/tick/file_bugs.py`:
  - `rule_violation_signatures` skips a violation whose `owner` is `operator`: no signature, no
    Bug, no bump. The owner is read from the violation dict first and from the card in the
    `rules_idx` it already builds (`:170-176`) as a fallback, so a caller that passed `data=` from
    an older payload still behaves.
  - `report_operator_rules(violations, ledger, day, out=print)` — **new**, beside
    `report_check_failures` and in the same shape. For each operator-owned rule in `violations`,
    one line per rule per UTC `day`:
    `NEEDS OPERATOR: <the rule's first violation line>`, with any further lines of that rule
    printed after it, one per line, unprefixed. Keyed in
    `ledger['operator'][rule] = {'since', 'last', 'day', 'lines'}` in the existing
    `rule-check-failures.json`; a rule whose `day` is already this day prints nothing; a rule that
    is clean this run has its entry dropped, so the next failure raises the line again. Mutates
    and returns `ledger['operator']`. Takes violations in the `--json` shape
    (`[{rule, line, owner}]`) so Task 4 can call it with lines it built itself (PD10).
  - `cmd_file_bugs` calls it beside `report_check_failures` at `:518-520`, before
    `_write_ledger`, guarded by the same `if rule_data is not None`.
- `tests/test_rules.py` — new `OwnerTest`:
  `test_owner_operator_is_carried_into_json` (an `owner: operator` card whose check exits 1;

  `NEEDS OPERATOR: `), plus `test_an_unrecognised_owner_is_read_as_factory_and_reported`.
