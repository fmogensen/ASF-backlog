stories: S-76255

after: Task 1, Task 4

The spec's §2. It needs Task 1's `pin_required` parameter on `stale_own_hook` and Task 4's
`which_asf()` — measured, neither `verify` nor `check_redaction_hooks` resolves an `asf_path` of
its own at this head (**PD1**). No new doctor row and no change to `cli dispatcher` (P10): this
Task only widens `redaction hooks` to the hook's body.

**Files**

- `asf/hooks.py` — `verify` (`:750`): one `asf_path` from `which_asf()`, and one problem line per
  hook whose text is asf's but whose `stale_own_hook(...)` is not None.
- `asf/doctor.py` — `check_redaction_hooks` (`:1088`): the same test, between its `foreign` test
  and its `hook_entry` test, and the `--approve` half of the remedy.
- `tests/test_doctor_pin.py` — the stale-body arms, the remedy's two wordings, and the four
  `check_cli_dispatcher` verdicts asserted unmoved.

**Steps**

1. `verify`: resolve `asf_path, _ = runnable_asf(which_asf())` once, before the repo loop, and add
   after the existing `hook_entry` test — for a pinned product, for a hook that is asf's — one
   line when `stale_own_hook(text, name, asf_path, product.name, pin_required)` is not None:

   ```
   <path> is an older body than this build writes — it does not check that the asf it runs is the pin
   ```

   Every line `verify` emits today is unmoved: `is not a git repo`, `missing`, `is not asf's`,
   `execs <entry>, not the dispatcher — it does not run the pin of <p>`, and
   `falls back to asf on PATH`. `pin_required` here is the `pinned` local `verify` already has.
2. `check_redaction_hooks`: the same line, placed **between** the `foreign` test and the
   `hook_entry` test, with `asf_path` read the same way. A host with no dispatcher reports the
   dispatcher problem, not a body problem it cannot fix — that falls out of `which_asf` returning
   `shutil.which`'s answer there, so `stale_own_hook` compares against the shared install's path
   and the `hook_entry` line fires first on the ordering the spec gives (P9, P10).
3. The remedy: the detail already ends `— asf hooks install --product <p>`; append ` --approve`
   when the row for that path is withheld, read the way `cmd_hooks --dry-run` reads it —
   `gated(product, plan(product, which=which_asf()))` — and not otherwise (P8).
4. `tests/test_doctor_pin.py`, over `PinFixture` (`:85`): `hooks.verify` names a hook whose text is
   asf's older body while the product is pinned, and stops naming it once the hook is rewritten;
   `doctor.check_redaction_hooks` is red for that same hook — **the one case that is green today**,
   reproduced here before the fix: measured at `9a3a897d6`, a pinned product whose `pre-commit`
   names the dispatcher with an older body gives `verify() == []` and
   `check_redaction_hooks() == (True, 'pre-commit, pre-push in 1 repos')`. Reproduce exactly that,
   then assert the new red.
5. The remedy's two wordings: `--approve` when the hook's path is tracked and the matrix withholds
   it, and not when it is not. Measured shapes for the two halves — a `.githooks` directory set as
   `core.hooksPath` gives `is_tracked` True (true even before the first commit: `is_tracked` is
   "in a work tree and not ignored", `asf/hooks.py:411`), `gate_level` `human-now`, `plan`'s action
   `upgrade`, and `gated` withholding that one path; a repo left on the default `.git/hooks` gives
   `is_tracked` **False** — that is the negative case, and it is the only easy one.
6. `doctor.check_cli_dispatcher`'s four existing verdicts are asserted unchanged (its rows do not
   move). No new row, no new label.
