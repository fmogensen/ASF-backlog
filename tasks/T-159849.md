The rest of the spec's design §1: one more input to `decide.breaches`, and no new kind of action
(`D5`). An open PR whose age — `Facts.now` less `opened_at` — passes `config.lead_p90_max` puts its
item in `due`, which is the **first** term of the launch key (`P5`,
`asf/kernel/decide.py:1663-1664`), so its review or fix round launches before anything else; its
place in the merge train is the front; and the tick logs one `LEAD BREACH` line per breached PR in
`Plan.breaches` beside the wait breaches.

**It waits on Task 2 and on nothing else**: `PR.opened_at` is Task 2's field and this Task reads it.
Every lever the breach pulls already exists — *"the breach's only job is to reorder them"* — so a
product with `lead_p90_max` set to `0` must see a plan byte-identical to today's, which is
S-131007's sixth acceptance line and the cheapest proof that nothing new was built.

**Read this Task from `docs/plans/f-0334.md`, not from this card.** The card's prose is cut at 4000
characters (`PC8`). Two decision rows bind it and are on no card: `PC7` (the launch key is
`:1663-1664` and `FINISH_FIRST` `:1625` at `8f237bd`, not the spec's `:1646` and `:1608`) and
`PC12` (`decide.py` is shared with Tasks 4, 5, 8 and 9, and `test_lead_time.py` with Task 2; the
queue serialises them and no `after:` line is added for that).

**Files**

- `asf/kernel/decide.py` — `breaches` (**`:2137`**, not the spec's `:2031`) gains the PR-age input
  and emits one record per breached PR in the shape the function already writes,
  `{'item', 'class', 'age_s', 'action'}` with `action` from `A.describe` — so `Plan.breaches`'
  consumers need no change and the line reads `LEAD BREACH T-0012 PR #41 4.6h > 4h -> review first`.
  The breached item joins `due`, which is built at **`:410`** (`due = overdue(facts, config, states)`)
  and read as the launch key's first term at `:1663`. Put the PR term where `due` is built, not
  inside the key, so the review queue, the fix-round queue and the train all see one set. A
  breached PR that is already conflicting or red is already a fix round and must not be ordered
  twice (S-131007's seventh line): `breaches` already computes `moves` over the tick's progress
  actions (`:2142-2147`) — reuse that, do not add a second guard.
- `tests/kernel/test_lead_time.py` — the `TheLeadBreach` class, on S-131007's command. The module

  is **19** tests at this head — 18 before #1425 added its `DirectMerge` class (`PC10`).
