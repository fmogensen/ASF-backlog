**Steps**

1. `open_pr_action(it, branch, session=None, base='')` (`:1243`) passes `base` through to
   `A.OpenPR(it.id, branch, base, …)` instead of the literal `''`. `ports.open_pr` already honours
   it (`:1796`: `--base base or product.main`), so the whole of the GitHub side is that string
   (`P4`). The two document call sites (`:1933`, `:2030`) are left as they are.
2. In `_judge`, at the one build-lane site that opens a pushed branch's pull request (`:678`), the
   base is the item's own stack while the predecessor has not landed:
   `stack_base(it, facts)` → `stack_of(it)[0]` when that branch still has an unmerged PR on
   `facts.prs`, else `''`. A predecessor already Done has had its branch deleted on merge and its PR
   is merged, so the test is a fact, not a guess, and it needs no `states` — which `_judge` runs
   before. This is `S-135958`'s third line: a stacked item whose predecessor is already Done gets
   its pull request against the trunk.
3. A new `hold_stacked(items, judged, facts, config, actions)` beside `hold_risky`, returning
   `{item: why}` and shaped exactly like it (`P11`):

   ```
   held = {p.number for p in facts.prs
           if not p.merged and p.base and p.base != config.main_branch}
   actions[:] = [a for a in actions
                 if not (isinstance(a, (A.EnableAutoMerge, A.MergePR)) and a.pr in held)]
   ```

   and `judged[iid].behind_pr = None` for each held item, so the merge train never selects it. The
   `why` is `stacked: waits for <base-branch> (<predecessor id>) to land`.
4. Wire it in `decide` immediately after `risky = hold_risky(...)` (`:458`), as
   `stacked_held = hold_stacked(...)`. Add `iid not in stacked_held` to the `due`-loop guard that
   re-arms `behind_pr` (`:477-481`, which today guards only on `risky`), and extend the notes loop
   (`:484-485`) with `stacked_held.items()`. Do **not** put the held items in `queued`: that dict is
   the launch queue's reasons, and a stacked hold is a landing hold, not a launch one.
5. Nothing else changes: the item still reads Landing, a review is still launched once its checks
   are green, a changes-requested verdict still opens a fix round on its own branch, a red check is
   judged as on any other pull request, and the still-needed gate reads it unchanged — because the
   PR's `files` and `change_id` are its diff against **its own base** (`P6`,
   `ports._open_pr:1433`), so they are the Task's own change and the file-overlap and high-risk
   rules see the Task's own paths.
6. Extend `tests/kernel/test_stacked_builds.py` with `class StackedPR`, covering all 13 of
   `S-135958`'s lines: the base on a stacked item's `OpenPR` and the trunk on an unstacked one's and
   on one whose predecessor is Done; `files` as the diff against the base feeding the overlap rule;
   no `EnableAutoMerge` and no `MergePR` for a PR whose base is not the trunk even when it is green,
   approved and clean; the Landing state and the note naming base and predecessor; the hold applied
   to the plan's actions; a review still launched; a changes-requested fix round on the same branch
   with the base unchanged; a red check judged the same; the merge train never selecting it; and the
   still-needed gate reading it as any other.
