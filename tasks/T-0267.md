## Description
stories: S-19953
writes: asf/briefs/templates/review.md, asf/briefs/build.py, asf/briefs/preamble.py, tests/test_briefs.py, tests/fixtures/briefs/golden/review.md
after: Task 1, Task 2

§2.3: the checklist becomes the table's skeleton, the mechanical pass is visible above the
judgement pass, and the line that told the reviewer to type a verdict is deleted. The kind is
*derived* from the branch prefix, not configured, because one `review` template serves all three
(§1.1). A code review's skeleton carries one extra mechanical row per acceptance line of the
Feature's Stories, so the reviewer sees the same text twice — once as a Story, once as a row to
answer.

**Files**

- `asf/briefs/preamble.py` — `review_kind(product, facts)` and `facts['review_kind']`; the review-file
  line of `state_lines` (`asf/briefs/preamble.py:551`) naming the kind
- `asf/briefs/build.py` — `context()` gains `review_kind`, `check_table`, `prereview_cmd`
- `asf/briefs/templates/review.md` — `{check_table}`, the two pass headings, `{prereview_cmd}`; the
  `verdict: approved` instruction removed
- `tests/test_briefs.py` — the per-kind table assertions of §3.4
- `tests/fixtures/briefs/golden/review.md` — regenerated (`ASF_UPDATE_GOLDEN=1`)

**Steps**

1. `preamble`: the kind from the branch prefix — `conventions.branch_prefixes['spec' | 'plan']` →
   that kind, anything else → `code` — with `feeder.rows.review_round(feature)[0]`
   (`asf/feeder/rows.py:409`) as the fallback when the row carries no branch. No path literal and no
   new row field (§1.1). `facts['review_kind']` is set for every kind in `REVIEW_KINDS`.
2. The review-file line becomes `Review file to write: \`{review_path}\` (round {n}, {kind} checks)`,
   §2.3's shape, for the `to write` and `to answer` forms alike.
3. `build.context`: `review_kind`; `prereview_cmd`, the whole command with `--kind` filled in and
   `--card` when the row has an item, so no session has to choose (D5); and `check_table` —
   `reviews.render_table` over the mechanical rows, a blank line, the standard rows, and for `code`
   one extra mechanical row per acceptance line of the card's Stories, verbatim. The three keys are
   set for every kind (empty for a non-review), because every placeholder must be a context key
   (§1.1).
4. `templates/review.md`: keep the opening and the round-1 rule; replace the hardcoded six-row table
   with §2.3's fenced block — the `A GATE RETURNS ONE CHECK PER THING IT LOOKED AT` sentence, the
   `### Pass 1 — mechanical` heading, `{check_table}`, and the `{prereview_cmd}` fence. Delete the
   `verdict: approved` / `verdict: changes requested` instruction; the C list and I list stay, and
   the final-message line names the failing rows and the gate lines, not a verdict. The fixer's and
   adjudicator's templates are untouched (§1.3).
5. Regenerate the golden: `ASF_UPDATE_GOLDEN=1 python3 -m unittest tests.test_briefs`, then read the
   diff of `tests/fixtures/briefs/golden/review.md` and confirm it is this change and nothing else.
6. `tests/test_briefs.py` per §3.4: `build.build` over the fixture record for `--kind review` — on a
   `spec/…` branch the brief contains all five spec mechanical checks and neither of the code ones;
   on a `plan/…` branch the plan checks; on a `worker/…` branch the six code checks **plus one row
   per acceptance line of the Feature's Stories**, verbatim. `Pass 1 — mechanical` precedes `Pass 2`;
   `reviews.parse` over the brief's own text finds two blocks and no fault; the brief carries the
   `review-checks` command with its `--kind` filled in; and `verdict: approved` appears in no
   template. The module's standing assertions — every placeholder a context key, no placeholder
   surviving into a built brief, no forbidden name in a template — keep holding.
