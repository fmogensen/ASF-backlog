§2.8. The backstop for both cases the landing deliberately does not refuse — a missing index (D4)
and a Task listing no Story (D5) — and for the one it cannot see: a landing that slipped through a
merge queue before this gate existed. Waits on Task 5 because the claims it reads are that Task's
key. The rule **card** is minted by hand when this lands (D9) and its id is not in this document.

**Files**

- `asf/rules/story_proof.py` — new. `violations(items, ev, root)` and `cmd_proves(args, root)`
  (**P10**).
- `asf/cli.py` — the `proves` subparser beside `rules` (`cli.py:142-146`) and its dispatch clause
  (`cli.py:338-340`).
- `rules/story-proof.sh` — new, and the `rules/` directory with it (**P12**).
- `tests/test_rules.py` — `StoryProofTests`.

**Steps**

1. `violations(items, ev, root)` — one line per violation, in the `<what> <where> <since>` shape
   `asf/rules/rules.py:9` expects, the rule id left to the runner to prefix so the script never
   carries one. A Task is *landed* when `ev['ids'][<T-id>]['commit']` is set (**P11**). The three
   shapes of §2.8, byte for byte:

   ```
   task landed proving nothing T-0123 (S-18750) since 2026-09-20
   claim names a line S-18750 has no more S-18750 line 7 (T-0124) since 2026-09-22
   task lists no story T-0125 since 2026-09-21
   ```

   `since` is the date part of the Task card's `updated` in the index, falling back to
   `record.core.today()`. Sorted, so two runs over one record print the same lines in the same
   order.
2. `cmd_proves(args, root)` serves both subcommands. `check` prints one line per violation and
   exits 1, or prints nothing and exits 0 — the contract `run_check` reads
   (`asf/rules/rules.py:131-142`), which is what lets `asf file-bugs` turn the lines into a Bug
   through the path every other rule already uses (`asf/tick/file_bugs.py:145`). `--json` carries
   the same rows as objects with the rendered line beside them.
3. `show <T-id>` prints one Task's claims and their problems — the same `proves.validate` output the
   refusal prints, available **before** the push. The branch is `conv.prefix('code') + <T-id>`
   when that branch is on the product's origin, and `origin/<main>..HEAD` of the product repo when
   it is not, which is what a session has in hand mid-run. `--branch` overrides both. No convention
   is written into either module: the prefix comes from `asf.conventions` (`asf/evidence/evidence.py:50`
   is the same read).
4. `asf/cli.py`: `p_proves = sub.add_parser('proves', ...)` with `proves_command` in
   `choices=['check', 'show']`, an optional positional item id, `--product`, `--branch` and
   `--json` — the `rules` subparser's shape. The dispatch clause imports `cmd_proves` late, as
   every other clause in that function does.
5. `rules/story-proof.sh`, exactly as §2.8 ships it:

   ```bash
   #!/usr/bin/env bash
   # F-0040 — every landed Task ticks the acceptance line its tests prove.
   exec asf proves check --product "${ASF_PRODUCT:?}"
   ```

   Committed with the executable bit, into a `rules/` directory this repo has never had (**P12**).
6. `StoryProofTests`: `violations` over a temp record and a stub evidence dict producing each of the
   three shapes and nothing for a landed Task whose every Story is proven; a Task with no landing
   evidence not reported at all; `cmd_proves` exiting 1 with one line per violation and 0 with
   none; `--json` carrying the same rows; the shipped script's body naming
   `asf proves check --product` and reading the product from the environment; and
   `rules.resolve_script(root, 'rules/story-proof.sh')` finding the shipped script from a temp
   record that has no `rules/` of its own — the proof that a rule card minted with
   `check=rules/story-proof.sh` resolves through `asf/rules/rules.py:53` (**P13**).
