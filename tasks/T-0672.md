The spec's §*The design* §2 and §3: `PREFETCH_WIDTH`, `harvest.prefetch`, `Lane.prefetch_facts` and
`Lane.prefetch_checks` — the per-branch `git` reads and the gated PRs' `gh pr checks` issued eight
wide *before* the sequential loop reads them back out of Task 1's store.

The prefetch is never load-bearing, and that is the property Task 2 is judged on rather than any
speed: it produces nothing anyone reads, it swallows every exception, and skipping it entirely
leaves the pass computing exactly the same thing at exactly Task 1's speed.

Read **PD2** (`prefetch_checks` goes in `gate_pass`, not `lane_pass`, and why the spec's placement
warms nothing), **PD7** (a lock across the subprocess ships a prefetch that passes its own
concurrency test and saves nothing), **PD8** (two callables in one wave may never share an argv) and
**PD9** (no slug, no warm) before starting.

**Files**

- `asf/harvest/harvest.py`:
  - `PREFETCH_WIDTH = 8`, with the spec's docstring — 8 is what `metrics.ci_from_api` already uses
    for concurrent `gh api` calls (`asf/metrics/metrics.py:1690`, P6/D8).
  - `prefetch(calls, width=PREFETCH_WIDTH)` — `pool.map` over zero-argument callables in a
    `ThreadPoolExecutor`, every answer discarded, `contextlib.suppress(Exception)` per call,
    returning the number of calls made. Each worker re-enters `mutation_guard.active()` when the
    submitting thread had it on (D9, P5): read `mutation_guard.is_active()` once on the submitting
    thread, and wrap each call so the worker opens `active()` when it was on. The docstring says
    **never load-bearing** in those words, and says why the guard line is there for a pool that
    submits only reads today.
- `asf/harvest/lane.py`:
  - `Lane.prefetch_facts(self, names, runs)` — called from `gather` (**:1241**) immediately after
    the `names` set is complete (**:1259-1262**) and before `for b in sorted(names)` (**:1263**);
    P10 establishes every branch and its item are known by then. **Wave 1**, one callable per
    branch: `touched_files`, `changed_lines`, `_subjects`, `merge_commits`, `trunk_history` and the
    ahead count (`git rev-list --count origin/<trunk>..origin/<b>`). **Wave 2**, one callable per
    branch: `already_on_trunk(self.repo, self.trunk, b, self.conv, item)` with no `files=`, which
    finds its `touched_files` in the store and issues only the path-filtered diff it adds. Two
    waves because wave 2's argv is a function of wave 1's answer (**:846-848**). Both through
    `H.prefetch`. The docstring carries PD8's constraint: no two callables in one wave may issue the
    same argv.
  - `Lane.prefetch_checks(self, entries)` — called from `gate_pass` immediately before `precheck`
    (**:2315**), inside Task 1's narrowed window, over what `take_for_tick` returned (**:2314**).
    One callable per entry with `isinstance(self.host, GitHubHost)` and `(f.get('prev') or
    {}).get('pr')` — `precheck`'s own condition (**:2493**), PD2 — calling `pr_checks(self.slug,
    number)`. The argv is a function of `(slug, number)` alone (P4), so `required` and `rerun` are
    none of this method's business.
- `tests/test_harvest.py` — `PrefetchTests` (new; no `git` at all).
- `tests/test_lane.py` — `PrefetchNeverLoadBearing` (new; on `LaneFixture`), and the two-wave
  additions to `PassReadsTests`.
