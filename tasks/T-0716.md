## Description
stories: S-37852

after: Task 2

The spec's §4 — `cancel_totals(product, now=None)`, pure over the claim ledger, and the one block
`cmd_queue` prints. No `gh` call, no new file, no second table (C12), and **one footnote line the
spec does not have** (PD1).

Read **PD1** (the word `expected`, and the footnote landed code now requires), **PD8** (where the
block goes, and why it is not where §4 says) and **PD10** (the other minutes figure) before starting.

**Files**

- `asf/ci_queue.py` — `cancel_totals(product, now=None)`; the block in `cmd_queue`
- `tests/test_ci_queue.py` — the new `TestCancelTotals`

**Steps**

1. `cancel_totals(product, now=None)` with the spec's §4 docstring: `{name: {'runs': n,
   'sunk_min': m}}` over `load_claims(env.state_dir(product.name))`, one key per relief reason
   (`relief:reserved` … `RELIEF_REASONS`) and one per other cause, **zeros left out**. A claim with
   no `sunk_s` counts its run and adds no minutes (Records, and PD4's unread case reads identically
   to a pre-upgrade claim). A `relief` claim with no `reason` — one written before Task 2 — keys as
   plain `relief`. `sunk_min` is `sunk_s // 60` summed per key, floor. Pure over the file, no `gh`
   call, never raises: `load_claims` already returns `{}` for anything unreadable. The docstring
   names `asf/ci_cancels.py` and says in one sentence that its minutes are a different figure
   (PD10) — an operator reading two tables deserves to be told which is which once.
2. The block's text, exactly §4's, with the widths it prints there:

   ```
   cancels claimed in the last 48 h — 1 131 min sunk:
     relief: main's reserved runners handed back   9 runs,   814 min   WASTE
     relief: trunk starvation                    23 runs,   201 min
     relief: competing jobs escalated             4 runs,    38 min
     superseded — a newer push replaced it       18 runs,    64 min   expected
     duplicate-push                               6 runs,    14 min
   ```

   `WASTE` and `expected` are the card's own two words on the card's own two rows, and **nothing else
   carries a verdict** — `relief: trunk starvation` is the minutes the queue trades on purpose and
   gets none. The `48 h` is `CLAIM_TTL_S`, rendered, never hard-coded. `relief:starved` and
   `relief:escalated` print as two rows, as §4 shows, not merged.
3. Per **PD1**, one footnote line under the block, verbatim:

   ```
   expected counts every newer push; whether a push carried no change is asf/ci_cancels.py's
   reading, not this block's
   ```

   It is one line in the printed output (wrapped here). This is the C15 discipline applied to §4:
   the landed `asf/ci_cancels.REREAD` says `superseded` is the weak reading, and a row that says
   `expected` without saying so would put this card's word against that module's.
4. The header line prints only when the ledger holds something — no ledger, no block, not even an
   empty heading.
5. Place the whole thing in `cmd_queue` **immediately before `if not line.order: return 0`**
   (`:3631-3632`), per **PD8** — so it prints for a product with nothing in line, which is the state
   an operator is usually in when they ask what the cancels cost. Leave the `if not line.order`
   guard itself, the `free:` lines and every numbered entry line exactly as they are. `--apply`
   returns at `:3618-3619`, well above this, so nothing extra is needed to keep the block out of the
   pass.
6. `tests/test_ci_queue.py`, the new `TestCancelTotals`: the three cases of the spec's fence, plus
   one this plan adds — `test_a_relief_claim_with_no_reason_keys_as_plain_relief`, because a ledger
   that straddles Task 2's landing has both shapes in it for two days and `cancel_totals` must not
   drop those runs. Assert the footnote line is present too.
