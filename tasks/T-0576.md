## Description
stories: S-35853
writes: tests/test_seat_claims.py
after: Task 3

The card's test, and nothing else: *two concurrent waves never exceed an account cap.* Against the
trunk at this branch point the sum is 8 (PD13, P2); after Tasks 1–3 it must be exactly 4.

**What changes when this lands.** No product code at all. This Task exists because the card's
sentence is a claim about two processes, and no single-process test can make it.

**Files**

- `tests/test_seat_claims.py` — `TwoWavesOneAccount(Home)` added. The other three classes are
  untouched.

**Steps**

1. One temp `ASF_HOME` with `state/a` and `state/b` (PD12 — `a` and `b`, never the product names the
   card's measurement used), one account at `cap: 4`, `sessions: 'fake'` so nothing shells out to
   `ps` (P14).
2. Two **real child processes**, started with `ASF_HOME` in their environment — the mechanism is the
   point: a thread would share `Pool.live` and prove nothing, since the defect is precisely that two
   *processes* cannot see each other's takes. Each child runs `wave_mod.wave` for its own product
   over 4 rows.
3. The child's `spawn_fn` is what makes the window real (P3): it sleeps `SETUP_S = 0.6` — standing in
   for the real `spawn`'s worktree, branch publish and `worktree_setup`, which the wave prints as
   `setup 41.3s` — and only then appends its launch line through `pool_mod.append_session`, the same
   last step the real `spawn` takes at `asf/workers/spawn.py:955`. A stub that appended first would
   test nothing this card is about.
4. Released together: each child writes `ready-<p>` into the temp home and waits for a `go` file; the
   parent touches `go` once both are ready. The two waves overlap by construction, not by luck — no
   sleep in the parent decides the race.
5. The assertions, all four: both children exit **0**; the launches they report sum to **exactly 4**
   — not fewer, so no seat is lost to the protocol itself, which is the failure mode a too-eager
   refusal would hide; the two registries together hold **4** live runs; and the ledger is empty at
   the end, every claim released by its launch line landing (C5 rule 3).
6. Keep the child's body in the test module and start it with `[sys.executable, __file__, ...]` or an
   equivalent that carries `PYTHONPATH`, so the child imports the same checkout the parent is
   running; `tests/test_harvest.py` and `tests/test_stop.py` are the suite's precedents for a test
   that starts a real process. `SETUP_S` is a module constant, not a literal, so a slow host is one
   edit away.
