The spec's design §3 and §4 (D-0002, D-0013; P3, P4, P6, P12). The two consumers that exist today — the
upgrade target and the bootstrap — each resolving a channel to the **version tag** it names, never
to the channel name, because a pin must be immutable and a branch name recorded in
`install.json` says nothing a week later (D-0002). Needs only Task 1: both read `channel_tag` and
`resolve`, and neither touches the log, the gate or the part.

**Read this Task from `docs/plans/f-0308.md`, not from this card** — the record cuts a Task card's
description at 4000 characters and this section is longer, so the card stops before the Acceptance.

**PD2** binds this Task and reaches no card: the peel fix the spec names as in flight is **already
on the trunk** at this head. `resolve_ref` (`:432-443`) already prefers the `^{}` line and
`resolve_target`'s checkout branch already asks `rev-parse --verify '<to>^{commit}'` (`:1093`), so
`to = tag` resolves an annotated version tag to its **commit** through the existing path, and
S-81209's *"the install record names the tag commit"* needs no change to those lines. This Task
coordinates with no other branch and must not edit them.

**Files**

- `asf/upgrade.py` — one step at the head of `resolve_target` (`:1080`), before the sha forms it
  already knows, exactly as §3 gives it: a `to` that is one of `channels.NAMES`
  (case-insensitive, stripped) resolves through `channels.resolve(url, name)`; no commit returns
  `None`, which is the caller's own unreadable-target path unchanged; otherwise `to` becomes the
  tag when the channel names one, the commit when it does not. The rest of the function is
  untouched, so every existing target form — a 40-hex sha, a prefix the record names, a branch, a
  tag — behaves exactly as it does today, and a word that is not a channel name is still just a
  ref. Imported inside the function, not at module scope.
- `tools/install.sh` — the `[ -z "$REF" ]` branch (`:102-118`). One listing,
  `git ls-remote "$REPO_URL" "refs/heads/releases/*" 'refs/tags/v*'` — `--refs` goes, because that
  is the flag that hides the peel (P4) — through one inline `python3` carrying the same rule as
  `channels.channel_tag`: the channel head's commit, the highest version tag whose `^{}` peel is
  that commit, else the newest version tag. `CHANNEL="${ASF_CHANNEL:-stable}"`, the script's own
  idiom for a non-default (`ASF_REF`, `ASF_REPO_URL`, `ASF_INSTALL_YES`) and not a new flag. It
  prints `product <p>, release <tag> (channel stable) from <url>` when the channel answered and
  `product <p>, release <tag> (no stable channel on <url> yet — the newest tag) from <url>` when it
  did not — printed, because the one thing this script already refuses to do is choose a ref
  silently. A `[ref]` argument still wins. The existing refusal is unchanged: no version tag at
  all is still the operator line it is today, never a silent fall back to a branch.
- `tests/test_channels.py` — `UpgradeTargetTest` and `BootstrapRuleTest`, one case per checkbox
  line of S-81209. `BootstrapRuleTest` extracts the script's new inline snippet the way
  `ReleaseRefTests` already extracts its sibling (`tests/test_install.py:2203`,
  `_bootstrap_resolve_tag_snippet`) and runs it against the **same** fixture remote as
  `channels.channel_tag`, asserting the two print the same string for a published channel, an
  unpublished one and an empty remote.
- `tests/test_install.py` — `ReleaseRefTests`' discipline kept and extended for the new snippet
  (§4). The sibling rule it does not replace is untouched, and `install.newest_tag` is not
  rewritten (**PD3**).
