## Description
stories: S-32559
writes: asf/feedback.py, asf/tick/step_groom.py, tests/test_feedback.py
after: Task 8

§2.6, D6 and D8. One comment on intake and one when the item lands, the History line as the only
ledger, and a retry as the only failure mode. The `groom` step calls `sync` before `cmd_groom`, so
an issue opened between two ticks is an intake card the same tick types it.

**Files**

- `asf/feedback.py` — `reply(root, product, items, conv, day, gh=metrics.gh)`, `sync(...)`
- `asf/tick/step_groom.py` — the call, in its own `try`/`except`
- `tests/test_feedback.py` — `ReplyTests`, `StepTests`

**Steps**

1. An item qualifies for the landing comment when `links.issues` is non-empty, its state is in
   `metrics.LANDED_STATES` (`asf/metrics/metrics.py:1122` — `Resolved`, `Closed`), and its
   `## History` carries no `feedback replied (issue #<n>)` line. With `feedback.ack` on (D8), an
   item whose History carries no `feedback acknowledged` line and which is not yet landed gets the
   intake comment instead. `feedback.ack: false` turns the first one off.
2. The comment is rendered from the index alone — no release read, no second forge call — in the
   shape §2.6 gives. A `Closed` item with no `links.prs` reads `closed without a change` instead
   of `landed`, because that is what happened and a reporter is owed the true one.
3. `gh issue comment <n> -R <repo> --body-file <tmp>` through `metrics.gh`
   (`asf/metrics/metrics.py:801`). On failure: one stderr line, **no History write**, and the next
   tick retries. The History line is written only after the comment is posted, so the failure mode
   is a duplicate-free retry and never a silent drop.
4. The History line goes through `asf.record.ingest.append_history_lines`
   (`asf/record/ingest.py:305`): `- <day>: feedback acknowledged (issue #<n>)` and
   `- <day>: feedback replied (issue #<n>)`. The item is published in the same commit shape the
   groom uses. No new `metrics/` stream, and the issue's comments are never read back (D6).
5. The issue is never closed, labelled or edited. One comment, on each of the two events; its own
   state stays the reporter's and the operator's (§1.2).
6. `sync(...)` runs `pull` then `reply` in one pass and returns what each did; `--dry-run` prints
   what it would write and writes nothing.
7. `step_groom.run` calls `feedback.sync(...)` **before** `cmd_groom`, inside its own
   `try`/`except Exception` that prints one `feedback:` line and carries on. The channel is never
   the reason a tick fails to groom, and `StepTests` asserts a `sync` that raises leaves the
   groom's exit code untouched.
8. No new tick step, no new clock, no new metrics stream (§1.2).
