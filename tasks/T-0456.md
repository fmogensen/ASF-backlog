The spec's §3 and D11: `cmd_upgrade` is the single funnel every upgrade path goes through (P11), so
one step inside it between the install and the table gives `tools/install.sh`, the tick's own upgrade
and F-0112's channel — when it lands — the migration for free. Plus the two places a file is first
written: `asf init`'s product yaml and `asf install`'s config template, which from this release stamp
what they write (D12).

**Files**

- `asf/upgrade.py` — the migration step in `cmd_upgrade`, `row`'s `config schema` column and its new
  `action` wording, `--to` and its restore, `render`'s header
- `asf/init.py` — `cmd_init` stamps the product file it writes
- `asf/install.py` — `CONFIG_TEMPLATE` carries `schema_version` as its first key
- `tests/test_install.py` — `UpgradeMigratesEveryProductTests`,
  `UpgradeToRestoresTheSnapshotTests` (new); `SchemaTest`, `InitTest`,
  `InstallConfigTemplateTests`, `UpgradeTest` follow the new output

**Steps**

1. `cmd_upgrade` gains one step between the install and the table: for every name in `products()`,
   `schema.auto_migrate(product, drain_s=…)`, printing its lines as they come —
   `migrate: schema 1 → 2` per record step, `upgrade: config.yaml schema 1 → 2 — <note>` per config
   step. A product whose config will not load is reported the way `row` already reports it and does
   not stop the others.
2. The step is skipped entirely when `--skip-pipx` was given and nothing was installed: that
   invocation is the read-only view of the table (P2) and must stay read-only, because
   `upgrade.row`'s only other caller is the operator asking what stands.
3. The drain here is the operator-facing one, not the tick's: `auto_migrate` is called with
   `schema.DRAIN_TIMEOUT_S`'s bound when the upgrade is an operator's (`owner` unset) and with
   `schema.tick_drain_s()` when the tick owns it (`owner` set, `asf/tick/tick.py:399`) — a tick's
   upgrade must not block for an hour inside a command the tick is waiting on.
4. `row(name)` returns five fields: `(product, record schema, config schema, package, action)`, with
   `config schema` read from `schema.product_version(name)` and `schema.config_version()` (`none`
   when unstamped). `render`'s header gains the column. `action` for a pending **additive**
   migration becomes `none (the next tick migrates)`; the newer-than-this-package action and the
   `fix the config: <e>` action keep their current wording.
5. `--to <ref>` (D11, PD13): `p.add_argument('--to', metavar='REF')`. It restores the newest snapshot
   at or below `<ref>`'s `CONFIG_VERSION` through `schema.restore`, then installs `<ref>` through the
   existing `_install`, then runs the doctor. With no snapshot and no `--force` it is exit 2, naming
   each file and each key the older release will refuse — which is what P6 and P7 make the operator
   need to know, since that release dies on every command and shows one red doctor row. Giving both
   `--to` and `--ref` with different values is exit 2 with the two values named.
6. `asf init` (`asf/init.py:264-290`): the product file it writes is stamped
   `schema_version: <CONFIG_VERSION>` as its first key (D12). The existing-file branch is untouched —
   `init` has always left an existing file as it is and printed the diff, and stamping it there would
   be an edit the operator did not ask for; `asf schema-migrate` is what stamps those.
7. `asf install`'s `CONFIG_TEMPLATE` (`asf/install.py:40`) carries `schema_version: <CONFIG_VERSION>`
   as its first key, so a config written from zero today is stamped and never needs the insert path of
   Task 1 step 8. The template is written only when the file is absent (`asf/install.py:217-220`);
   that stays true.
