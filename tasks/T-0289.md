## Description
stories: S-30305

after: Task 1

§2.4 and §1.4's exemption row: the scorer, the three-row table of what a lever without a pair
does, and `asf evals run | check | hash`. This is acceptance #4's whole machinery, and it lands
before any lever has a task — which is the honest order: the rule that a gap must be *recorded*
is what makes every later Task's exemption removal visible.

**Files**

- `asf/evals/adapters.py` — `Broken`; `ADAPTERS = {}`; `fires(lever, task)` — the dispatch, raising
  `EvalError` for an adapter name with no function. The two pure adapters are Task 3's, the rule
  adapter Task 4's.
- `asf/evals/run.py` — `Reading`, `LeverReading`, `Failure`; `score(eval_set, product=None,
  record_root=None)`; `print_reading(reading, out=print)`; `cmd_evals(args, ...)`.
- `asf/cli.py` — the `evals` subparser and its dispatch.
- `tests/test_evals.py` — `CoverageTests`.

**Steps**

1. `asf/evals/adapters.py`: `Broken(Exception)` carrying the line a check printed when it could
   say neither (§2.3); `ADAPTERS` as `{name: fires_fn}`; `fires(lever, task)` looking the lever's
   adapter up and calling it with `(task.given, task.want)`. An adapter that raises anything but
   `Broken` is the scorer's problem, not this module's — it does not catch.
2. `asf/evals/run.py`: the three record types of §2.4 — `Reading(set_hash, levers)`,
   `LeverReading(lever, lever_hash, passed, total, exempt, exempt_reason, unrecorded, failures,
   seconds)`, `Failure(task_id, why, expected, got, detail)`.
3. `score`: per lever, in manifest order, then the discovered `rule:<id>` levers (Task 4 writes
   that half; here the parameter exists and the roster is the manifest's). Per task: `fires` →
   `(fired, detail)`, `passed` when `fired == (task.expect == 'fire')`. `Broken` is a **fail** with
   `got: 'broken'` whichever polarity was expected (§1.4) — never a no-fire, never excluded from
   the total. Any other exception is a fail whose `detail` is the exception's first line.
4. The coverage rule, exactly §2.4's table: a lever with fewer than `min_tasks` tasks or missing a
   polarity is **not scored** — `passed = total = 0`, `exempt = True`, `lever_hash = None`; it is
   `unrecorded = True` as well when `exemptions.json` has no entry for it. A lever with a pair and
   an exemption entry is Task 1's loader error, so the two states cannot both be recorded.
5. `print_reading` — §2.4's printed shape byte for byte: the `== EVALS set <hash> — <p>/<t> passed,
   <n> lever(s) exempt, <n> unrecorded` header, one line per lever with its rate and lever hash, a
   `FAIL <task id>  expected <e>, got <g>` line and its `why:` under the lever it belongs to, and
   `exempt — <reason> (<card>)` for an exempt one. A rate is never printed for an exempt lever
   (§2.6's second rule; here it is `0/0` and the hash column is `—`).
6. `cmd_evals`: `run` scores, prints, and exits 1 when any task failed **or** any lever is
   unrecorded — the reading doubles as a gate (§2.4). `check` scores nothing: it loads, applies the
   coverage rule and exits 1 on an unrecorded lever, naming it and nothing else. `hash` prints the
   set hash and each lever's. `--json` prints the reading as one object. A `default_root()` of
   `None` (PD10) is not a crash and not a pass: `run` and `hash` print
   `no eval set on disk (<where it looked>)` and exit 2, `check` prints the same and exits 0 — a
   checkout without the set has no coverage failure to report.
7. `asf/cli.py`: `p_evals = sub.add_parser('evals', …)` beside `p_rules` (`asf/cli.py:246`), with
   `evals_command` as a `nargs='?'` positional over `('run', 'check', 'hash')`, `--product` and
   `--json` (PD14); two lines of dispatch in `main`, importing `asf.evals.run` locally as every
   other verb does. `--pre-commit` is Task 7's.
