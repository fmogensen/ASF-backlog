## Description
stories: S-32804

after: Task 3

`release_report` steps 5–8, D7, D8 and D9. The card's own acceptance: when a newer tag exists and
no session of the product is mid-landing, the tick reinstalls the pinned install at that tag,
re-renders the clocks, runs the doctor, and logs `upgrade: <old> → <new>`. The RED half is Task 5;
this Task's step 8 records `installed` and returns on a green doctor, and leaves the RED branch as
the one `TODO` Task 5 replaces.

**Files**

- `asf/upgrade.py` — `venv_bin`, `_new_asf`, `release_report` steps 5–8
- `tests/test_release_channel.py` — `AutoInstallsTheNewestTagTests`
- `tests/test_release_readiness.py` — new module (PD7): `ReleaseChannelUpgradesAreCountedTests`

**Steps**

1. Step 5, the card's mid-landing condition (D7): `mid_landing(product)` non-empty → print
   `upgrade: held — <n> item(s) mid-landing (<item> on <branch>, …)` and return `'held'`. Nothing
   is installed and nothing is recorded; the next tick asks again. The drain is **not** widened to
   worker sessions — that is the trunk channel's hazard too and its own card (the spec's Out).
2. Step 6: `rc = install(ref=tag, sha=sha, owner=product.name, wait_s=drain_wait_s(), run=run)` —
   the whole existing protocol (P3), unchanged and unduplicated: the pending marker parks every
   other product's ticks, the floor drains over `other_ticks()`, a red remote CI **at the tag's
   commit** refuses, and the new venv's own `direct_url.json` verifies the install. `sha=` is what
   makes both of those last two work on a tag rather than silently skipping (PD3, PD5) and it is
   Task 2's, already landed. `DEFERRED` returns `'held'` and files nothing — the install said why
   itself. Any other non-zero prints `upgrade: FAILED <old> → <tag> (exit <rc>)`, records `last`
   with `result: 'failed'`, and returns `'failed'`.
3. Step 7, two lines (D9): the card's own `upgrade: <old> → <tag>`, and the sha-shaped
   `tick: ran asf upgrade (<old>@<old_sha7> → <tag>@<sha7>), exit 0` — the trunk channel's exact
   form, matched by `release._UPGRADE_RE`'s `(?:\S*@)?([0-9a-f]{7,40})` (PD9). Without the second
   line `asf release-readiness`'s upgrade criterion counts zero and `min_upgrades` silently gates
   the next release forever. Both shas are written at 7 characters, the regex's floor.
4. `venv_bin(name='asf', run=subprocess.run)` — `<PIPX_LOCAL_VENVS>/asf-factory/bin/<name>`, read
   the way `new_install_commit` already reads it (`asf/upgrade.py:453-460`:
   `pipx environment --value PIPX_LOCAL_VENVS`). `None` when pipx cannot be asked.
5. `_new_asf(argv, run=subprocess.run, out=print, timeout=600)` → `(rc, output)`. This process
   holds the **old** package's modules and its cached metadata, so everything that must see the new
   install is a subprocess of it (D8) — calling `scheduler.install()` or `doctor.run()` in-process
   would render the old clocks and run the old doctor, and is the exact B-0135 tear the install
   protocol exists to prevent. A binary that is missing or will not start is `(2, <why>)`, which
   step 8 reads as RED: a broken install rolls back rather than being taken as fine.
6. Step 7 continues: `_new_asf(['scheduler', 'install', '--product', product.name], run)` —
   the clocks re-rendered by the new package, which is the card's second requirement.
7. Step 8: `_new_asf(['doctor', '--product', product.name], run)`. Exit 0 → write `last` with
   `from`, `from_sha`, `to`, `at` and `result: 'installed'`, and return `'installed'`; the fork
   Task 3 landed in `tick.py` then ends the tick, exactly as the trunk channel does after an
   install (P2). Non-zero is RED (P10: `cmd_doctor` returns 1 when either table is red) and is
   Task 5's; this Task leaves it recording `result: 'rolled-back'` is **not** yet true, so it
   records nothing, prints `upgrade: doctor RED after <tag> — rollback lands with the next Task`
   and returns `'failed'`. That is a del
