**Steps**

1. `JUDGEMENT = 'correct/judgement'` in `asf/briefs/build.py`, with the comment that it is the one
   refinement key and why (`correct` covers a chore and a question).
2. `need_key(kind, row=None)` exactly as §2.2 fences it: every kind is its own need but `correct`,
   which reads `getattr(row, 'correction_kind', '')` and `getattr(row, 'correction', '')` and asks
   `lifecycle.mechanical(cause, text)`. `getattr` with a default is deliberate — a hand-built row
   and an older ledger line both answer, and both answer `False` (P14).
3. `model_for(product, kind, row=None)` exactly as §2.2 fences it: the product's table by need key,
   then by the kind before the `/`, then `DEFAULT_MODELS` by need key, then by kind, then `LIGHT`.
   Two `dict.get`s, no branching on the product.
4. `build()` passes the row: `model=model_for(product, kind, row)`. Nothing else in the brief path
   changes — `Brief.model` is still the label, `step_wave.worker_row` still copies it onto the
   worker row, `spawn.model_arg` still maps it to an id (P17).
5. `Row.correction_kind: str = ''` on the dataclass, documented as "the ledger's
   `correction.kind` — the cause, beside the text; read by `briefs.build.need_key`".
6. `correction_rows` sets `correction_kind=c.get('kind') or ''` on the `FIX → CORRECT` row it
   already builds. The `STALEMATE → ADJUDICATE` row at the cap is untouched: adjudicate stays
   heavy, as the card asks (§1.2).
7. `ModelNeedTests` per §3.1's list, over a product built from a mapping and hand-built rows, with
   no git and no clock.
8. `CorrectionCauseTests` per §3.3's first clause, plus the assertion that `step_wave.worker_row`
   carries the resolved label from the brief onto the worker row unchanged.
