The plan-reader half of the spec's `## The design` §5, and nothing else. After this lands, each
plan reader makes two processes where it made two per plan.

The whole decision is D13, and it is about not breaking the injected reader. **`trunk_reader`
returns a `TrunkReader` object: callable with one path exactly as its closure is today, plus
`prefetch(paths)`.** Every test injects a bare callable as `read_plan`, and `overlay` is called from
the wave with a reader built elsewhere — an added capability that a plain lambda simply does not
have keeps all of them working with no adapter. `backfill` and `overlay` call `prefetch` **only when
the reader they were handed has it**.

D14 is the same shape for `_mint`: every guard before `text = read_ref(ref)` (`plan_tasks.py:78-98`)
reads metadata only — type, `has_task_child`, `DONE_STATES`, `is_retired`, `match_feature` /
`plan_ref`, `decided` / `own_lane_plan` — so a collection pass reaches the same refs in the same
order, and the minting loop is otherwise untouched. Verified by reading all seven guards.

**Files**

- `asf/record/plan_order.py` — `class TrunkReader` with `__call__(path)` returning exactly what
  `trunk_reader`'s closure returns today (`evidence.read_ref(f'origin/{main}:{path}',
  product=product)`, or None), plus `prefetch(paths)` reading the lot in one `evidence.read_refs`
  and serving `__call__` from it; a path outside the prefetch is still read on demand.
  `trunk_reader(product)` (`:245-252`) returns one. `backfill` (`:259`) and `overlay` (`:298`) each
  already compute their plan-path list before their loop (`plans`, `:270-273` and `:302-306`) and
  gain one line: `prefetch` on the reader they were handed, when it has one. `overlay` keeps its
  `try/except Exception` around the read — *the guard never breaks the wave* — so `prefetch` must be
  inside that protection or be equally total. Nothing else in the module moves.
- `asf/record/plan_tasks.py` — `_mint` (`:73`) splits into one pass over the Features collecting the
  refs it will need, one `evidence.read_refs` for the lot, then the minting loop, which reads its
  text out of that mapping. The injected `read_ref` parameter (`:75`) **stays**: when it is given,
  the collection pass calls it per ref as now, because that is the seam every test uses. Nothing
  else moves — `stories_of`, `has_task_child`, `plan_ref`, `own_lane_plan`, `writes_lines` and the
  minting itself are untouched, and the cards minted must be the same cards in the same order.
- `tests/test_plan_order.py` — one new class, `BatchedPlanReads`. The cases §3.5 names:
  `TrunkReader` is callable with one path as `trunk_reader`'s closure is today; `prefetch` over five
  plans makes **two** processes and the five subsequent reads make none; a path outside the
  prefetch is still read; `backfill` and `overlay` handed a bare lambda (no `prefetch`) behave
  exactly as they do now, and handed a `TrunkReader` write the same `after:` values.
- `tests/test_plan_tasks.py` — D14's cases: the same Task cards are minted, in the same order, from
  one `read_refs` — asserted by counting `evidence._batch` with the injected reader absent — and the
  injected-reader path still mints identically.
