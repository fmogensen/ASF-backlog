## Description
stories: S-14304
writes: asf/tick/step_health.py, tests/test_tokens.py

Depends on T-14651 (`stall.capped`). It queues behind it on `tests/test_tokens.py`, which is the
order it needs anyway. Last Task of the card: its gate is the card's final green.

**Files**

- `asf/tick/step_health.py`: `run()`'s first call, the per-run event; the module docstring gains the
  cap sentence.
- `tests/test_tokens.py`: `HealthStepTest`.

**Steps**

1. `run(ctx, out=print, runtime_fn=_runtime)` calls `stall_mod.capped(product, out=out)` **before**
   `health_mod.health(product, fix=True, out=out)`. The capped run's log now carries a result, so
   the very same pass ends it `failed: token cap` — no session waits a tick to die.
2. One `ctx.event('capped', job=…, item=…, kind=…, dimension=…, tokens=…, limit=…)` per capped run,
   the `item` read from the session record. `ctx.event` appends to
   `metrics/events/<day>.jsonl` in the record clone (`tick.py:140-149`).
3. `ctx.counts` is unchanged: a cap is not a stall, and the `ticks` stream's shape is not this
   card's.
4. Nothing else in the step changes, and nothing needs to: `dead_jobs` names a job only when health
   ended it `dead pid` or stall reported `DEAD`, and a capped run is neither (PD11). The docstring
   says that, so the next reader does not have to re-derive it.
5. `HealthStepTest` as below, on `tests/test_workers.py`'s `Home` and the tick `Ctx`, with
   `stall._signal` patched (PD5).

  - `test_the_health_step_caps_then_ends_in_one_pass`: a live over-cap session; one
    `step_health.run(ctx)` → the output has a `CAP` line and an `ended … failed: token cap`
    line, and the registry's run carries `end_reason: failed: token cap`.
  - `test_a_capped_run_is_not_given_a_cold_retry`: the same tick → no `-correction` job in the
