**Steps**

1. `CHECKLIST['enduser']`, both tuples, from §2 verbatim. These are what `reviews.required('enduser')`
   normalises, and `reviews.covers` (`:168-179`) then lets a reviewer's shorter wording count — so
   `leaked internals: none` answers row two without the reviewer copying the sentence. Do not
   shorten the rows in the checklist to what a reviewer might type: `covers` runs the other way
   (every word of the required name must be among the row's), so a short required name is the one
   that fails to be matched by a longer row.
2. The template. Its four parts are §2's four bullets, in the house voice, and every
   `{placeholder}` in it is a key `context()` builds — a typo is a test failure, not a brief that
   ships with a literal `{audience}` (P18). It states, in order: **who you are** (the `audience`
   sentence verbatim, and that this is the only perspective in the brief — not a diff, not a plan,
   not a footprint, and the code review has already passed); **what to read** (`{pages}`, whole, as
   published — the rendered page at `{app_host}` where there is one, the rendered source top to
   bottom otherwise, never only the changed lines); **what to look for** (the five mechanical rows
   as questions a reader asks); **the two lists** — `### C — MUST FIX`, numbered, each item opening
   with `file:line` or the page and the sentence, then the exact change; `### I — SHOULD FIX` for
   what should be better and will not block; and `none` under MUST FIX as the shape that approves.
   It ends with the standing rule every review template carries: write the review file in the
   worktree, commit nothing, push nothing — the factory files it.
3. The heading text in the template is `### C — MUST FIX` and `### I — SHOULD FIX`. `C_HEADING_RE`
   accepts the hyphen and the `##` level t
