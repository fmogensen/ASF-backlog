The spec's design §5 whole. The counter already exists per tick — `loop.py` prints
`questions: resolved by code N, to the console M (P% by code)` (`:110-117`) over the six classes
code answers today — and it is **persisted nowhere** (`P9`): `summarize` (`:73`) computes
`resolved` (`:94`) and `escalated` (`:95`) into a dict, `save_plan` writes neither, and the line
reaches a rotated log no reader parses. So *"80 % over the window"* has no readable source and no
gate can hold it. This Task gives it one: a JSONL ledger beside the wait ledger, one record a tick,
which is the pattern this kernel already has three of (`D12`).

**It waits on Task 4** and on nothing else: the per-tick record carries §2's `intake: {waiting,
oldest_s}` beside the question figures, and that count is Task 4's. S-131012's classifier is in the
same Task as the ledger because both live in the new module and both are read by the one new verb.

**The classifier codes nothing, and that is the Story** (`D14`, `PC13`). The reading it automates
has already been done by hand once — F-0339's §1.1 classifies 62 live records and names the next
two classes, `pushed` and `trunk-base`, which its own landed spec and plan already own. What is
missing is that the reading was a one-off. So `asf kernel questions --classify` is the standing
instrument, and **no resolver class is added here**: `asf/kernel/resolvers.py` is on no `writes:`
line in this plan, and S-131012's last two acceptance lines are what hold that mechanically.

**Read this Task from `docs/plans/f-0334.md`, not from this card.** The card's prose is cut at 4000
characters (`PC8`). Two decision rows bind it and are on no card: `PC14` (`asf/kernel/mainmoves.py`
is the precedent for both the ledger and the `asf/cli.py` wiring — a `--product` and a `--since`,
read-only, the dispatch catching `ValueError` and returning `2`; copy it rather than inventing a
shape) and `PC13` (what this Task must **not** touch).
