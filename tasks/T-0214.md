## Description
stories: S-18808

§2.8. The card's third acceptance says *one review whose check table covers every Task's proves
lines*. That is made a property of the brief — the Tasks, their footprints, their commits and
their acceptance lines are handed to the reviewer — rather than of the reviewer's diligence. One
new kind, one new caller, and no per-Task review anywhere (§1.2).

**Files**

- `asf/briefs/templates/review-train.md` — **new**: the existing review table repeated per Task,
  per §2.8.
- `asf/briefs/build.py:46` — `KINDS` gains `'review-train'`; `DEFAULT_MODELS` gains
  `'review-train': HEAVY` (the `review` model); the brief context gains `n`, `review_path` and
  `task_blocks`.
- `asf/metrics/metrics.py:51` — `RECORD_KINDS['review-train'] = 'review'` (PD12).
- `asf/tick/step_train.py` — the cutter's one call: build the brief and launch it through
  `workers.wave.wave(product, [row], 1, …)`.
- `tests/test_briefs.py` — `ReviewTrainTests`, §3.7.

**Steps**

1. The template is `asf/briefs/templates/review.md` with §2.8's addition: the verdict is a table
   per Task, `{n}` names how many the train carries, `{review_path}` is where the file goes, and
   `{task_blocks}` is one block per Task — its id, its title, its `writes:`, its commit sha and
   its acceptance lines. A Task the reviewer cannot find a commit for is a `fail` row, not a
   missing section. The verdict line is per train; the C list names the Task each finding belongs
   to, because that is the unit Task 8 can revert.
2. The review path is derived — `conventions.review_path(slug, n)` — and never written as a
   literal, which is what `check_conventions.sh` in this Task's Gate proves.
3. The row the cutter builds: `job = f'review-{train}'`, `item` the train's first Task (so the
   registry and the preamble have an item to hang on), `branch` the train branch, `brief_kind`
   `review-train`.
4. It is launched through `workers.wave.wave`, not by a direct spawn (D10) — the pool, the quota
   and the S1 reserve still decide whether it runs now, and a wave that is full defers it to the
   next tick rather than bypassing the one thing a new launcher must not bypass.
5. PD12, in this same diff: `RECORD_KINDS['review-train'] = 'review'`, one line beside
   `'review': 'review'`. Without it `session_kind` falls through `derive_kind` to its `'code'`
   default and every train review is counted as a coder session — which would make Task 10's row
   wrong the first time a train is reviewed.
6. `ReviewTrainTests` per §3.7: one `review-train` brief per cut train, carrying one block per
   Task with that Task's id, title, `writes:`, commit sha and acceptance lines; the row's job name
   (`review-<train>`), its item (the train's first Task) and its branch (the train's); a train with
   one Task still getting exactly one review; the placeholder test over the new template; and
   `metrics.session_kind({'kind': 'review-train', 'job': 'review-code-2026…'})` → `review`.
