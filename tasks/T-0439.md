## Description
stories: S-32904, S-32905

after: Task 2

The spec's "the wave prints it once in the tick log", "the wave's 94 lines become one line and five"
and "an S1 nobody is working is said aloud" bullets: three log surfaces over Task 2's `Plan` and Task
1's two formatters. No plan changes here — only what the wave says about the one it already made.

**Files**

- `asf/tick/step_wave.py` — `GATE_LINES`, the gate and `NEEDS OPERATOR` lines in `launch`, the cap on
  `left_out`'s S1 reasons
- `tests/test_s1_gate.py` — `TheWaveSaysWhatTheGateHolds`, `AnUnworkedS1NeedsAnOperator`

**Steps**

1. `GATE_LINES = 5` with the spec's comment: the wave names this many S1-cut rows one by one, then
   counts the rest (D9).
2. In `launch`, directly after the plan is made, the spec's loop:
   `for line in [tiers.gate_line(plan.gate)] + tiers.needs_operator(plan.gate, product, skip=held):`
   — a falsy line is skipped, the gate line is printed as `wave: {line}` and each `NEEDS OPERATOR`
   line as itself, to the same `out` as `approvals.raise_holds`' lines. `held` is the dict
   `raise_holds` returned on `launch`'s first line (PD13); it is already in scope.
3. The gate line prints exactly when `plan.gate.held > 0`, which by P1 is exactly when the wave
   launches no tier-2 row because of the lane — the cut is all-or-nothing, so the two conditions are
   one condition and no second test is needed.
4. `left_out` keeps its signature, its `why` strings and its reasons. Only the loop that prints them
   changes, in `launch`: a `why` beginning `S1 first` is counted, the first `GATE_LINES` of them are
   printed as today, the rest are counted into `s1_more`, and one closing line
   `waits    +{s1_more} more row(s) behind the S1 gate (asf next)` is printed when `s1_more`. Every
   other `waits` reason keeps a line per row — the standing rule of P10 is kept, not traded.
5. Nothing else in `launch` moves: the per-row loop's own `waits` lines (host hold, held class, no
   seat left), the fair share's lines, `triage`, `adjudicate` and the `wave:` outcome lines are
   untouched.
6. `TheWaveSaysWhatTheGateHolds` in `tests/test_s1_gate.py`, on `StepsTestCase`
   (`tests/test_tick_steps.py:38`): a record whose plan has one unseated S1 and more than
   `GATE_LINES` tier-2 rows behind it. The wave's output holds exactly one line beginning
   `wave: S1 gate:`, with the card's shape and the right total; exactly `GATE_LINES` per-row
   `waits` lines carrying the `S1 first` reason; one `+N more row(s) behind the S1 gate (asf next)`
   line whose `N` closes the arithmetic against the gate line's total; and a `waits` line for every
   row cut for a reason that is not the S1 lane. A second case with three cut rows prints all three
   and no `+N more` line. A third with no S1 at all prints no `S1 gate` line.
7. `AnUnworkedS1NeedsAnOperator`, same base: an S1 blocked by an open item, with tier-2 rows behind
   it, produces one `NEEDS OPERATOR` line naming the id, the reason, `holds 0 of <behind> tier-2
   rows` (D7) and the `asf set … blockedBy=` command; an undecided S1 and an attempt-limited one each
   produce their own reason and command; the line prints on **every** tick the condition holds (D6) —
   asserted by running the wave twice and seeing it twice, with no state file, no latch and no
   counter written between them; and an S1 an open parking hold already named through
   `approvals.raise_holds` gets **one** line, not two (D8).
