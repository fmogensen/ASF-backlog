The spec's §3 and C5. After this Task `asf center follow` polls four append-only streams per
product in one loop at one interval, in `_all_products()` order, and prints each new line stamped
with its product and its kind — a tick rendered exactly as the tick renders itself. `asf watch`
becomes the N=1 case of the same reader, and **`tests/test_watch.py` is unchanged and green**,
which is the fence C5 asks for and the only proof that lifting the reader changed nothing.

No threads. C5 refuses them outright, and the reason is worth repeating at the point of temptation:
*"a monitor whose bug is a race is a monitor nobody trusts, and N files polled in one loop at one
interval is the same latency with none of that."*

Read **PD6** (`tail.py` is stdlib-only; the renderer is the caller's) and **PD7** (the function is
`_read_new_lines` today; `digest_lines` and the day-rollover rule do *not* move).

**Files**

- `asf/center/tail.py` — new. `read_new_lines(path, pos)`, moved from
  `asf/tick/watch.py:37-53` with its docstring verbatim and its leading underscore dropped;
  `Stream`; `follow(streams, out, poll, once=False, sleep=time.sleep)`. **Module-level imports:
  the standard library only** (C5) — `os`, `time`, `json`.
- `asf/tick/watch.py` — `_read_new_lines`'s body replaced by nothing: the function goes, and the
  one call in `run` (`:76`) becomes `tail.read_new_lines(path, pos)`, with
  `from asf.center import tail` at module scope. `digest_lines`, `COUNTER_KEYS`, `_ticks_dir`,
  `_today_path`, `run`'s day-rollover lines (`:73-76`) and `register`/`cmd_watch` are untouched.
- `asf/cli.py` — the `follow` sub-parser on Task 2's `center` parser: `--poll` with
  `tail.POLL_SECONDS`' default and `--once`.
- `tests/test_center.py` — `class Follow`.

**Steps**

1. Move `_read_new_lines` to `asf/center/tail.py` as `read_new_lines`, docstring and all, and
   point `watch.run` at it. Run `tests/test_watch.py` **before writing anything else**: six tests,
   green, byte-identical file. If it is not green the lift is wrong and nothing after this step
   matters.
2. `Stream(product, path, kind, render)` — a `namedtuple` or frozen dataclass. `path` is a
   **callable** returning the current path, so the ticks stream's `<day>.jsonl` can roll over
   (PD7); `kind` is the four-character label the line carries (`TICK`, `GATE`, `HOLD`, `MAIL`);
   `render(rec)` returns the list of text lines for one parsed record, and is supplied by the
   caller (PD6) — `read.streams()` passes `watch.digest_lines` for the ticks stream and small
   local renderers for the other three.
3. `follow(streams, out, poll, once=False, sleep=time.sleep)` — one dict of `{stream: (path,
   pos)}`, seeded with `os.path.getsize(path)` for every file that exists when `follow` starts, so
   **only lines appended after it started are shown** (`watch`'s own rule). Each pass, per stream
   in order: resolve `path()`; when it differs from the remembered one, reset `pos` to 0 (the
   day-rollover rule, per stream); `read_new_lines`; `json.loads` each line, skipping a malformed
   one and continuing with the ones after it; and print
   `f'{HH:MM:SS}  {product}  {kind}  {text}'` for each line `render` returns. A file that did not
   exist when `follow` started is picked up the first pass it appears, at `pos` 0.
4. `--once` does one pass and returns — what every test drives, and what Task 6's fenced digest
   calls.
5. The `follow` command function, and `class Follow` — the spec's eight cases, all driven through
   `follow(..., once=True)` with lines appended between passes, never through a clock.
