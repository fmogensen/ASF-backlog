§2.6. The same shape as `scorecard.loop.verify` (`asf/scorecard/loop.py:332`), with D6's comparison
and one new outcome. Two Stories on one Task because T7's guards are assertions about the code T6
writes: every one of them is a path through the same function, and a `verify` built for T6 alone is
a `verify` that reverts on three readings and a wobble.

An automatic revert is the one thing in this spec that can do damage on its own, so §2.6's five
rails each get their own test, and the Task is not done until all five are red without the code and
green with it.

**Files**

- `asf/product_loop/loop.py` — `verify`, `revert_text`, `_fmt`, the `verify` call in `daily`
- `tests/test_product_loop.py` — `RevertTests`, `VerifyGuardTests`

**Steps**

1. `verify(product, history, cfg, state, cards_of, now, enqueue_fn=..., root=None)`. For each state
   entry with no verdict, resolve its card as `scorecard.loop.verify` does: `entry['card']` or
   `_find_marker(cards_of(product.name), entry['marker'])`, and skip when there is none — a card the
   drain has not minted yet is not a verdict, it is a wait. `cards_of` is
   `facts.load_cards(record_dir)` by default, and it is called for `product.name` only (rail 5).
2. Read `landed` off the card through `facts.card()`'s `landed`/`landing_shas`
   (`asf/scorecard/facts.py:183,199`), and do nothing until `now >= landed + verify_days`. A card
   the ingest marked `removed` closes the entry as `dropped` with one log line, the way
   `scorecard.loop.verify` does (`:347-351`).
3. The two medians, `score.median` over this measurement's `ok` readings only
   (`asf/scorecard/score.py:77`, D7): `before` over `[landed - verify_days, landed)` and `after`
   over `[landed, landed + verify_days)`. Both windows read the readings file, never the state
   entry's `baseline`.
4. The three no-verdict exits, before any comparison: fewer than `cfg.min_readings` `ok` readings on
   either side; `worse(...)` returning `None`; and — the same thing said from the other side — an
   after side whose every reading is `broken`. The loop waits: it does not revert, does not close
   and does not reopen. This is D4 arriving where it matters most, and the docstring says so.
5. `False` → the verdict is `held`. One History line queued on the card in §4's shape, the state
   entry updated with `verdict`, `verified`, `before` and `after`, and nothing else.
6. `True` → the revert. The same History line reading `got worse`, plus one revert card queued per
   §2.5's third column: `kind: 'card'` at `auto` and `kind: 'inbox'` at `groom`, `decided: True`,
   `parent: epic_of(...)`, `rank: 0` (PD11a — `0` survives `write_new_item`),
   `source: product-loop:revert:<sha7>`, marker `product-loop: revert <sha7> #<n>`, title
   `Revert <sha7>: <name> got worse after <id> landed`. Its Description names every sha in the
   card's `landing_shas`, both medians, the window, and the original card's id.
7. Rail 1 — **a revert card is never itself verified.** Write the revert's own state entry with
   `verdict: 'revert'` at the moment it is filed, so the loop cannot revert a revert. Assert it by
   running `daily` twice.
8. Rail 2 — **one revert per proposal.** The verdict closes the entry; a measurement still breached
   afterwards is a *new* proposal at `#n+1` going through `met_before` again like any other, which is
   Task 3's `propose` and needs no special case here.
9. Rail 3 — **no sha, no revert card.** A card whose `landing_shas` is empty gets the History line
   ending `landed without a traceable commit to revert` — use `facts.UNTRACEABLE`
   (`asf/scorecard/facts.py:180`), which already names this state, rather than a second spelling —
   and the verdict, and nothing else.
10. Rail 4 — **a broken probe never reverts** — is steps 4 and 7 together, and gets its own test
    rather than being left implied.
