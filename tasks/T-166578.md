**Steps**

1. `asf/kernel/ports.py`: a cloud session's observation is built from the same two refs and judged
   by the same `heartbeat.verdict` as a local one — the loop Task 3 landed already does this for
   every live run, so this step is the assertion, not an edit.
2. The one edit: a cloud session whose remote status reads terminal (`lifecycle.pid_alive` on its
   cloud token is `False`) but whose beat verdict is `alive` is **alive**, within
   `cloud.Settings.report_grace_min` of the run's end — the operator's 2026-10-11 ruling
   ("a run that reports SUCCEEDED while beats continue is alive"). Past that grace the existing
   verdict stands. The knob is read through `cloud.settings`, never re-declared (`K6`).
3. A cloud session whose status cannot be read is `unknown`, never stalled. Nothing in this step
   calls GitHub: the status comes off the ledger row and `cloudpid`'s record, as the port already
   reads it.
4. `asf/workers/cloud.py` and `asf/workers/remote.py` are in no footprint here: `cloud_brief`
   already appends `heartbeat.brief_lines` whenever `job.heartbeat` is set, so the cloud brief
   names the ref, the work-in-progress push and the interval from Task 2 alone, and
   `remote.report_grace` keeps its own behaviour for a floor run.
5. Create `tests/kernel/test_beat_cloud.py` with one case per acceptance line: the two-ref
   observation; a cloud session with branch pushes and no beat ref; one with a moving beat ref and
   no commit; the reported-but-beating case inside and outside the grace;
   `cloud.Settings.report_grace_min` still defaulting to 45; the unreadable status;
   the local job-log rule; the cloud brief's block; the lane's own keys overriding the workers
   block; and the floor's sync path asserted against its landed behaviour.
