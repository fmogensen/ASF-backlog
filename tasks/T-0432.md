The spec's §`asf/upgrade.py` down to `mid_landing`, D4, D5, D6, D7 and D12 — plus the correction
PD3, PD4 and PD5 all turn on. Everything here is a reader except the cache file and the `sha=`
parameter; no policy is consulted and no channel exists yet, so this Task changes no behaviour of
any product.

**Files**

- `asf/upgrade.py` — `RELEASE_POLL_S`, `RELEASE_RE`, `releases_path`, `latest_release`,
  `installed_release`, `version_tuple`, `newer`, `mid_landing`; `sha=` on `install`, `_install` and
  `refuses`, and `_ref_label`
- `asf/cli.py` — `latest_release()`'s remote branch routed through the cache (D12)
- `tests/test_release_channel.py` — `VersionComparisonTests`,
  `LatestReleaseIsReadOnceAnHourTests`, `MidLandingTests`, `TagInstallVerifiesByShaTests`
- `tests/test_install.py` — `LatestReleaseTests` (PD8)

**Steps**

1. `RELEASE_POLL_S = 3600` and `RELEASE_RE = re.compile(r'^v(\d+)\.(\d+)\.(\d+)(?:\+(\d+))?$')` at
   module level, with the spec's comments. `releases_path()` returns
   `os.path.join(env.ASF_HOME, 'state', 'releases.json')` — the exact shape `pending_path()` uses
   (`asf/upgrade.py:70-71`), one file for every product and for `asf status` (D4), written through
   the existing `_write_json` so the write is atomic and makes its directory.
2. `latest_release(url, now=None, run=subprocess.run)` → `(tag, sha)`. Read the cache; when its
   entry for `url` has an `at` younger than `RELEASE_POLL_S`, return its `tag`/`sha` and shell out
   to nothing. Otherwise `git ls-remote --tags <url> 'v*'` — **without** `--refs`, because the
   peeled `^{}` line is the commit an annotated tag points at and that sha is what PD3 and PD5 both
   need. Pick the greatest tag by `version_tuple`, prefer its peeled line's sha over the tag
   object's. Every attempt stamps `at`, successful or not; a failed read keeps the entry's previous
   `tag` and `sha` rather than forgetting them, so a dead network neither hammers the remote nor
   un-knows the release. `(None, None)` when nothing was ever read. The function never raises.
3. `version_tuple(text)` → `(major, minor, patch, past)` or `None` (D5): `v0.1.62` → `(0,1,62,0)`,
   `v0.1.62+7` → `(0,1,62,7)`. A plain tuple, not a string compare and not `packaging` — `v0.1.9`
   against `v0.1.62` is the string compare's classic wrong answer and `packaging` is not a
   dependency of this package. `+N` is ASF's own "commits past the tag", written by
   `cli._described_release` (`asf/cli.py:71-77`), and not a PEP 440 local version.
4. `newer(latest, installed)` is `version_tuple(latest) > version_tuple(installed)` with either
   side unreadable returning **False** (D6). An install whose release cannot be read at all is
   never upgraded on a guess: `__version__` is never bumped per release, so comparing against it
   would read as BEHIND forever and reinstall on every tick.
5. `installed_release()` → `(tag, sha)` of the running install: the tag from
   `cli._release(cli._checkout_root(), cli._direct_url())` — a git install's `requested_revision`,
   else a checkout's `git describe`, else the build stamp — and the commit from
   `drift.installed_commit()`. `(None, <sha>)` when the install records no release. Both are
   existing readers (P5) and nothing new is recorded at install time.
6. `mid_landing(product)` → `[(item, branch)]` from
   `lifecycle.occupancy(pool.sessions_path(product))['landing']` (PD14), sorted by item. The whole
   call is wrapped: any exception returns `[]`— and `[]` **holds** the install, it never clears it,
   so an unreadable ledger is the conservative answer. The docstring says which way round that is,
   because the return being empty means "nothing is landing" at the call site and the two readings
   of an error are opposite.
