§2.2. Three functions and one constant, all pure or nearly: `shipped` answers which Features reached
production in a window, `throughput` answers how many and at what mean cost, and
`record_throughput` is the pair of windows over one record. Nothing renders yet — Task 4 does.

**Files**

- `asf/metrics/metrics.py` — `ON_PROD_STAGE = 'on-prod'` beside `STREAMS`/`KINDS` (`:39-40`);
  `shipped`, `throughput`, `record_throughput` in the rollup section, after `subtree_cost`
  (`:375-387`) and before `esc` (`:389`); `from asf.record.ingest import ON_PROD_EVENT` beside the
  existing `asf.record` imports (`:34-36`).
- `tests/test_metrics.py` — `ShippedTests` and `ThroughputTests` (new).

**Steps**

1. `ON_PROD_STAGE = 'on-prod'` with the comment that it is the token `evidence.feature_stage`
   returns, not the card's prose "on-production" (§1.1).
2. `from asf.record.ingest import ON_PROD_EVENT` at module level — one owner for the kind string
   (verified acyclic: `asf.record.ingest` pulls no `asf.metrics` module).
3. `shipped(events, items, days)` exactly as §2.2 specifies, in three passes and with no clock:
   `seen = {}` over **every** event given, not the window's — `ev.get('kind') == ON_PROD_EVENT`,
   keep the newest `ts` per `item`, value `ts[:10]`; then for each Feature in `items` with
   `stage == ON_PROD_STAGE` and a truthy `stage_since`, `seen.setdefault(fid, stage_since[:10])`;
   then return `{fid: d for fid, d in seen.items() if d in set(days) and items.get(fid, {}).get('type') == 'feature'}`.
   The docstring says why the first pass is over the whole stream: an item an older event names
   must never fall back to `stage_since`, or it lands in both windows.
4. `throughput(items, costs, ids)` → `{'features', 'priced', 'usd', 'mean'}`. For each id,
   `subtree_cost(items, costs, iid)['usd']`; `features` counts every id, `priced` and `usd` only
   those whose `usd is not None`, `mean = usd / priced` when `priced` else None, and `usd` is None
   when `priced` is zero — never `0.0`, which would render `$0.00` and read as free work (§1.4).
   `max(1, …)` is not used; the `priced` guard is the one that keeps the division safe.
5. `record_throughput(root, items, day)` → `(week, prev, this_wk, prev_wk)` where
   `this_wk = days_back(day, 7)` and `prev_wk = days_back(day, 14)[:7]`. It reads
   `read_stream(root, 'events')`, `read_stream(root, 'ci')` and `read_stream(root, 'sessions')`
   **undated** — the cost is whole-life (§1.4) — builds `costs = compute_costs(ci, sessions)` once,
   calls `shipped` twice over the one event list, and `throughput` twice. The docstring names the
   whole-stream read as deliberate and points at P5's consequence for the fixture.
6. `ShippedTests`: the nine clauses of §3.2, each its own assertion — `F-0001`'s event in this
   window and not the previous; `F-0002`'s in the previous only; `F-0003` at `on-prod` with a
   `stage_since` and no event falling back into this window; `F-0004` at `on-prod` with a
   `stage_since` in this window **and** an older event landing in the previous window only and
   never both; two events for one id resolving to the newer day; a `T-0001` with the kind excluded;
   an id `items` does not name excluded; `stage: landed` with a windowed `stage_since` excluded;
   `stage: on-prod` with no `stage_since` excluded.
7. `ThroughputTests`: §3.3's five clauses — three priced ids → `{'features': 3, 'priced': 3,
   'usd': 37.20, 'mean': 12.40}`; a fourth unpriced → `features` 4 and the rest unchanged; all four
   unpriced → `mean` None, `usd` None, `priced` 0; no ids → zeros, `mean` None, no
   `ZeroDivisionError`; a Feature's cost summing its Stories, Tasks and Bugs. The last clause is
   the whole-life one and is P5's mechanism proved in isolation: the same record read with 7 days
   of streams and with 30 gives the same `features` and a larger `usd`.
