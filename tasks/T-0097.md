## Description
stories: S-15509
writes: asf/metrics/metrics.py, tests/test_metrics.py

§2.8: two scorecard rows over the `events` stream, median and p90 in whole minutes across the
rollup's 7-day window, counting only the pairs both ends exist for and saying how many it could
not measure. Independent of every other Task's writes, so it runs in wave 1 (PD13).

**Files**

- `asf/metrics/metrics.py` — `intake_latency_rows(events, conv=None)` (new);
  `scorecard_rows(ci, sessions, ticks, conv=None, events=())` (`:405`); `render_daily` reads
  `read_stream(root, 'events', week)` and passes it through (`:501`). `STREAMS` (`:37`) is not
  touched — `events` is not appended through the validated path (spec P9).
- `tests/test_metrics.py` — `IntakeLatencyTests` (new, §3/T10); `Rollup:319` for the rendered rows.

**Steps**

1. `intake_latency_rows(events, conv=None)` joins per §2.8's table: `intake → decided` from the
   `intake` event's `filed` to the first `groom_answer` with `field == 'decided'` and
   `value == 'true'` for that item; `decided → first session` from that `groom_answer`'s `ts` to the
   first `launch` event for the item at or after it.
2. Two rows in §2.8's shape — `median <n> min, p90 <n> min` and an `n of m` clause naming what could
   not be measured (a card decided outside the groom writes no event, §1.4, so it is counted out
   loud rather than guessed).
3. An empty stream divides by nothing and both rows read `no pairs measured`.
4. `scorecard_rows` keeps its positional signature and appends the two rows when `events` is
   non-empty, so every existing caller and test is unaffected.
5. `render_daily` reads the events stream for the same window it already reads the others for.
6. `IntakeLatencyTests` per §3/T10, over a synthetic stream: the right median and p90, the pair
   counting, the empty stream, `render_daily` rendering both rows, and `scorecard_rows` with no
   `events` argument returning exactly what it returns today.
