## Description
stories: S-33555
writes: asf/metrics/metrics.py, tests/test_quota_pressure.py, tests/test_metrics.py
after: Task 4

§2.5. This row is the card's first acceptance. Everything before it is instrumentation; this is the
one place a human meets the trigger, in the file `asf metrics rollup` rewrites every day (P15).

Two keywords on `scorecard_rows` and one row appended beside the `bandwidth` row that already speaks
for the pool. `render_daily` hands it the week it already computes for the cost table.

**Files**

- `asf/metrics/metrics.py` — `scorecard_rows(..., ticks7=None, day=None)`, the `quota pressure` row,
  and `render_daily`'s call
- `tests/test_quota_pressure.py` — `ScorecardTests`
- `tests/test_metrics.py` — the row through `render_daily`

**Steps**

1. `asf/metrics/metrics.py`: `scorecard_rows` (`:514`) gains `ticks7=None, day=None` as its last two
   keywords, with §2.5's docstring addition copied as it stands — `ticks7` is the window the
   `quota pressure` row reads and defaults to `ticks`, which for a one-day rollup is one day and so
   can never fire the trigger; `day` is that window's last day, and left unset it is the latest
   `ts` in `ticks7`.
2. The row goes after the `bandwidth` row (`:589-592`) and before the `intake_latency_rows` block
   (`:593-594`), exactly as §2.5 writes it: the window, the last day, the 5-tuple, the `—` branch
   when `measured` is empty with the reason *no tick in the window carries quota_held — the counter
   starts with F-0068*, and otherwise
   `f"{len(days)} of {len(measured)} measured days held ready work back — {verdict}"` with the note
   `f"{', '.join(days) or 'no day'} · {held} ready rows held, {seats} seats banded at the peak"`.
   The verdict is `the spike trigger has fired (F-0068)` or
   `f'under the trigger ({PRESSURE_DAYS} of {PRESSURE_WINDOW})'`.
3. `render_daily` (`:731`): pass `ticks7=read_stream(root, 'ticks', week)` and `day=day`. `week` is
   already computed at `:719` for the cost table, so this is one more `read_stream` of a stream the
   function already reads for one day — and it is the difference between a row that can fire and a
   row that cannot.
4. `tests/test_quota_pressure.py`, `ScorecardTests`: a week of hand-built tick lines with four
   pressure days renders the row with `4 of 7 measured days held ready work back — the spike trigger
   has fired (F-0068)` as its value, the four dates in the note in order, the summed `held` and the
   peak `seats`. Three pressure days also fire (the boundary is `>=`, and a test that only proves
   four is a test that would pass for a `> 3`). Two read `under the trigger (3 of 7)`. A week whose
   ticks carry no `quota_held` at all renders `—` and the reason, and **never** `0 of 7` — assert
   the absence of that string, because that is the failure D5 names. A window with some measured
   days and some silent ones counts `len(measured)` and not 7.
5. `ScorecardTests` also pins the default: `scorecard_rows(ci, sessions, ticks)` with no `ticks7`
   reads `ticks` — so a caller that has one day gets a row about one day and cannot fire a
   seven-day trigger off it — and `scorecard_rows([], [], [])` yields the `—` row rather than
   raising on an empty `max`.
6. `tests/test_metrics.py`: one case that the row reaches `render_daily`'s markdown — a fixture
   week of ticks written under `metrics/ticks/`, `render_daily` called, and
   `| quota pressure |` asserted present in the table with the verdict the fixture earns. This is
   the only assertion in this Feature that the row is in the file an operator opens.
