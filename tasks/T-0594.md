## Description
stories: S-37000
writes: asf/upgrade.py, tests/test_install.py
after: none

The spec's §1 — `upgrade-due.json` and the seven functions that own it — plus the two ends of
`install()` that write and settle it. Nothing else reads the record when this lands: `due()` has no
caller in the package until Task 2, `due_label()` none until Task 5, and `DUE_GRACE_S` does not
exist yet.

**What changes for the machine when this lands.** One new file appears in `~/.ASF/state/` the first
time a tick's upgrade is deferred by a busy floor, and one new line is printed there
(`upgrade: due 5cab3a2 — pass 1, owed by asf`). Nothing reads either, so no tick behaves
differently, no install is taken that was not taken before, and no product is parked that was not
parked before. A debt written while Tasks 2 and 3 are still unlanded is inert on disk and is
removed by the first `due()` call after them, or by any `install()` of that sha in the meantime
(`settle_due`) — it can neither park a product nor trigger an install on its own.

**Files**

- `asf/upgrade.py` — the module docstring gains the paragraph the spec's "In" names (the debt, its
  lifetime, and that it is *not* a park: paid by an install, cancelled by a refusal or a failure,
  never by age). New: `due_path`, `read_due`, `clear_due`, `_write_due`, `bump_due`, `due`,
  `due_label`, `settle_due`, placed together after `record_last` and before `_config_number` so the
  file reads park-then-debt-then-config. Changed: `install()`'s floor deferral (`:573-583`) gains
  the `bump_due` call, its tail (`:584-589`) gains `settle_due`, and `batch_hold`'s local `due` is
  renamed `at` (PD2). `pending()`, `held()`, `held_label()`, `write_pending()`, `cooling()`,
  `refuses()`, `drain()` and `_install()` are untouched.
- `tests/test_install.py` — `DueRecordTest(HomeCase)` added after `DrainTest`. No existing class is
  touched.

**Steps**

1. `due_path()` is `os.path.join(env.ASF_HOME, 'state', 'upgrade-due.json')` — beside
   `pending_path`, `expired_path` and `last_path`, the same shape as all three.
2. `read_due()` is the spec's: open, `json.load`, return the dict only when it is a dict with a
   truthy `sha` and an `at`, `None` on `OSError`/`ValueError`. **No clearing, no git, no
   `installed_commit`** — its docstring says so and names the views as the reason (P11: a
   `git merge-base` does not belong in a view, which is why `held()` skips the same check).
3. `clear_due()` is `os.remove` under a bare `except OSError: pass`, exactly as `clear_pending`.
   `_write_due(data)` is `_write_json(due_path(), data)` then `return data` — one writer, and the
   existing `_write_json` is already atomic (`os.replace` over a pid-named temp).
4. `bump_due(sha, owner, now=None)` is the spec's, verbatim in behaviour: a record for the same sha
   keeps its `at` and every other key and gains `owner=owner, passes=passes+1`; a record for a
   different sha, or no record, starts fresh at `passes: 1` with `at = now or time.time()` and
   **no `parked_at`/`loud`**. The docstring carries the spec's sentence about why it is never
   refused where `write_pending` is: a cool-down suppresses the *park*, and the debt is not a park.
   Note explicitly in the docstring that it merges over whatever is on disk and never writes
   `parked_at` or `loud` itself — Task 3's `draining()` owns those two, and PD4 is why that matters.
5. `due(installed=None, out=print, run=subprocess.run)`: `read_due()`, `None` out; resolve
   `installed` from `drift.installed_commit()` only when the caller gave none (the lazy import of
   `asf.drift` inside the function, as `pending()` does at `:181-183` — `asf.drift` imports
   `asf.upgrade`); `_installed(data['sha'], installed, run)` → `clear_due()` and `None`; else the
   record. **Never removed by age** — the docstring says it, and `DueRecordTest` asserts it at
   `10 * PENDING_TTL_S`.
