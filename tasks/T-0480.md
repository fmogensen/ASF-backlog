## Description
stories: S-33604

after: Task 3

The spec's seventh **In** bullet (D7) and its `## The design` §4. `why_not_as_is` already accepts
either lane kind and `Lane.adopt` already takes the document kind as an argument (P11), so what is
spec-only is `wanted`, three `'spec'` literals, the job name and two messages.

**Files**

- `asf/tick/land_spec.py` — `PLAN_JOB_PREFIX`, `DOCS`, `wanted`, `adopt`; the module docstring
- `tests/test_land_spec.py` — `LandTheApprovedSpec` extended, `LandTheApprovedPlan` (new class)

**Steps**

1. `PLAN_JOB_PREFIX = 'land-plan-'` beside `JOB_PREFIX = 'land-spec-'` (`:26`), which is **kept** so no
   product's ledger loses a job name it already carries (D7).
2. `DOCS = (('spec', ('spec-approved',), feeder_rows.spec_carrier), ('plan', ('plan-approved', 'building'), feeder_rows.plan_carrier))`
   — the spec's table, with its comment. The stage tuples are what PD9 rests on.
3. `wanted(items)` returns `[(feature id, carrier, doc)]`: the open/decided/unblocked/not-removed/
   not-moved filter at `:35-37` is unchanged, and the stage test becomes a loop over `DOCS` —
   `if stage_word in stages and (carrier := read(f)):` append the triple. Its docstring says
   "``[(feature id, branch the document is on, doc)]`` for every open, decided, unblocked Feature
   whose approved spec — or whose plan — is on a branch, not the trunk." The `sorted(...)` over the
   items is kept, so the order is the ids' and is stable.
4. `adopt` loops over the triples. `lane = feeder_rows.branch_for(product, doc, fid)`;
   `job = f'{JOB_PREFIX if doc == "spec" else PLAN_JOB_PREFIX}{fid}'.lower()`;
   `host.adopt(carrier, fid, doc, job=job)` on the clean path;
   `branch = carrier if product.conventions.branch_kind(carrier) == doc else lane` on the other.
   The `fid in owed` skip and both `spoken_for` calls keep their shape, with the second now reading
   **that document's** lane branch through the `doc`-derived `lane` (PD9).
5. Both printed lines and the `landing-gate` correction text name the document:
   `f'land-{doc}: {fid} — approved {doc} on {carrier} adopted by the lane'`, and
   `f'The {doc} for {fid} is approved but not on the trunk: it is on {carrier}, and {why}. Land the '`
   `f'existing approved {doc} on the trunk from {branch} — bring it over from {carrier} as written, '`
   `f"resolve what stops it merging, and don't rewrite it."`. `why_not_as_is`, the `LANDING_GATE`
   kind and the feeder's routing of that correction to a STARVED → SPEC/PLAN session need no change
   (P11) — asserted in step 7, not assumed.
6. The module docstring gains the plan: what it says about a spec that is approved but not on the
   trunk it now says about a plan at `plan-approved` or `building`, and it names both job prefixes.
7. `tests/test_land_spec.py`: `LandTheApprovedSpec` (`:30`) keeps every assertion and gains the third
   element of `wanted`'s tuples, asserted to be `'spec'`. `LandTheApprovedPlan` (new): a Feature at
   `plan-approved` with `plan on plan/f-0001` is named by `wanted` as `(fid, 'plan/f-0001', 'plan')`;
   a clean documents-only branch that merges is adopted PUSHED under the job `land-plan-<id>` (the
   job name asserted literally, lowercased); a branch carrying a `.py` file is adopted BACK with a
   `landing-gate` correction whose text names **the plan** and both branches; the same for a branch
   that conflicts with the trunk and for one that is no lane branch. Cases: a Feature at `building 1/3`
   is named too; one at `spec-approved` whose spec is off the trunk yields only the spec triple, and
   one Feature never yields two (PD9); a Feature that already `owed` a correction is skipped; a
   spec landing and a plan landing in one pass each get their own job and neither `spoken_for` skip
   takes the other's turn.
