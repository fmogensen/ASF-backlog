The spec's §3 minus its `update_for_merge` bullet — `Lane.flight`, `Lane.ci_deferred`, and the guard
at `repair_naming` (T13n), `drop_copies` (T13c) and `repair_signoff` (T13s). C7's point is the whole
of this Task: the launch deferring while the lane rebuilds the same branch minutes later is the same
supersede one call site over, so these two sites are one decision.

**Read PD2 before writing the `repair_signoff` guard**: `return None` there is a hold that sends the
branch BACK, not a wait — the return value is `DEFERRED` and its caller changes with it. **Read
PD6**: the guard is the last refusal at all three sites, not the first.

**What changes for the machine when this lands.** A lane branch with a `ci.workflow` run in flight
is not reworded and not rebuilt on the trunk: nothing is pushed, no `archive/<branch>-copies-…` ref
is written, the lane record's state and head do not move, one line is printed, and the next pass
re-asks. Its sign-off trailers are still repaired at once — unless it is S1 or hotfix, which waits
in `WAITING_CI`. For every product with no `ci.workflow` (P8: every product in the suite, and
`LaneFixture.product()` sets none) nothing changes at all.
