## Statement
Before calling a wave ready, or reading a red run as "just the gate", count how many jobs executed:
the code host's run command view <id> --json jobs --jq '.jobs[]|"\(.name) \(.conclusion//.status)"'. Say "n of m jobs executed", never
"CI red on X". A suite reported `skipped` has no evidence, not good evidence.

## Why
Every `ci` job is `needs: gate`, so a failing gate marks the downstream jobs `skipped`, not `failure`. On 2026-09-06
a slow job had never executed on the milestone branch (a CI run was its first real evidence), and on a milestone a slow job was
`skipped` on six heads; the container file fix repaired the gate and a slow job then failed at a journey spec:567 — a
pre-existing failure the broken gate had hidden.

## Check
None yet. The source check for this rule sources a shared library bound to one product's repository, state directory, branch naming and scheduled job, so it cannot be carried as it stands. It becomes a check when the rule runner reads those four facts from the product's configuration.
