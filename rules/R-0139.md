## Statement
When the branch being pushed is not the branch checked out, the checks are run against that
branch's own tree first — `git worktree add <dir> <branch>` and the package manager -s lint there — or the push
is made from a worktree that has the branch out. A green pre-push is never read as covering a
branch whose files are not on disk.

## Why
`.githooks/pre-push` runs its checks against `$(git rev-parse --show-toplevel)`, the working tree,
not against the commits in the push. The two normally agree, so the gap is invisible; they diverge
exactly when the pushed branch is not the checked-out one. On 2026-09-09
a CI-triggering branch was pushed from the main checkout after committing on `main`, moving
the commit to a branch and `git reset --hard origin/main`; the package manager -s lint passed because the two
new SVGs were no longer in the tree, and CI's gate failed in ten seconds on
`a11y/noSvgWithoutTitle`.

A gate failure's duration is a cheap discriminator: ten seconds means the first step (lint), about
600 s means it reached the home clock. Read the step timings with
the code host's API repos/<o>/<r>/actions/jobs/<id> --jq '.steps[]' before the logs, especially while the run
is still in progress.

## Check
None yet. The source check for this rule sources a shared library bound to one product's repository, state directory, branch naming and scheduled job, so it cannot be carried as it stands. It becomes a check when the rule runner reads those four facts from the product's configuration.
