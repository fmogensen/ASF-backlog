## Statement
A workflow `run:` step never pipes into `head`. the code host runs bash steps with `-eo pipefail`, so when `head` closes the pipe
early the writer dies with SIGPIPE (exit 141) and the step fails with no message. Take the first N lines with
`sed -n '1,Np'`, which reads to the end of its input. When a shell step dies saying nothing, suspect a killed pipeline
before the logic.

## Why
2026-09-09, a pull request: merging 241 commits of main into a stale branch made a 458-file push diff; the `changes` path
filter (every runtime job `needs:` it) exited 1 after printing 40 paths, and eight downstream jobs showed `skipping` —
a broken PR that looked partly green. It is a race, which is why a 68-file diff passed the same hour and the script ran
clean locally on the same input. Proof: `printf '%s\n' "$(seq 1 200000)" | head -1` → exit 141, `… | sed -n '1,1p'` →
exit 0. Fixed in a pull request at all four sites across both the CI workflow and a specialised workflow — the two workflows carry their own
differing copies of the classify step, and the run diagnosed was `computer`, so patching only the CI workflow would have missed it.

Folded in, the same job's second defect (2026-09-10, a pull request): a branch's first push has the null sha as
the code host.event.before, and the classifier ran everything; now it diffs from `git merge-base origin/main "$AFTER"` and fails
open only when that is missing too. the case classifier runs seven edge cases against each workflow's real `run:`
block as a gate step. Read a red `changes` with many `skipping` siblings as this class of bug, never the skips as passes.

## Check
