## Description

Measured on ASF's own build to 2026-09-23: **216 ended sessions, 195 hours, $267.49**. 106 of
those sessions — **69.2 hours, 35 % of all session time** — ended without landing anything.

They end for a small number of reasons, and each is a defect class with a fix, not bad luck:

| runs | how it ended | what it means |
| --- | --- | --- |
| 40 | `finished` | the session declared success and had nothing on its branch |
| 14 | `failed: empty branch: nothing to land` | the same thing, caught by the ledger |
| 14 | `failed: not pushed: N uncommitted file(s)` | work written, never committed |
| 8 | `stopped by operator` | a human had to intervene |
| 4 | `superseded: the work is on main` | the item was already done elsewhere |

The first three — 68 of 106 — are the same failure wearing three coats: **a session ends without
its work being on origin, and the factory finds out afterwards.** The answer today is a new
session (a `correct` row: 39 runs, 19.7 h), which pays the whole start-up cost again to fix
something the ending session knew about.

The fix is to make the end of a run a gate inside the run: the session cannot report finished
until its branch is pushed and its commits name its item, and if it is not, it is told so in the
same session while its context is still warm. The end record then carries the verdict as a field,
not as a string a regex has to read.

## Acceptance

- A session that would end with uncommitted files or an unpushed branch is told so in-process and
  gets one chance to fix it before the run is closed; the round counter does not advance.
- The end record carries typed fields — `pushed`, `commits_name_item`, `gate` — and `end_reason`
  is derived from them, not written as prose.
- `asf sessions` reports the non-landing share per week; the number is on the scorecard.
- A property test over the ledger: no run is recorded `finished` with an unpushed branch.
- Target, measured the same way in a week: non-landing session time under 15 %.

## History
- 2026-09-23 11:15 a cause found, and fixed in operator config: worker sessions ran with the
  default 120 s Bash timeout while the gate takes ~85 s and grows with the suite. A session a few
  seconds from a timeout backgrounds the gate, the background task dies with the run, and the work
  never reaches origin — `coder-t-0022` died exactly that way, and three more sessions ended
  `failed: not pushed` within one hour. `~/.claude-workers/settings.json` now sets
  `BASH_DEFAULT_TIMEOUT_MS=900000`. That is not the fix this card asks for: the end of a run must
  still be a gate inside the run, because the next cause will not be a timeout.
