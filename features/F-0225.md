## Description
The CI start queue counts a runner as free for a class even when it lacks the labels the waiting jobs ask for, and double-counts a just-started run for up to 3 minutes.

Evidence (botseon, 2026-09-28 04:31Z): `free_by_class` (asf/ci_queue.py:1103-1125) counted contabo heavies h1, h2, h4, h5 as free heavy, but most heavy PR jobs require `hetzner-heavy` + `class-pr-heavy`, carried only by ci-1..5. Result: the queue started cloud/T-0400 (run 36357648161) whose 7 hetzner-heavy jobs then sat queued behind bench/F-0120 on ci-1..5. Separately, the `started` ledger (Queue.free, asf/ci_queue.py:1767; prune after PICKUP_S=180s at :1201) is subtracted while the run's first job already holds a busy runner, so the run counts twice for up to 3 min (heavy read 0 free instead of 4 at 06:26 CEST).

Want: free slots per class computed against the label sets the product's jobs actually request (from the workflow's runs-on, or a conventions map), so a run is only started when runners that can take its jobs are free; and a ledger entry is dropped as soon as any of its jobs is seen on a busy runner.

Verify: a test with a fake runner table (hetzner vs contabo heavies) where a run needing hetzner-heavy is not started while only contabo heavies are free; and a test that a started run whose job is on a busy runner is counted once.
