## Description
Implements D-0049 for the `asf` product (and any product whose yaml sets `approvals.groom: auto`).

## Parts

1. `asf groom --auto`: every question class in D-0049's table answered by code, the answer and its
   reason written into the groom file's `answer:` slot, then applied (`--apply`) in the same run.
   The tick runs it in the record step.
2. Judgement calls: a `GROOM → ADJUDICATE` row — one session, cheapest model, the record as context,
   answers only the lines the rules left blank, written in the same slot; never edits cards directly.
3. Approvals matrix as code (F-0031): `approvals:` in the product yaml — action classes →
   `auto | inform | human-now`; the groom refuses to answer a `human-now` line and prints it as
   `NEEDS OPERATOR`.
4. Inform: the tick's digest (F-0078's "done since last tick" table gains a "decided" block) and a
   `notify:` command in the product yaml (`notify: <command>` receives the digest on stdin) — the
   operator's channel is operator config, not the factory's business.
5. Override: a card edited by the operator within 24 h of an auto answer wins; the groom never
   re-answers a line that carries `answered_by: operator`.

## Tests

Each rule row is one test on a fixture record; the adjudicate row on the fake runtime; the notifier
with a fake command; a `human-now` line stops with `NEEDS OPERATOR`.

## Part 6 — the switch (build first): `asf auto <level> | status --product <p>` → `/asf:auto`

Operator, 2026-09-22 09:50: "If we had an /asf:auto manual switch to turn on autonomy?"

- `asf auto on` writes `approvals: {groom: auto}` (later the whole matrix's default mode) into
  `~/.ASF/products/<p>.yaml` with `auto_since: <timestamp>`; `off` writes `operator`; `status` prints
  one line. The tick reads the field every run: `auto` → parts 1–5; `operator` → the groom writes its
  questions and waits (the 0.1 default).
- `asf status` gains the row `Autonomy | on since 2026-09-22 09:50 (groom) / off`.
- The plugin is generated from the CLI, so registering the command is what creates `/asf:auto`.
- A product with no `approvals:` block is `off`. Turning it off never undoes an answer already applied.

Levels, per product (operator 2026-09-22 09:55: "maybe the auto should be on a per project level"):

| Level | The factory decides | Still `human-now` |
| --- | --- | --- |
| `off` | nothing — the groom writes questions and waits (the 0.1 default) | everything |
| `groom` | the groom's answers (D-0049 rules + the adjudicate session) | spec/plan approval, prod, money |
| `deliver` | + spec and plan approval by check table and panel; landing to main | prod ✓ on customer-facing paths, money, credentials, releases |
| `full` | + the prod probe as closing evidence, releases | money, credentials, deleting history, anything leaving the machine |

`approvals.level: <level>` in the product yaml; each level is a named row set of the approvals matrix (F-0031). The levels are the plan's autonomy stages 0.1 → 0.2 → 0.3; a product climbs one when its scorecard earns it. `asf` starts at `groom`; the first adoption starts at `off`.
