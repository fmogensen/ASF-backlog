## Description
Operator, 2026-09-24: "make sure schema upgrades doesn't break anything for others when they upgrade". Decided; rank 1; blocks the release (F-0108) and the auto-update card.

Today (asf/schema.py): the record carries SCHEMA_VERSION (1); migrations are forward-only, numbered and idempotent; every writing command refuses on a mismatch (exit 3, NEEDS OPERATOR); `asf schema-migrate --drain` exists. Product and operator config files are validated strictly (an unknown field is a hard ConfigError). Gaps that would break other installs:
1. An upgrade that bumps SCHEMA_VERSION halts every writing command, the tick included, until a human runs schema-migrate. With auto-update, every customer's factory would silently stop.
2. Config fields are not versioned. A renamed or added field in a release breaks every install that has not edited its yaml, or makes an older install refuse a newer config.
3. Several ASF versions can share one ~/.ASF/config.yaml (on the author's machine one product runs the checkout's main while another runs a pinned release). A field only the newer version knows breaks the older one today.
4. Rollback after a migration: once a newer package migrates a record, reinstalling the older release (auto-update's rollback on a red doctor) refuses the newer record.
5. Tests: 1 test in tests/test_schema_version.py, and no test upgrades from a real earlier release.

## Acceptance
- [ ] **Migrate on upgrade, not by hand:** `asf upgrade` and the auto-update path run `schema-migrate --drain` for every installed product as part of the upgrade. The tick never stops on a pending migration it can run itself; it runs it (drained) and logs `migrate: schema a → b`.
- [ ] **Versioned config migrations:** config.yaml and products/<p>.yaml carry schema_version. Field renames and removals are migrations (MIGRATIONS for config, same rules as the record), applied on upgrade with a backup. Renamed fields keep being read, with a deprecation warning, for at least one minor version (as feeder.capacity → capacity.per_product did).
- [ ] **Tolerant reader across versions:** an unknown field is a warning (doctor row, "written by a newer asf?"), not an error, whenever the file's schema_version is newer than the package's. A typo in a known-version file stays an error.
- [ ] **Rollback-safe:** migrations are additive within a minor version, so the previous patch release still reads a migrated record. A migration that cannot be additive bumps the minor version, snapshots the record and config before running, and `asf upgrade --to <older>` restores the snapshot.
- [ ] **Upgrade test from every release:** CI job `upgrade-matrix`: for each released tag (v0.1.0, v0.1.1, …), install that tag into a temp HOME, set up `sample/` and tick once, upgrade to HEAD, then doctor green, one tick green, and the record migrated. Plus a mixed-version test: two products at different installed versions sharing one config.yaml both stay green.
- [ ] Release checklist (F-0108): a tag is cut only when upgrade-matrix is green, and each release's notes list its migrations.
