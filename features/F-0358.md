## Description
## Description
Review loops converge. On 2026-10-12/13 Tasks took 3 to 7 fix rounds and the console ruled on about twenty of them. Causes observed: weak tests found late; reviewers contradicting an earlier review or an operator ruling; findings repeated from an older head; a finding the author could not close because the file was outside `writes:`; a final fix commit that never got a review; an operator answer cut to 500 characters in the brief.

## Acceptance
- [ ] Before a review is launched, code proves each acceptance test is red on the base and green on the head; a PR that fails the proof goes back to the author without spending a review.
- [ ] A finding records the head it was found on and a stable key. A finding already closed, or ruled on by the operator, cannot be raised again; two findings that contradict each other on the same line escalate once to a ruling instead of alternating.
- [ ] A finding that names a file outside the Task's `writes:` is turned into a writes request the kernel grants by rule (a test or fake that only proves the Task) or routes to the console; it never loops as a finding.
- [ ] The round limit counts only rounds caused by the author: a red that is also red on the trunk, a session that ended without pushing, and a rebase charge no round.
- [ ] After the last allowed round the kernel always runs one review of the final head; it never marks Stuck on an unreviewed head.
- [ ] Operator answers reach the next brief whole (no 500-character cut), newest first.
- [ ] Measured over 24 hours: the share of review verdicts that are "changes" is at most 30% (57% on 2026-10-12), and no item exceeds 3 rounds.
