## Description

D-0050 says every saving spotted becomes a card with a number behind it. It ran today because
Frank asked "did you run the auto improvement cycle?" — not because anything runs it. A rule only
a session remembers is not a rule (D: code beats memory).

The data it needs already exists and is already written every tick: the session ledger
(`~/.ASF/state/<product>/sessions.jsonl` — start, end, kind, model, minutes, end reason,
harvested), the cards' `cost` blocks (sessions, fix rounds, USD), and `metrics/daily/`. The pass
is arithmetic over those three, and today it produced four ranked cards in one sitting.

`asf improve` is a tick step that runs weekly: it computes the same table — session time that
landed nothing, hours and spend per kind and per model, the items that took three sessions or
more and their share of spend, minutes per landed item — compares it with the previous run, and
writes `improve/<date>.md` with (a) the numbers, (b) the movement since last time, and (c) a
proposed card for every class above its threshold, each carrying the measurement that justifies
it. The cards are proposals: the groom presents them, the operator's autonomy level decides
whether they are filed automatically.

## Acceptance

- `asf improve --product <p>` prints the table and writes `improve/<date>.md` in the record.
- It proposes a card per class over threshold, each with the measured number in its Description
  and a `source:` naming the measurement, and files nothing the record already holds (an existing
  open card on the same class is bumped with the new number instead).
- The tick runs it weekly; a week with no class over threshold writes the table and no cards.
- The first run reproduces today's numbers from the same ledger: 216 ended sessions, 35 % of
  session time landing nothing, 23.7 Opus hours in adjudication.
- The scorecard's first line carries the two numbers this exists to move: non-landing session
  share, and USD per landed item.
