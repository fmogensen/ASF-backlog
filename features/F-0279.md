## Description
A review that ends "needs input" because its heartbeat could not start parks the PR for good. The review brief makes the heartbeat loop a precondition. When the session's sandbox refuses it ("Unauthorized Persistence", or a git-common-dir outside the sandbox), the review ends with no verdict, the relaunch cap counts it as an unchanged cause, and the row is parked with seats free. Seen 2026-10-07 on ASF: B-0351 (#926), T-0312 (#878), T-0745 (#848) and T-0248 were parked, and T-0528 hit its cap of 6 in 24 h. The liveness hotfixes (F-0265) make the runtime the beat, but the local brief still asks for the loop.

The real block is structural, and I verified it by reading the code, not by taking either side's word for it: asf.feeder.rows.needs_stories (rows.py:428) refuses any plan session for a Feature until the record holds an open Story child (has_stories, rows.py:423); but asf.record.plan_tasks._mint only turns a spec's declared `### S-nnnnn:` headings into Story cards for a Feature whose plan is already on the trunk (the `candidates` collection at plan_tasks.py:137-152 requires plan_ref(fev), and only then is specs[fid] populated for the declared-Stories read at plan_tasks.py:192-213). A cloud session has no record reach to mint a Story card directly (asf new story) the way CHANGELOG.md:749's spec-amend design normally does, and the fallback it takes instead -- declaring Stories as spec text -- only pays off once a plan lands, which the gate refuses until a Story exists: no session launched on this card, cloud or otherwise, can close that circle by itself. That is a one-time operator decision, not a question that should cycle through more sessions, so I am not filing it as another needs-input; I name the two ways out and recommend one. Recommended: an operator runs `asf new story --parent F-0279 --title <title> --acceptance <lines>` on the record host, once per Story, using the three blocks already under docs/specs/f-0279.md's `## Stories` section verbatim for title and acceptance text -- this touches only F-0279. Because `asf new` assigns the next free id from whatever block is live at call time rather than S-74454/55/56, the spec's `## Stories` and frontmatter `stories:` list must then be re-pointed at the ids it prints, in a short, ordinary spec-amend commit, before any plan session starts -- otherwise plan_tasks._mint would later read the old S-74454/55/56 as still-undeclared and mint three more Story cards on top of the real ones. The alternative -- setting conventions.feeder.stories_before_plan: false for this product so the first plan can be drafted and land, minting the three declared Stories through the designed path (F-0285) with no id to re-point -- is simpler to execute but drops the stories-first gate for every other Feature in the product, not just this one; I don't recommend it unless the operator judges that product-wide exposure acceptable.
