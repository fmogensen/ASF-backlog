## Description

The factory knows two relations and needs three. It knows **containment** (`parent:` — Epic →
Feature → Story/Task/Bug, with children and backlinks derived) and it knows **file footprints**
(`writes:`, which decides what may run at the same time). It does not know **order**: that one
item's output is another item's input.

`after:` exists on the Task card since 2026-09-22 and the feeder honours it, but nothing produces
it. It is typed by a human who noticed. F-0075 is what that costs: its plan states the order in
prose — task 8353 creates `asf/hooks.py`, 8354 calls it; 8352 creates `asf/redact.py`, 8354 and
8357 call it — and the feeder, seeing disjoint `writes:`, launched all of them at once. Three
branches went red for a reason no session on them could fix. T-0026 alone spent 7 sessions and
$6.49 discovering it, and its adjudicate session wrote the correct answer as a paragraph that no
code can read.

Order becomes a derived relation, in four layers:

1. **Declared** — `after: [id, …]` on every item type, not only Tasks.
2. **Written by the planner** — when the planner emits a plan's task table it emits the order it
   already states in prose; a plan whose steps name each other produces `after:` on the cards.
3. **Checked before launch** — preflight reads the task's own brief and plan step for modules,
   files and symbols that no landed item provides, and holds the row rather than launching it.
4. **Recorded when discovered** — a session or an adjudication that finds a missing predecessor
   writes `blocked_on: <id>` on the card; the tick shows it as one WAITS ON line, and the item is
   not relaunched until the predecessor lands.

## Acceptance

- `after:` parses and is honoured on every item type, not only Task.
- A planner run over a plan that names its own order produces cards carrying `after:`, proven on
  `docs/plans/f-0075.md` — the plan that caused this — as a fixture.
- Preflight holds a row whose brief names a module no landed item provides, with the predecessor
  named in the reason; a property test asserts no launched row has an unlanded predecessor.
- An adjudication that finds a missing predecessor writes `blocked_on:` and the tick prints it;
  no ruling about order lives only in prose.
- The tick's tables show `WAITS ON <id>` for every held row, as they do today for `after:`.

## Non-goals

- Inferring order from the code itself (static import graphs over unwritten code).
- Cross-product dependencies.
