## Description
When Stories are very small the overhead of the gates costs more than writing the code. The answer is size class and train cutting by code, with no model deciding either. (1) Size class from the Task's own data — the file count of its `writes:` footprint and its kind (docs, test, config, copy, code): small is at most three files with no migration and no new route, medium at most fifteen, large the rest; the thresholds live in the product's configuration. (2) One open train branch per lane, per product; a small Task's coder commits onto the current train (one commit per Task, the Task id in the subject) instead of its own branch. (3) The tick's train cutter opens the train's pull request when it holds six Tasks or its first commit is two hours old — one path-scoped CI run, one review whose check table covers every Task's proves lines, one merge. (4) A red Task never holds the train: the cutter reverts that Task's commits, re-runs, and re-queues the Task alone as medium. (5) Medium Tasks keep their own pull request; large Tasks are unchanged.

## Acceptance
- [ ] every Task carries a derived size from its footprint and kind, with the thresholds in configuration
- [ ] small Tasks land on their lane's train branch, and the cutter opens the pull request at six Tasks or two hours
- [ ] one CI run and one review per train; a red Task is reverted and re-queued alone
- [ ] runner minutes per merged small Task fall by at least 60 % over two weeks

## Non-goals
Any model deciding a size or a cut; trains that span lanes.
