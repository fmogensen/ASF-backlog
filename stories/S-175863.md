## Acceptance
- [ ] [ ] kernel launch carries max_holders with a default of 2, validated as an integer, and Config reads it
- [ ] [ ] a Ready item whose writes overlap exactly one item in flight is launched, where today it is held
- [ ] [ ] a Ready item whose writes overlap two items in flight is held, and the plan queues it as an overlap
- [ ] [ ] max_holders set to 1 reproduces today's behaviour exactly, holding the first overlapping candidate
- [ ] [ ] the cap counts items launched earlier in the same tick, so one tick never launches more than max_holders on one file
- [ ] [ ] a launch that joins a held file carries one shared files finding naming every shared path and every other holder
- [ ] [ ] the shared paths and the holder ids in that line are sorted, so the same tick produces the same line twice
- [ ] [ ] a launch with no other holder carries no shared files finding at all
- [ ] [ ] the brief of a launch that joins renders the notice under a Shared files heading of its own
- [ ] [ ] that notice is not rendered under the review findings heading, and a fix round's review findings are untouched by it
- [ ] [ ] the notice is split out before the appended text cap is applied, so it can never push a review finding out of a brief
- [ ] [ ] a fresh build launch carrying only a shared files finding is still a coder brief and not a fix round
- [ ] [ ] a risk high item whose writes overlap an unlanded PR still waits for it to land, unchanged by the cap
- [ ] [ ] the three landed cases named in the spec's A3 table are updated to assert the cap rather than the old refusal
