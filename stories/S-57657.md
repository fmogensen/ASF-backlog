## Acceptance
- [ ] `step_wave` emits one `launch` event per launched job, keyed on the job, carrying `item`, `job`, `branch` and `account` as `a<n>`
- [ ] `step_harvest` emits one `merge` event per landed branch, keyed `<branch>@<sha>`, carrying `item`, `branch`, `fields.sha` and `fields.trunk`
- [ ] a status file written by an older `asf`, carrying `merges: 3` and no `landed` list, emits three `merge` events keyed `legacy:<started>:<n>`, so the tick's count stays true across the upgrade instead of reading 0
- [ ] `step_health` emits one `relaunch` event keyed on the new job name, carrying the old job as `job`, the `item`, and the reason as `text`
- [ ] `step_health` emits one `stall` event per stalled session, keyed `<tick>:<job>`, carrying `item` and the reason as `text`
- [ ] `approvals` emits one `refusal` event per open hook refusal, keyed `<tick>:<item>/<class>`, carrying `fields.class` and `fields.path`
- [ ] the `ctx.counts[…] += …` line is gone from all five of those sites
- [ ] a `stall` and a `refusal` for the same open condition at two different ticks are two lines, not one, because the tick is in the key
- [ ] a retried tick re-emitting the same events adds no second line for any of the five kinds
- [ ] no event line carries an account name or a machine path — `account` is `a<n>`
