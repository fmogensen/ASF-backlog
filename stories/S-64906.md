## Acceptance
- [ ] step_wave.launch over a paused product never calls _wave — the launcher is patched to fail the test if it is reached, which closes the local lane, the cloud lane and the S1 row at once
- [ ] every launching row of the paused plan prints one 'waits ... — held: launches paused: <reason> (by <who>, since <at>)' line, the S1 row among them and with the same reason — no bypass
- [ ] the paused step's last word is the 'wave: ... — no new session this tick; recording and harvesting go on, and the sessions in flight finish and land' line, and launch returns 0
- [ ] a paused event carrying the reason, the author, the at and the count of held launching rows is on the events stream once per tick
- [ ] under the pause lane_pass was still called and push_deferred still ran, so a finished branch still moves to GATE and its ref pushes still reach origin
- [ ] the same case with no pause does call _wave, which is what makes the held half mean anything
- [ ] step_health.handle_dead on a dead session of a paused product returns 'paused', never calls stall.correct_once, and prints a DEAD line naming the item and that it goes back to its own row
- [ ] that held cold retry emits no held event, leaves ctx.counts['relaunches'] at 0 and writes no round to the ledger, so the pause never walks an item toward an ADJUDICATE row
- [ ] an unpaused tick's wave and health steps are unchanged — proven by tests/test_tick_steps.py
