## Description

## Acceptance
- [ ] a clock launchd holds whose state is running gets one line saying the bootout ends this tick, before the bootout reaches launchctl
- [ ] the install polls launchd after the bootout and bootstraps only once the label has left the domain
- [ ] that clock is loaded when the install returns, where the bootout-then-bootstrap order loses it
- [ ] the line after a successful wait names the seconds the install waited
- [ ] a label still held when the bound passes is bootstrapped anyway, with one line saying it was still loaded
- [ ] a first install of a clock launchd holds nothing of enters no wait and prints the two lines it prints today
- [ ] the wait returns at once with its waited seconds the moment launchd no longer holds the label
- [ ] the wait returns not-gone with its waited seconds when the bound passes with the label still held
- [ ] the wait spends no real seconds in a test, because its sleep and its clock are injected
- [ ] the bound and the poll interval both come from the operator config when it sets them, and from the module constants when it does not
- [ ] a reinstall of a clock launchd holds idle enters the wait, finds it already gone and prints no wait line at all
- [ ] the host clock's two successive installs print the same number of lines, as they do today
- [ ] the bootout is still issued before the bootstrap, for every clock, with the read that decides the wait in front of both
- [ ] the fake launchctl holds what it bootstraps and releases what it boots out, so the suite models a launchd that can be waited for
- [ ] a paused clock still has its plist written and is still never loaded — proven by tests/test_scheduler.py
