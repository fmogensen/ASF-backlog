## Acceptance
- [ ] lifecycle.pending_on_branch(path, item, branch, run) returns the newest pending correction found on an older run of the item when the branch's newest run carries none — the P2/P3 case where pending_correction(by_branch(path)[branch], path) answers None
- [ ] A correction naming branch Y is not returned for branch X: item-wide is how it is found, branch-scoped is how it is applied
- [ ] A correction naming no branch, sitting on a run whose own branch is this branch, is returned
- [ ] A correction naming no branch, on a run that names no branch either, is returned
- [ ] The item park is never returned by pending_on_branch, whatever its age — it speaks for the item and the feeder's PARKED row speaks for it
- [ ] A run that a branch park or a job park holds (scoped_park_of) is skipped
- [ ] With no item — an adopted or foreign branch no card claims — pending_on_branch answers pending_correction(run, path), and None when that run carries none
- [ ] lane.branch_facts sets its 'correction' fact from pending_on_branch, with no 'if run else None' arm, so the lane sees a ruling recorded on an older job of the item
- [ ] lifecycle.occupancy reads the same call at its three pending_correction sites, so an item whose landing-wait branch owes a correction is in neither occupancy['landing'] nor occupancy['waiting_landing'] and rows.occupied no longer holds it
- [ ] pending_correction's own answered rule is untouched: a session run of the item started at or after the correction still answers it and the row disappears — proven by tests/test_correct.py
- [ ] The same-run path that works today still works: a correction on the branch's own newest run still turns a WAITING_CI lane record BACK and leaves the item out of occupancy's busy and landing — proven by tests/test_correct.py
