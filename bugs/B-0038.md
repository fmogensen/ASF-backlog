## Symptom
Every run of the `tests` workflow on `main` is red from the first run (2026-09-21 16:08Z) onwards. Job `tests (3.12)`: five to six `tests/test_harvest.py::HarvestTests` cases (`test_green_branch_lands_on_main`, `test_non_machine_conflict_is_held`, `test_failing_tests_are_held`, `test_index_json_only_conflict_is_resolved`, `test_dry_run_prints_and_does_not_push`, `test_reap_holds_for_live_pid_and_for_no_finished_line`) fail with `'HARVEST OK ff1' not found in ''` — `run_harvest` printed nothing. The same commits are green on a developer machine. Because the 3.12 job fails, fail-fast cancels `tests (3.13)` in every run, so the 3.13 job has never completed. A red main blocks every Bug close (D-0047).

## Cause
`tests/test_harvest.py::make_repo` builds the fixture with `git init -q --bare origin` and `git clone`, then commits and pushes `HEAD:main`. The clone's first branch is whatever `init.defaultBranch` says; a developer machine with a system gitconfig setting it to `main` gets `main`, the CI runner (no such setting) gets `master`. `add_job_worktree` then runs `git worktree add -q -b worker/<job> <path> main`; with no local `main`, git resolves `main` from `origin/main` and checks out a tracking branch `main` instead of creating `worker/<job>`. `harvest.worker_branches()` finds no `worker/*` branch, the loop in `run_harvest` has nothing to do, and the assertions read an empty stdout. Sibling fixture `ProductHarvestTests` already uses `git init --bare -b main` and is green in CI; `make_repo` did not. This is a fixture defect, not a harvest defect.

## Fix
`make_repo` creates the bare origin with `-b main` and pins the clone's unborn HEAD to `refs/heads/main`, so the fixture is on `main` regardless of the host's `init.defaultBranch`. A new failing-first test runs the fixture with an empty global gitconfig and `GIT_CONFIG_NOSYSTEM=1` and asserts the clone's branch is `main` and `add_job_worktree` creates the `worker/` branch — this fails on every host before the fix and pins the invariant.
