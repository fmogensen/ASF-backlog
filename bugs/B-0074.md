## Symptom

`T-0010` and `T-0011` landed on main at 19:07 (`cada650`, `ee8dfff`), CI green, their branches deleted by harvest. Forty minutes and three ticks later both cards still read `state: Active`, `evidence: ['branch task/T-0010']`. `T-0001`, landed the same way, reads `Closed` with `commit e90acef names T-0001`. Their Features (F-0085 `building 0/6`) therefore cannot close although a third of their work is on main.

## Cause — proven, not guessed

The evidence pass itself is right:

    T-0010 {'branches': [], 'commit': 'cada650…', 'green': True}

so `id_state()` would say `Closed`. But `asf/record/ingest.py match_task()` matches the Task against its **plan's** task table first and returns that table's evidence (`branch <name> exists`, ingest.py:267-269), and the plan-derived line wins over the id evidence for Tasks. The plan's table is written when the plan lands and never says "landed", so a Task matched by its plan can only ever be `Active`. `T-0001`'s plan does not list it under that alias, so it fell through to the id evidence and closed correctly.

## Fix

Id evidence with a commit on the trunk outranks every other source for any item type: in `ingest`, compute the id evidence first; when it yields `Resolved`/`Closed`, that is the state and the plan-derived lines are appended as context, not as the verdict. A plan's `branch … exists` line may only produce `Active` when there is no commit naming the item. One rule, all types (D-0047: the evidence is the commit and the green run).

## Tests

`test_a_task_with_a_landed_commit_closes_even_when_its_plan_lists_the_branch`; `test_a_task_with_only_a_branch_is_active`; keep the plan-matching tests green.

## Acceptance

`T-0010`, `T-0011` and every task landed since read `Closed` with `commit … names …` after one tick; `F-0085` shows `building n/6` with n = the landed tasks.
