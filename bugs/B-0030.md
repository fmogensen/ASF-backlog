## Symptom

Seen twice on 2026-09-21 (the card was filed as "predicted"; it was already happening).

- The tick that started about 18:38Z (four branches held by the gate) ends with `tick: state committed, push refused — re-derived next run (<state>/record)`.
- The tick that started about 19:33Z and landed five branches (`landed fix/B-0010 → 9136269…` … `landed fix/B-0026 → 7c12bea…`) ends with the same line.
- `metrics/ticks/2026-09-21.jsonl` on origin has no line for either tick: it jumps from 18:28:40Z to 19:29:18Z and stops there. Their `launch` events and the two `harvest gate red` Bugs the first one filed are gone with them (the next tick re-filed the same signatures as B-0034 and B-0035).
- What moved origin each time: hand commits to cards (18:36Z, 18:54Z, 20:04Z) pushed while the tick ran. With ticks of 25 minutes (B-0031) the window is the whole tick.

## Cause

Verified 2026-09-21 against `origin/main` (7c12bea).

- `asf/tick/shadow.py:102-107 push()`: one `git push -q origin HEAD:<default branch>` with `check=False`, returns `returncode == 0`. Its docstring declares a non-fast-forward refusal "not an error: the clone is derived state, the next run resets it and re-derives".
- `asf/tick/tick.py:168-180 commit_and_push()` prints the refusal line and returns 1. On the next tick `asf/tick/shadow.py:71-74 ensure_clone()` runs `fetch`, `reset --hard origin/<branch>`, `clean -fdq`: the refused commit — and every line appended in it — is discarded.
- The premise is false for the appended streams. `Context.event()` (`tick.py:132-141`) appends to `metrics/events/<day>.jsonl`; `write_tick_line()` (`tick.py:283-294`) appends to `metrics/ticks/<day>.jsonl`; `harvest.file_gate_bug()` (`asf/harvest/harvest.py:629-642`) writes cards. None of that is re-derivable; only ingest, rollup and index output is.
- NOT the cause: a hook on origin (none — the same origin took the next tick's push); the factory identity (`ensure_clone` sets it, `commit_local` succeeded: the line says "committed"); the shared checkout of B-0013 (resolved — the tick works in its own clone).

## Fix

`asf/tick/shadow.py push(path, out=None)` — keep the bool contract, add one recovery:

1. Push as today. Success → `True`.
2. On refusal: `git fetch -q origin` (`check=False`; a failed fetch → `False`, as today). Then `git merge-base --is-ancestor origin/<branch> HEAD`: rc 0 means origin has not moved — the refusal has another cause (hook, unreachable) → return `False`, behaviour unchanged. rc ≠ 0 means origin moved → `git rebase origin/<branch>` (`check=False`). Rebase rc 0 → push once more and return that push's success. Rebase rc ≠ 0 → `git rebase --abort`, return `False` (a conflict is not resolved here; the tick prints the existing refusal line and that tick's streams are lost as today — the docstring says so).
3. When the second push succeeds and `out` is given, print one line: `tick: origin moved during the tick — rebased onto origin/<branch> and pushed`.

- `asf/tick/tick.py commit_and_push()` calls `shadow.push(path, out=print)`; its two existing lines stay verbatim (tests assert them).
- Every new git call in `shadow.py` passes `check=False` — `_sh` (line 22) raises on non-zero by default.
- Docstrings: `shadow.py` module docstring (lines 3-5, "a stray local commit … is discarded") and `push()` (103-105) describe the rebase-once rule and the conflict case.

Must NOT change: `ensure_clone()`'s reset-hard on the next run (a commit whose push finally failed is still discarded — `test_refused_push_exits_1_then_next_run_resets_the_stray_commit` and `test_stray_local_commit_is_reset_and_tick_proceeds` stay green); `commit_local`; `_default_branch`; the exit code 1 on a refused push; the shadow tick (`--shadow` never pushes).

Config keys: none.
