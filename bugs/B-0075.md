## Symptom

`T-0013` failed twice in a row the same way: the worker ran the suite as a **background task**, ended its turn with "Waiting for the background full-suite run to finish; I'll pick up … and push once it completes", and left three files uncommitted, nothing pushed. Four background-task notifications in its log. The same shape closed B-0052 this morning and it is still happening (also seen on B-0005, B-0016, B-0039, T-0027, T-0053).

The correction loop catches every one — but a task that bounces twice costs 20 minutes and two sessions' money, and the feature behind it stops.

## Cause

The brief forbids it in prose (`asf/briefs/build.py TAIL`: "Never start a background task you do not wait for"). A prose rule is a suggestion: the runtime still offers the background-task tool, and a model under time pressure uses it. Nothing mechanical prevents it.

## Fix — three layers, in this order

1. **Take the tool away.** The workers' settings deny the background-task tool and `Bash(* &)`; the operator file now has it (`~/.claude-workers/settings.json`), and `asf doctor` gains a row "worker settings deny background work" so a new install cannot forget.
2. **Judge at the source.** The runtime's result reader marks a result whose text matches "waiting for … background" as failed with `background work left running`, so the run never counts as finished even if a push happened to exist (today it is caught only by the unpushed-work rule).
3. **Re-cut, do not re-run.** A task that fails twice with the same reason is not corrected a third time: it goes to adjudicate with `same failure twice` so a session re-cuts the task rather than repeating it (D-0048's rounds are per attempt, not per cause).

## Tests
