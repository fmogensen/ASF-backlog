## Symptom

The first scheduled full-lane tick (2026-09-21 20:28) printed `harvest: none to land` while `origin/fix/B-0024` (`af619a2`) and `origin/fix/B-0026` (`d01bbaa`) sat finished on the product repo. Their registry lines read `ended … end_reason: dead pid`, then `corrected: 1` — and stayed there, although both job logs end in a `type: result, subtype: success` line.

## Cause

The runtime writes `system` lines (`background_tasks_changed`, `task_updated`, `task_notification`) *after* the `result` line when the session used background tasks. `asf.workers.runtime.read_result` accepts a result only on the log's last line, so a finished session reads as "no result"; with its pid gone, `health()` judges `dead pid`. Two follow-on gaps keep it there:

1. `health()` skips every session that already has `ended`, so a `dead pid` judgement is never revisited even when the log plainly ends the run with a result.
2. `step_health.handle_dead()` then runs `correct_once()` on a session that had already finished; on success it records only `corrected: 1`, never the outcome, so `harvest.is_eligible()` (which wants `rc: 0` or `end_reason: finished`) refuses the branch forever.

Seen on `fix-bug-b-0024` (result at line 64 of 83, three `system` lines after it), `fix-bug-b-0026` (line 150), `fix-bug-b-0002` (line 85 of 88).

## Fix

- `read_result`: the result of the **last run** in the log — the last `type: result` line after the last `system/init` line; trailing `system` lines do not hide it.
- `health()`: a session with `end_reason: dead pid` and no `harvested` mark is re-read every tick; when its log now carries a result it is re-judged `finished` or `failed` (one `re-judged` line).
- `handle_dead()`: after `correct_once` returns, the outcome is recorded on the session — `end_reason: finished, rc: 0` on ok, `end_reason: failed, rc: 1` otherwise.
- Failing-first tests: `tests/test_workers.py` (result followed by system lines; re-judge), `tests/test_tick_steps.py` (corrected session is finished).
