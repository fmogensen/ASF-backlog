## Symptom

Eight coder sessions finished and pushed (`task/T-0001`, `T-0003`, `T-0007`, `T-0008`, `T-0010`, `T-0011`, `T-0017`, `T-0024`); two ticks later harvest had landed every `plan/` branch and none of them. `harvest: 4 branches eligible` never counted a Task branch. The Tasks stay New, the Features stay `plan-approved`, the lane's last mile never runs.

## Cause

The feeder names a coder's branch `branch_for(product, 'task', id)`: no convention carries a `task` prefix, so the fallback is the kind itself — `task/`. Harvest scans origin for the conventions' prefixes only (`code: worker/`, `fix/`, `spec/`, `plan/`); a `task/` branch is invisible to it, finished or not. Two readers of "the code lane's branch" disagreed.

## Fix

- The feeder's PLAN → CODE rows (and a Task's CONFLICT → REBASE / STALE → CLOSE rows with no recorded branch) use the **code** lane's prefix — `conventions.branch_prefixes.code`, `worker/` by default; `branch_for` falls back to the documented default for a kind before the kind's own name.
- Harvest scans, beside the prefixed branches, every branch the registry knows (`sessions_by_branch`) that is on origin — so the eight `task/` branches already pushed land, and a branch under a prefix nobody named never hides again.

Tests: `tests/test_feeder.py` (every PLAN → CODE row's branch is `worker/…`; the golden `next-s1-held.md`), `tests/test_harvest.py::ProductHarvestTests::test_b0067_a_branch_the_registry_knows_is_harvested_whatever_its_prefix` (a finished `task/T-0001` lands; an unknown, unprefixed branch is not the lane's).
