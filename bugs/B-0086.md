## Description

The scheduled tick runs `/Users/frank/Library/Application Support/pipx/venvs/asf-factory/bin/python
-m asf.cli`. The repository at `~/Code/fmogensen/ASF` is a different copy. Nothing compares them.

Today six fixes landed on the trunk — B-0077, B-0078, B-0079 (twice), B-0081, B-0085 — and none of
them were in the running factory. The lane kept behaving as it had that morning: `harvest: none to
land` beside pushed branches, corrections blocking the tick for an hour, `wave: nothing to launch`
while `asf next` in the checkout offered three rows. Hours were spent reading those symptoms as new
defects when the fixes for them were already merged and simply not installed.

A factory that builds itself must know which version of itself it is running. Nothing else in the
day cost as much as this one silent gap.

## Acceptance

- Every tick's first table line names the running package version and the trunk's head, and says
  `BEHIND by <n> commits` when the installed copy is older than the record's product repo.
- `asf doctor` reports the same, as a row that goes red on drift.
- A landing on the trunk that changes the package proposes its own upgrade: the tick prints
  `UPGRADE AVAILABLE <old> → <new>`, and under an autonomy level that allows it, runs `asf upgrade`
  itself and says so.
- A test: a tick whose installed package is behind the product repo prints the drift line.
