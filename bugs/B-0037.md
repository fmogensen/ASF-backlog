## Symptom

The `tests` workflow on the trunk has been red on every push since 16:51Z: six `HarvestTests` cases (`test_green_branch_lands_on_main`, `test_dry_run_prints_and_does_not_push`, `test_failing_tests_are_held`, `test_index_json_only_conflict_is_resolved`, `test_non_machine_conflict_is_held`, `test_reap_holds_for_live_pid_and_for_no_finished_line`) each assert a printed line and get `''` — `run_harvest` printed nothing. The same suite is green on a developer machine at the same sha. With CI red, no Bug can reach Closed (Closed needs CI green at or after the landing commit).

## Cause

`tests/test_harvest.py::make_repo` runs `git init -q --bare origin` without `-b main` and then clones it. Where `init.defaultBranch` is unset (the hosted runner), the clone's unborn branch is `master`; the fixture commits there and pushes `HEAD:main`, so origin has `main` but the clone never does. `add_job_worktree` then runs `git worktree add -b <branch> <wt> main`, which fails on the unknown ref, no worker branch exists, and harvest has nothing to say. Reproduced locally with `GIT_CONFIG_GLOBAL` pointing at a config with `init.defaultBranch = master`: the same five failures.

## Fix

The fixture names its branch instead of inheriting one: `git init --bare -b main` for the origin and `git symbolic-ref HEAD refs/heads/main` in the fresh clone (before its first commit); the same in `ProductHarvestTests` so the checkout the product harvest fast-forwards is on the trunk by construction. Proven by the local repro (red → green under the `master` default) and a green `tests` run on the trunk after landing.
