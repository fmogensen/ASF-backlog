## Symptom

A session was stopped by killing its client process (`kill <pid>` on the `claude -p` process). The client died, the run's daemon kept working, and 20 minutes later it pushed a commit to the lane branch (`D-7854` on fix/B-0016 at 12:59). Health saw the pid gone and judged the run ended; the work kept coming.

## Cause

`asf/workers/health.py` and `asf/workers/stall.py` treat "pid alive" as "the run is alive": the runtime's process is a client, and the work continues in a daemon the registry never records. Nothing in the lane can actually stop a run; a stopped run's later push lands in a state the state machine believes is terminal.

## Fix

- The runtime records what it takes to stop a run, not only its pid: session id and the process group (`os.setsid` is already used at spawn, so the group id is the pid — record it explicitly as `pgid`), plus the runtime's own stop verb where it has one.
- `lifecycle.stop(run)` — one place that stops a run: signal the group, wait, verify by the log going quiet and by no new push on the branch for a grace period, then mark `end_reason: stopped`. Any later push by a stopped run is a hold with `pushed after stop`, back to the correction loop.
- `health` never infers "ended" from a dead pid alone when the branch moved after the pid died (`lifecycle.gather` already reads the branch — compare timestamps).
- No hand kill is part of the lane; this makes the operator's emergency stop work too.

## Tests

`test_a_stopped_run_that_pushes_afterwards_is_held`; `test_stop_signals_the_group_and_verifies_quiet`; keep the dead-pid judgement tests green.
