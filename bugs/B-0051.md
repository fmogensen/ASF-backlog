## Symptom

09:2x: three fix sessions (B-0005, B-0016, B-0039, ended 22:58 as `finished`) left worktrees with 6 uncommitted files and 0 commits; nothing on origin. Health keeps them (`ended: uncommitted changes`), the feeder re-emits the items every tick, and spawn refuses (`worktree already exists`). Four spec sessions (F-0075/78/82/83) are in the same loop for a different reason: their branches are `spec/<id>`, a prefix the product had not declared, so harvest never looked at them (operator config fixed today).

## Cause

- `health` judges `finished` from the runtime's result line alone (`result_ok`). A session that ends "done" without committing, or without pushing, is finished for health, unlanded for harvest, and re-emitted by the feeder — the three views disagree and the item is stuck behind its own worktree.
- `spawn` refuses an existing worktree instead of resuming the job on it.

## Fix

- `health`: a `finished` result is only `finished` when the job's branch is pushed (`origin/<branch>` exists and contains the worktree's HEAD) — otherwise `end_reason: failed` with the reason `not pushed: <n> uncommitted file(s), <m> unpushed commit(s)`, which D-0048's loop turns into a `FIX → CORRECT` row whose brief says "commit and push what you have, or say why not".
- `spawn`: an existing worktree of an **ended** session for the same item is reused (branch and tree as they are, after `git fetch` + `rebase origin/<main>`), never refused — the refusal stays only for a **live** session (B-0025's rule lands here too).
- `harvest`: every prefix in `conventions.branch_prefixes` is a lane branch (already so; `asf init` writes all four keys with defaults so a product cannot forget one).
- Footprint: `asf/workers/health.py`, `asf/workers/spawn.py`, `asf/init.py` (defaults), `tests/test_workers.py`, `tests/test_install.py`.
