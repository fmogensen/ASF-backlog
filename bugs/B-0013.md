## Description
`asf tick --product <p>` (the live, non-shadow branch of `asf.tick.tick.cmd_tick`) runs step 0 against `product.backlog_dir` — the operator's working checkout — and stops at `print("tick: state updated")`. It never clones, never commits, never pushes. Observed at the first product's 2026-09-21 17:04 cutover: the launchd job exited 0, the log read `tick: state updated`, no `tick: state` commit reached the record's origin, and the derived state (three cards, `index.json`, two metric streams, the daily rollup) sat as uncommitted changes in the operator's checkout until the operator's next unrelated commit swept them in. The `--shadow` branch already has the right shape (`ensure_shadow_clone` → hard reset to origin → step 0 → `commit_local`); the live branch does not share it.

## Fix
The live tick works in its own clone at `~/.ASF/state/<product>/record/` (same helper as the shadow clone: clone once, then `fetch` + `reset --hard origin/<default>` every run — B-1352's rule, derived state owns nothing), runs step 0 there, commits as the factory identity, pushes `HEAD:<default>`, and prints one of `no change` / `committed and pushed` / `committed, push refused — re-derived next run` (exit 1 on the last). The operator's `backlog_dir` is read by nothing in the tick. A test with a bare-repo origin proves: a run produces a pushed commit; a second run with no changes produces none; a run after a failed push leaves origin untouched and the next run re-derives cleanly.
