## Description
The brief gives the workers a model label (`heavy`/`light`) and the launcher maps it through `worker_pool.models`; with no mapping configured it passed the literal `light` to the runtime. Both sessions of the first wave died at once with "There is an issue with the selected model (light)" — and the runtime read the result as `subtype: success`, so health marked them ended clean and nothing was filed.

## Fix
(1) `model_arg` refuses an unmapped label before spawning: `NEEDS OPERATOR: worker_pool.models has no entry for <label> — add it to config.yaml`, printed as the row's waits reason, no session started. (2) The runtime classifies a result whose text matches the CLI's error signatures (unknown model, auth, quota, permission) as failed (`ok: false`, `reason`), health ends the session with that reason and files one Bug per signature. Tests: an unmapped label yields no spawn; a fixture result with the model error is `ok: false`.
