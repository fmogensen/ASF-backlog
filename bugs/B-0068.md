## Symptom

The harvest gate and CI run the suite serially: 835 tests in 324 s on the operator's machine (`python3 -m unittest discover -s tests`, measured 2026-09-22 on main at 03562d2). Every landing pays it once; with B-0040 a tick pays it once, but a red gate's bisect pays it several times, and a session's own pre-push run pays it too. Most of that time is subprocess-bound fixtures (git, `asf tick`, `asf init`) that leave the other cores idle.

## Cause

`unittest` runs one module after another in one process. Nothing in the repo shards the suite.

## Fix

A stdlib-only runner, `tools/run_tests.py`: discovers `tests/test_*.py`, splits the modules into N shards (N = `min(cpu_count, 8)`, `--shards N` overrides; greedy by the test count each module carries so the heavy modules spread), runs each shard in its own `python3 -m unittest` process with the hermetic environment (`asf.hermetic.build`, its own `ASF_TESTS_HOME`), streams each shard's failures as they finish, and prints the suite's own summary shape (`Ran X tests in Ys` then `OK` / `FAILED (failures=…, errors=…)`), exiting non-zero when any shard did. A module that cannot run beside others is listed in `SERIAL` in the runner and runs in one final shard on its own after the parallel ones.

- `~/.ASF/products/asf.yaml` `ci.test_command` → `python3 tools/run_tests.py` (operator config, one line).
- `.github/workflows/tests.yml`: the `tests` step and the hermetic step run the runner (the sample-product step stays a single module).

## Tests

`tests/test_run_tests.py`: the split is balanced and complete (every module in exactly one shard; the serial set last), a red shard fails the run and its failure is in the output, the summary line matches the suite's shape, `--shards 1` is the serial suite.

## Measurement

Before: 324 s (835 tests, serial). After: filled in below when landed.
