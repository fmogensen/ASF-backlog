## Decision
ASF installs as a normal Python tool and never puts code in the operator's config directory.
- **Code**: `pipx install git+https://github.com/<owner>/ASF@v<version>` → `asf` on PATH. Stdlib only. Developers: `pipx install -e <checkout>` so a commit is live at the next tick.
- **`~/.ASF/` holds data only**: `config.yaml`, `products/*.yaml`, `state/<product>/`, `logs/`. No tools directory, ever.
- **The record** is the product's backlog repo; **product-specific scripts** live in the product's own repo and are named in `products/<p>.yaml` as provider settings, or become an ASF provider with config when generic. Nothing product-shaped enters the ASF repo (`check_generic`).
- **Plugin**: installed from the repo through the Claude Code marketplace; every skill runs `asf <view>` from PATH.
- **Scheduler entries and hooks** are written by `asf scheduler install` / `asf hooks install` and call the absolute path of `asf` on PATH, never a checkout.
- **Upgrade**: `pipx upgrade asf`; every write checks the package `schema_version` against each product's record and `config.yaml` — a mismatch refuses writes with `NEEDS OPERATOR: run asf migrate`; `asf migrate` is forward-only and idempotent, commits to the record, and refuses while sessions are in flight (`--drain` waits). Rollback = revert the migration commit + `pipx install asf==<old>`. `asf doctor` shows installed version · each product's schema · each job's version.
- Worker sessions run `asf` from PATH: a new version applies at their next launch, never mid-session.

## Alternatives
A `git clone` + wrapper script (no prerequisite, `git pull` to update, no version pinning) — rejected for lack of pinning and rollback.
